# 视觉文本压缩与文档理解

> **主要来源**：[DeepSeek-OCR: Contexts Optical Compression](https://arxiv.org/abs/2510.18234)（简称 DeepSeek-OCR）；[Glyph: Scaling Context Windows via Visual-Text Compression](https://arxiv.org/abs/2510.17800)（简称 Glyph）；[Optical Context Compression Is Just (Bad) Autoencoding](https://arxiv.org/abs/2512.03643)（简称 Lee 等）；[Visual Merit or Linguistic Crutch? A Close Look at DeepSeek-OCR](https://arxiv.org/abs/2601.03714)（简称 Liang 等）；[DeepSeek-OCR 2: Visual Causal Flow](https://arxiv.org/abs/2601.20552)（简称 DeepSeek-OCR 2）；[LensVLM: Selective Context Expansion for Compressed Visual Representation of Text](https://arxiv.org/abs/2605.07019)（简称 LensVLM）（截至 2026-10-02）。其余来源见第十三节。
> **研究线**：架构思想（把文字渲染成图像、用少量视觉 token 读入，编码器与渲染配置怎样决定压缩率与可读性）· 评测字段（OCR 重建精度、长上下文问答与语言建模分别能说明什么，各论文的「压缩率」口径有何不同）
> **范围与相邻笔记**：
> - ≠ [[多模态架构脉络]]：本篇不写视觉编码器、连接器与多模态架构的通用谱系，只写与文本渲染和压缩相关的编码器设计。
> - ≠ [[长上下文位置编码与系统侧]]：本篇不写位置编码外推与长上下文的系统侧做法。
> - ≠ [[KV缓存量化与压缩]]：本篇不写 KV 缓存的量化、淘汰与压缩。
> - ≠ [[智能体长程记忆]]：本篇不写智能体记忆系统的一般设计，只把光学历史压缩当作一个实例。
> - ≠ [[MMMU多模态推理基准]]：本篇不写多模态推理基准本身。
>
> **意义**：大模型处理长文本的代价随序列长度快速上升。一页文字渲染成图像后，可以用比原文 token 少得多的视觉 token 表示，这让「把文本当图像读」成为一种输入侧压缩。这条思路有两段前史：免 OCR 的文档理解，以及以像素建模语言。2025 年 10 月，DeepSeek-OCR 用 OCR 重建精度给出压缩率与精度的对应关系，Glyph 把渲染压缩用于长上下文问答，这一方向随之集中出现。此后的独立复核指出，重建精度高不等于语言建模有用，模型读出的文字也有相当部分来自语言先验。2026 年的工作一方面改进编码器，一方面把压缩用到推理链与智能体历史上，并用按需展开或放大来处理字小到看不清的问题。

## 一、问题背景

**长上下文的成本**：DeepSeek-OCR 指出，LLM 处理长文本时，计算量随序列长度二次增长（DeepSeek-OCR 第 1 节）。Glyph 把已有的降本路线归为三类（Glyph 第 1 节）：

- 扩展位置编码（如 YaRN），不需额外训练就能接受更长输入，但既不加速推理，外推到更长序列时也难以保持精度；
- 修改注意力机制（稀疏或线性注意力），降低单个 token 的成本，但 token 数不变，上下文到数十万 token 时总开销仍然很大；
- 检索增强，用外部检索缩短输入，但可能漏掉重要信息，还会增加延迟。

**换一种表示**：DeepSeek-OCR 的出发点是，一张包含文档文字的图像可以用远少于等价文字的 token 表示丰富信息，因此经由视觉 token 的光学压缩可能达到高得多的压缩率（DeepSeek-OCR 第 1 节）。Glyph 把这称为「视觉上下文扩展」：不延长 token 序列，而让每个视觉 token 承载多个文本 token，从而在不扩大上下文窗口的情况下处理更长的文本（Glyph 摘要、第 1 节）。LensVLM 补充了一个工程上的理由：改变文本分词（比如用更长的子词单元）需要扩充词表、代价高昂地重新训练，压缩率在选定分词器后就固定了；而 VLM 本来就能处理图像，调整渲染配置就能连续地调节压缩率，不必重训分词器或模型（LensVLM 第 1 节）。

**OCR 为什么是试验场**：DeepSeek-OCR 认为，OCR 任务在视觉与文本表示之间建立了天然的「压缩—解压」映射，又有可量化的评测指标，因此适合检验视觉文本压缩（DeepSeek-OCR 第 1 节）。这也是后来争议的起点：OCR 精度衡量的是能否把文字还原出来，不直接衡量模型能否利用这些内容。

## 二、「压缩率」的几种口径

各论文的「压缩率」定义不同，下文引用数字时注明口径。

| 口径 | 定义（按来源） | 使用者 |
|---|---|---|
| 文本—视觉 token 比 | 原文文本 token 数除以视觉 token 数；DeepSeek-OCR 用自身分词器（词表约 129K）对原文计数 | DeepSeek-OCR 第 4.1 节；Glyph 第 3.2 节；LensVLM 第 3.1 节称「输入压缩率」 |
| 编码器输出比 | 输入 token 数除以编码器输出长度，所有方法压到同一解码器的嵌入空间 | Lee 等第 2.1 节 |
| 有效压缩率 | 原文 token 数除以阅读模型实际处理的全部 token 数；对 LensVLM 而言，分母包括初始视觉 token 与工具展开后追加的 token，因此有效压缩率不高于输入压缩率 | LensVLM 第 3.2 节 |
| token 节省比例 | 与纯文本输入相比，解码器 token 或总 token 减少的百分比 | Text or Pixels 第 1 节；AgentOCR 第 1 节 |

渲染配置（分辨率、字体、字号、行距、页面尺寸等）直接决定每张图能放多少字，因而决定压缩率。Glyph 把这些参数写成一个配置向量，认为字号与 dpi 决定信息密度，版式与间距决定视觉清晰度，调节配置就是在压缩与可读性之间取舍（Glyph 第 3.2 节）。

## 四、两段前史

### 4.1 免 OCR 的文档理解：Donut 与 Pix2Struct

**Donut**：Kim 等指出，当时的视觉文档理解方法把读字交给现成的 OCR 引擎，再在 OCR 输出上做理解，这有三个问题：OCR 的计算成本高，OCR 模型对语言和文档类型不够灵活，OCR 的错误会传到后续环节（Donut 摘要）。Donut 是一个简单的 Transformer，预训练目标就是「读字」：在图像与已生成文字的共同条件下，按阅读顺序预测图中的全部文字，论文称之为伪 OCR 任务（Donut 第 2.3 节）。论文还提供合成文档生成器，使预训练能灵活扩展到不同语言与领域（Donut 摘要）。

**Pix2Struct**：Lee 等让模型学习把遮挡过的网页截图解析成简化 HTML，认为这一目标涵盖了 OCR、语言建模与图像描述等常见预训练信号（Pix2Struct 摘要）。它有两处输入设计与本篇相关（Pix2Struct 第 2.2、2.5 节）：

- 可变分辨率输入：不把图像缩放到固定分辨率，而是缩放到在给定序列长度内能切出最多固定大小图块的尺寸，并用二维绝对位置嵌入，以适应文档、界面与图表的极端长宽比；
- 问题直接渲染在图上：做视觉问答时，不为问题单独留文本通道，而是把问题作为页眉画在原图顶部，让模型通过视觉模态一起读题和读图。

论文称，单个预训练模型首次在文档、插图、用户界面、自然图像四个领域的九项任务中有六项达到最佳（Pix2Struct 摘要）。

### 4.2 以像素建模语言：PIXEL

Rust 等指出，语言模型定义在有限的输入集合上，要支持更多语言就会遇到词表瓶颈：要么嵌入矩阵难以表示足够多的符号，要么输出层计算代价过高（PIXEL 摘要）。PIXEL 把文本渲染成图像，通过重建被遮挡图块的像素来训练，而不是预测词表上的分布；这样可以基于字形相似性或像素的共同激活在语言之间迁移表示（PIXEL 摘要）。

论文用与 BERT 相同的英文数据预训练 86M 参数的 PIXEL，结果是（PIXEL 摘要）：

- 在预训练数据中没有出现过的文字系统上，句法与语义任务明显优于 BERT；
- 在拉丁文字上略弱于 BERT；
- 对字形扰动攻击与语码转换比 BERT 更稳健。

这两段前史提供了两个要素：图像可以直接承载文字信息并被端到端读取；文字的视觉形式本身可以作为语言模型的输入表示。

## 五、文档解析模型

文档解析模型把 PDF 或扫描页转成结构化文本，既是大规模预训练数据的来源，也是「视觉压缩」路线的工程底座。

**olmOCR**：Poznanski 等认为，PDF 文档有可能为语言模型训练提供数万亿新的高质量 token，但版式多样，难以忠实抽取（olmOCR 摘要）。要点如下（olmOCR 摘要、第 2.2 节）：

- 目标：把 PDF 转成按自然阅读顺序排列的干净纯文本，同时保留章节、表格、列表、公式等结构；
- 模型：在 olmOCR-mix-0225（取自 100,000 多份爬取的 PDF，共 260,000 页）上微调的 7B VLM；
- 训练数据的生成：作者发现 GPT-4o 单独处理高密度页面或复杂版式时，容易遗漏内容、不忠实地改写或补写，于是在页面图像之外附上从 PDF 抽取的文本块与位置信息，称为 document-anchoring；
- 成本：论文称处理一百万页只需 176 美元，而用 GPT-4o 要超过 6,240 美元；
- 评测：另建 olmOCR-Bench，收 1,400 份对现有工具仍有难度的 PDF。

**PaddleOCR-VL**：Cui 等把文档解析拆成两个阶段（PaddleOCR-VL 第 2.1 节）：

1. PP-DocLayoutV2 做版面分析，定位语义区域并预测阅读顺序；
2. PaddleOCR-VL-0.9B 依据版面结果，对文字、表格、公式与图表做细粒度识别。

0.9B 模型由 NaViT 式的动态分辨率视觉编码器与 ERNIE-4.5-0.3B 语言模型组成，支持 109 种语言；论文称它在页面级解析与元素级识别上都达到最佳（PaddleOCR-VL 摘要）。

olmOCR 处理的科学 PDF 被用作开放模型的长上下文预训练数据，见 [[OLMo3全栈开放配方]]。DeepSeek-OCR 也把自己定位为预训练数据的生产工具，见第 6.1 节。

## 六、光学上下文压缩：DeepSeek-OCR 与 DeepSeek-OCR 2

### 6.1 DeepSeek-OCR

Wei 等把 DeepSeek-OCR 定位为通过二维光学映射压缩长上下文的初步探索，模型由编码器 DeepEncoder 与解码器 DeepSeek3B-MoE-A570M 组成（DeepSeek-OCR 摘要）。

**DeepEncoder 的设计**（DeepSeek-OCR 第 3.2.1 节）：编码器要同时满足支持高分辨率、高分辨率下激活低、视觉 token 少、支持多种分辨率、参数量适中，论文认为当时的开源编码器都不能全部满足，因此自行设计：

- 前半部分以窗口注意力为主，采用 SAM-base，约 80M 参数，处理大量图块 token；
- 中间用 2 层卷积模块对视觉 token 做 16 倍下采样；
- 后半部分是全局注意力的 CLIP-large；
- 以 1024 乘 1024 的输入为例，先切成 4096 个图块 token，经压缩模块后变为 256 个，再进入全局注意力，从而控制激活内存。

**多分辨率模式**：原生分辨率有四档，Tiny、Small、Base、Large 分别对应 512、640、1024、1280 像素见方的输入和 64、100、256、400 个视觉 token；另有由多个局部切片加一个全局视图组成的动态分辨率模式 Gundam（DeepSeek-OCR 第 3.2.2 节）。同一个模型支持多档分辨率，才能测试解码一定数量的文字需要多少视觉 token。

**解码器**：DeepSeek-3B-MoE，推理时激活 64 个路由专家中的 6 个和 2 个共享专家，激活参数约 570M（DeepSeek-OCR 第 3.3 节）。

**压缩率与精度**：论文在 Fox 基准的英文文档中选取原文 600 到 1300 个 token 的 100 页，只用 Tiny（64 个视觉 token）与 Small（100 个）两档测试（DeepSeek-OCR 第 4.1 节）。结果（DeepSeek-OCR 摘要、第 1 节）：

- 压缩率低于 10 倍时，解码（OCR）精度可达 97%；
- 9 到 10 倍时精度在 96% 以上，10 到 12 倍时约 90%，20 倍时约 60%；
- 论文称，考虑到输出与标准答案的格式差异，实际精度还会更高。

论文对超过 10 倍后精度下降给出两个可能原因：长文档的版式更复杂；长文本在 512 或 640 分辨率下变得模糊。作者认为前者可以通过把文本渲染到统一版式的单页来解决，后者则可以当作「遗忘机制」的特性（DeepSeek-OCR 第 4.1 节）。在 OmniDocBench 上，幻灯片只需 64 个视觉 token 就有满意表现，书籍与报告用 100 个即可；报纸的文字有 4,000 到 5,000 个 token，远超其他模式的 10 倍压缩，需要 Gundam 甚至更高的模式（DeepSeek-OCR 第 4.2 节）。

**作者设想的用途**：

- 光学遗忘：把多轮对话中较早轮次的历史渲染成图像做初步压缩，再逐步缩小更旧的图像，使 token 数递减、文字逐渐模糊，以此模拟遗忘（DeepSeek-OCR 图 13 图注、第 5 节）；
- 数据生产：单张 A100-40G 每天可生成 200,000 页以上的 LLM 或 VLM 训练数据（DeepSeek-OCR 摘要）。

**作者自述的限度**：论文结论写明，仅靠 OCR 不足以充分验证真正的光学上下文压缩，作者计划做数字—光学文本交错预训练与大海捞针等测试（DeepSeek-OCR 第 6 节）。

### 6.2 DeepSeek-OCR 2：按语义重排视觉 token

DeepSeek-OCR 2 关注的是另一个问题：常规 VLM 按固定的光栅顺序（从左上到右下）把视觉 token 送入 LLM，与人按逻辑结构扫视复杂版面的方式不符（DeepSeek-OCR 2 摘要）。DeepEncoder V2 的做法（DeepSeek-OCR 2 第 3.2 节）：

- 视觉分词器沿用 SAM-base 加两层卷积，保留 16 倍 token 压缩；
- 把 DeepEncoder 中的 CLIP 换成 LLM 式结构，用 Qwen2-0.5B 实例化；
- 在视觉 token 之后接一组数量相同的可学习查询（因果流 token）：视觉 token 之间用双向注意力，查询之间用因果注意力，每个查询能看到全部视觉 token 和之前的查询；
- 只把查询的输出送入解码器，由此在进入 LLM 前完成按图像语义的重排。

论文把这理解为两个一维因果推理器的级联：编码器负责阅读顺序，解码器负责视觉任务本身（DeepSeek-OCR 2 第 6.1 节）。送入 LLM 的视觉 token 限制在 256 到 1120 个，上限低于 DeepSeek-OCR Gundam 模式的 1156（DeepSeek-OCR 2 第 1 节、第 3.2.3 节）。

结果：在 OmniDocBench v1.5 上得 91.09%，比 DeepSeek-OCR 提高 3.73%（原文写法），阅读顺序的编辑距离从 0.085 降到 0.057（DeepSeek-OCR 2 第 5.1 节）。论文也指出报纸类文档仍是弱项，原因可能是视觉 token 上限较低，以及报纸训练样本只有 250k 条（DeepSeek-OCR 2 第 5.2 节）。

## 七、长上下文扩展：Glyph 及其后

### 7.1 Glyph

Cheng 等的 Glyph 分三个阶段（Glyph 第 3 节）：

1. **持续预训练**：把大量长文本用多样的渲染配置与风格主题渲染成图像，训练三类任务：重建页面全部文字的 OCR 任务；部分文本渲染成图像、其余保留为文本的交错语言建模；给出部分页面、补全其余内容的生成任务。目的是把长上下文理解能力从文本模态迁移到视觉模态。
2. **LLM 驱动的渲染搜索**：用遗传算法搜索渲染配置。每一代在验证集上渲染、推理，记录准确率与压缩率，再由 LLM 分析结果并建议变异与交叉，直到准确率和压缩率都不再提升。
3. **后训练**：在搜到的配置下做 SFT 与 RL（GRPO），并加入辅助 OCR 任务，以加强对图中文字的识别、对齐视觉与文本表示。

骨干模型是 GLM-4.1V-9B-Base（Glyph 第 4.4 节）。主要结果：

- 在多个长上下文基准上达到 3 到 4 倍 token 压缩，准确率与 Qwen3-8B 等同规模领先模型相当；预填充最多快 4.8 倍，解码最多快 4.4 倍，SFT 训练约快 2 倍（Glyph 第 1 节）；
- LongBench 上的平均有效压缩率为 3.3 倍，部分任务约 5 倍；MRCR 上平均为 3.0 倍（Glyph 第 4.2.1 节）；
- 后训练改用有效压缩率 8 倍的配置，在序列长度从 128K 扩到 1024K 的 MRCR 上，表现与 GLM-4-9B-Chat-1M、Qwen2.5-1M 相当；论文据此称 128K 上下文的 VLM 可以处理百万 token 级的文本任务（Glyph 摘要、第 4.5 节）；
- 消融显示，搜索得到的配置在相近压缩率下优于随机采样与人工设计的配置，加入辅助 OCR 任务也带来一致提升（Glyph 第 4.5 节）；
- 在 MMLongBench-Doc 长文档理解上比骨干模型有明显提升（Glyph 第 4.4 节）。

论文自述的局限（Glyph「Limitations and Future Work」节）：

- 结果对分辨率、字体、间距等渲染参数明显敏感，如何让模型在不同渲染设定下都稳健，仍是开放问题；
- UUID 这类罕见字母数字串对当前 VLM 仍很困难；
- 评测以长上下文理解为主，没有覆盖智能体或重推理任务；与文本模型相比，视觉文本模型在不同任务之间的泛化较弱。

### 7.2 现成模型的 token 效率：Text or Pixels

Li 等不做任何训练，只把长文本渲染成一张图像交给现成的多模态模型（Text or Pixels 摘要）。在 RULER 的大海捞针任务上，GPT-4.1-mini 与 Qwen2.5-VL-72B 在解码器 token 最多减少 58% 的情况下保持 97% 到 99% 的准确率；在 CNN/DailyMail 摘要上，以相同或更高的压缩率优于两种专门的剪枝基线（Text or Pixels 第 1 节）。效率上，视觉编码在较小模型上会带来一些额外开销，而在较大模型上，解码器序列变短最多带来 45% 的端到端加速（Text or Pixels 第 1 节）。论文承认，没有充分评估数万 token 以上的超长上下文（Text or Pixels「Limitations」节）。

### 7.3 把生成阶段也压缩：VIST2

Jiao 等指出，此前把输入渲染成图像的做法只在预填充阶段减少 token，逐 token 生成时的计算与内存开销并没有降低（VIST2 摘要）。VIST2 把输入文本块与它们的视觉编码交错排列，预测下一个文本 token 时只依赖前文的视觉 token，从而在预填充与生成两个阶段都节省 token；模型规模从 0.6B 到 8B（VIST2 摘要）。论文报告，在 4 倍压缩率下，长文写作任务上首 token 生成平均快 3 倍，内存减少 77%，FLOPs 减少 74%（VIST2 摘要）。

## 八、质疑与边界

### 8.1 重建不等于语言建模：Lee 等

Lee 等把 DeepSeek-OCR 看作一个自编码器：文本渲染成图像，编码成少量视觉 token，再解码回文本。论文指出，词元嵌入本身就是高维的学习表示，渲染成像素等于先丢掉它们，再让视觉编码器从像素里恢复（Lee 等第 1 节）。论文检验了两个隐含假设（Lee 等第 1 节）：

- A1：视觉压缩对文本重建有独特优势；
- A2：DeepSeek-OCR 的重建结果说明视觉压缩对语言建模有用。

**实验设计**（Lee 等第 2.1、3.1 节）：所有方法共用 DeepSeek-OCR 的预训练解码器。对照的编码器有两种：只有一个可学习分隔符的均值池化（滑动窗口平均词元嵌入），以及 13M 到 92M 参数、随机初始化的层次卷积编码器；而 DeepSeek-OCR 的视觉编码器有 400M 参数，在超过 500M 张图像上预训练过。数据是英文维基百科片段：重建任务用前 1,000 个 token，语言建模任务用 1,000 个 token 的上下文预测后 1,000 个 token。语言建模另设截断基线，即在相同 token 预算下只保留最近的原文、丢弃更早的内容。

**结论**（Lee 等摘要、第 2.2、3.2、4.2 节）：

- 重建：直接方法在每个压缩率下都与视觉相当或更好；层次编码器在所有压缩率下最好，均值池化在中等压缩率下与视觉相当。
- 语言建模：视觉与截断表现相当，并在每个压缩率下都输给层次编码器；即使额外保留最近 100 个 token 的原文，视觉与均值池化仍不如截断。
- 事实回忆：所有压缩方法都优于截断，因为截断丢掉了远处的上下文；但视觉在任何压缩率下都没有超过最好的直接方法。

**论文的解释**：视觉路径在共有的学习瓶颈之前多了一道像素空间瓶颈。图像分辨率与输出 token 数绑定，压缩率越高，图像越小，像素空间能容纳的信息也越少；直接方法只受输出 token 数这一项约束（Lee 等第 2.2 节）。

**论文自述的限度**（Lee 等第 5 节）：

- 上下文只有 1,000 个 token，更长时压缩与截断的取舍可能改变；
- 只用英文维基百科，没有测代码、对话或嘈杂网页文本；
- 只测了 DeepSeek-OCR 的视觉编码器；
- 每组配置只训练一次、一个 epoch，没有报告方差。

### 8.2 视觉能力还是语言拐杖：Liang 等

Liang 等认为，DeepSeek-OCR 的高 OCR 分数可能并不反映视觉理解：解码器是 LLM，视觉 token 很少时，它可以靠语言统计知识「补空」（Liang 等第 1 节）。论文用语义扰动把模型的视觉识别能力和语言先验分开（Liang 等摘要、第 1 节）：

- **句级扰动**：把句子换成语义荒谬但视觉相似的替换。平均精度在 Tiny 档下降 11.2%，Small 档下降 3.6%，Base 档下降 0.6%，说明视觉 token 越少，全局语言先验帮得越多。
- **词级扰动**：打乱词内字母、完全打乱或换成随机字符序列；没有语言支撑时，精度从约 90% 跌到约 20%。
- **跨模型对照**：在 13 个 OCR 与 VLM 模型上，端到端架构普遍严重依赖先验，传统流水线式 OCR 对语义扰动稳健得多；论文还发现视觉 token 越少，越依赖先验，幻觉风险越高。
- **上下文压力测试**：把长篇叙事切成 500 到 20,000 token 的片段渲染成文档图像，DeepSeek-OCR 各档都在 8,000 到 10,500 token 之间失效（Liang 等第 1 节、第 6.1、6.2 节）。

论文由此认为，当前的光学压缩以牺牲保真度换取 token 减少，不加架构改造就不足以用于长上下文，并主张采用不依赖先验的评测协议（Liang 等第 8 节）。论文也说明，实验集中在稠密文字上，没有充分测试公式、代码、表格这类语言先验预测力较弱的数据（Liang 等「Limitations」节）。

### 8.3 理解与读字的差距：VTCBench

Zhao 等建立了视觉文本压缩下的长上下文理解基准，分检索与聚合、需要推断隐含关联的推理、长期对话记忆问答三种设定，另有模拟多样输入的 VTCBench-Wild（VTCBench 摘要）。结论是：大多数 VLM 尽管能很好地解码文字信息（如 OCR），对经过视觉压缩的信息的长上下文理解能力却出人意料地差，抓不住上下文中的长程关联与依赖（VTCBench 摘要）。

### 8.4 可读性的边界

LensVLM 把边界说得很直接：VLM 的图像编码器把固定尺寸的图像映射成固定数量的视觉 token，渲染分辨率因此成了细粒度的压缩旋钮；但压缩一加大，字符就缩到编码器的有效分辨率以下，彼此无法区分（LensVLM 摘要）。论文的说法是，超过某个压缩率后，像素中已经不含相应的信息（LensVLM 第 1 节）。

渲染配置的影响也很大：在大致相同的压缩率下，基座模型在 20 种配置之间的准确率相差 32 个点（LensVLM 第 5.1 节）。这与 Glyph 自述的渲染参数敏感性一致。

### 8.5 小结

| 来源 | 任务 | 结论方向 |
|---|---|---|
| DeepSeek-OCR | OCR 重建（Fox，600 到 1300 token） | 10 倍以内约 97%，20 倍约 60% |
| Glyph | 长上下文问答（LongBench、MRCR 等） | 3 到 4 倍压缩下与同规模文本模型相当 |
| Text or Pixels | 大海捞针与摘要，现成模型 | 解码器 token 约省一半而效果不降 |
| Lee 等 | 重建、语言建模、事实回忆（1,000 token） | 视觉路线不优于直接压缩嵌入；语言建模上与截断相当 |
| Liang 等 | 语义扰动下的 OCR | 去掉语言先验后精度从约 90% 降到约 20% |
| VTCBench | 检索、推理、记忆 | 能读字不等于能理解长程关联 |

正反证据针对的任务、上下文长度与基线不同，本篇并列，不作裁决。

## 九、压缩后的使用方式

### 9.1 推理链的光学记忆：VTC-R1

Wang 等指出，已有的高效推理方法要么需要额外的训练或采样阶段，要么依赖外部强模型来压缩推理链，两者都可能丢掉对推理关键的细节（VTC-R1 第 1 节）。VTC-R1 把推理过程拆成多段：每段完成后渲染成图像，下一段推理时把之前各段的图像与原题一起送回 VLM，作为「光学记忆」（VTC-R1 摘要、第 1 节）。

论文基于 OpenR1-Math-220K 构建训练数据，最多达到 3.4 倍 token 压缩，并微调了 Glyph 与 Qwen3-VL（VTC-R1 第 1 节）。在 MATH500、AIME25、AMC23、GPQA-Diamond 等基准上，VTC-R1 一致优于标准的长上下文推理，端到端推理延迟最多快 2.7 倍（VTC-R1 摘要、第 1 节）。论文选数学推理作试验场，理由是其符号结构与逐步推导天然适合视觉渲染（VTC-R1 第 1 节）。

### 9.2 智能体历史的光学自压缩：AgentOCR

Feng 等面对的问题是，多轮交互中智能体要缓存全部观测与动作，文本历史迅速膨胀，推高 token 与内存成本（AgentOCR 摘要、第 1 节）。AgentOCR 把累积的观测—动作历史渲染成一张紧凑图像，策略以此为条件做决策（AgentOCR 摘要）。两项机制：

- **分段光学缓存**：把历史拆成可哈希的片段并缓存渲染结果，避免历史增长时反复渲染；论文称渲染加速 20 倍以上（AgentOCR 摘要、第 1 节）。
- **智能体自压缩**：渲染器作为工具开放给智能体，智能体每步输出一个压缩因子，图像的高与宽各除以该因子的平方根。训练时加入压缩感知奖励：只有回合成功时才给压缩因子的自然对数作为奖励；为防止智能体贪图压缩，这项奖励每隔若干训练轮才注入一次（AgentOCR 第 4.3 节）。

实验以 Qwen2.5-VL 3B 与 7B 为骨干，在 ALFWorld 与基于搜索的问答上进行（AgentOCR 第 5.1 节）。结果：

- 保留文本智能体 95% 以上的表现，token 消耗减少 50% 以上，峰值 token 最多减少 80%（AgentOCR 第 1 节）；
- 固定压缩因子为 1.2 时约省 55% 的 token，ALFWorld 与搜索任务分别保留文本基线的 99.5% 与 95.0%；压缩因子到 2.0 时约省 67%，ALFWorld 仍保留 87.2%，文字密集的搜索任务则降到 66.8%（AgentOCR 第 5.3 节）。

论文据此认为，粗粒度场景理解为主的任务更耐压缩，文字密集的任务对模糊很敏感，因此需要动态选择压缩率（AgentOCR 第 5.3 节）。论文自述的局限包括：只用了并非为 OCR 密集任务设计的现成 VLM；渲染器参数固定，没有系统研究敏感性；只处理以文本为主的历史，没有覆盖 GUI 截图、图表等本身就是视觉的内容（AgentOCR「Limitations」节）。

### 9.3 按需展开：LensVLM

LensVLM 不要求 VLM 在任何压缩率下都读得清，而是让它先扫描压缩后的图像，再调用学到的工具把相关图像展开为未压缩的形式（LensVLM 摘要、第 1 节）。论文的假设是：压缩图像即使不再保留逐字内容，也保留了足够的粗略证据，足以判断答案大概在哪一块（LensVLM 第 3.2 节）。工具返回的形式可以是原文、OCR 抽出的文本或高分辨率图像；推理框架靠提示就能用于前沿 VLM，后训练（合成轨迹、SFT 与 RL）则让较小的模型可靠地使用它（LensVLM 第 1 节、第 3.2 节）。

以 Qwen3.5-9B-Base 为基座，在七个文本问答基准上（LensVLM 摘要、第 1 节）：

- 有效压缩率 4.3 倍时，准确率与全文上限相当；
- 有效压缩率最高到 10.1 倍时，仍优于检索、文本压缩与视觉压缩基线；
- 在三种约 3 倍压缩的版式上，训练前准确率相差 18.0 个点，训练后缩小到 0.5 个点（LensVLM 第 5.1 节）。

工具形式的对比（LensVLM 第 5.2 节）：

- 对渲染出来的文本，返回原文效果最好；拿不到原文时，OCR 文本效果相近；放大图像不如两种文本工具；
- 对原生的多模态文档图像，排序反过来，放大图像优于文本工具，因为文本丢掉了版式与视觉结构。

### 9.4 放大关键片段：AGAR

Zeng 等研究 VLM 内部怎样处理渲染文本。他们发现，定位证据的注意力在中后层急剧出现，而且与答对与否基本脱钩：答错的样本也几乎同样关注到了正确证据，论文称之为「能定位、未利用」（AGAR 摘要、第 3.3 节）。

一个对照实验：在 1,000 个 HotpotQA 样本上，用 Qwen3-VL-8B，按标准答案把证据片段的字号放大到 1.5 倍、其余不变；修复与破坏的比例约为 4 比 1，SubEM 提高约 16 个点（AGAR 第 3.4 节）。

据此提出的 AGAR 不需训练：用模型自己中后层的注意力选出最重要的若干图块，映射回词语片段，放大后重新渲染页面，再推理一次（AGAR 摘要）。论文在九个基准、四个骨干模型上报告一致提升，并称它可与后训练叠加，对视觉侧与文本侧的输入退化都稳健（AGAR 摘要）。局限是需要访问骨干模型的注意力分数，难以用于闭源 VLM（AGAR 第 6 节）。

LensVLM 与 AGAR 处理的是同一个边界：压缩图像中看不清的部分，要么换回原文，要么放大重画。

## 十、意义

1. **输入表示成为压缩维度**：与位置编码外推、注意力改造、KV 缓存压缩不同，视觉文本压缩在输入侧减少 token 数，Glyph 称其与基于注意力的方法正交（Glyph 第 5 节）。
2. **重建与理解要分开评估**：DeepSeek-OCR 的压缩率—精度曲线是 OCR 重建结果；Lee 等、Liang 等与 VTCBench 从语言建模、语言先验与长程理解三方面说明，重建得好不等于用得好。
3. **压缩与可读性此消彼长**：字小到低于编码器有效分辨率时，信息不在像素中。后续工作不再追求一律高压缩，而是让模型自选压缩率（AgentOCR）、按需展开（LensVLM）或放大证据（AGAR）。
4. **文档解析是基础设施**：olmOCR 与 DeepSeek-OCR 都把 PDF 转文本作为预训练数据的生产手段，PaddleOCR-VL 则强调实际部署；这类用途不依赖「压缩」叙事是否成立。

## 十一、局限与待核实

1. **适用范围**：现有证据集中在以读为主、对逐字精确度要求不高的任务。Glyph 自述 UUID 等罕见字符串难以识别，AgentOCR 发现文字密集的搜索任务在高压缩下下降明显，Liang 等发现去掉语言先验后精度大幅下降。
2. **渲染配置的影响**：Glyph 与 LensVLM 都报告结果对渲染参数敏感；LensVLM 称训练可大幅缩小这一差距，但只在其设定下验证。各论文的数字都依赖各自的渲染配置。
3. **缺少统一对照**：多数工作与文本模型或截断比较，只有 Lee 等在相同解码器下与直接压缩文本嵌入的方法比较，而那组实验只有 1,000 个 token、只测了 DeepSeek-OCR 的编码器。视觉压缩与文本侧上下文压缩方法之间，还没有长上下文、多任务的统一对照。
4. **压缩率口径不一**：文本—视觉 token 比、有效压缩率与 token 节省比例不能直接对比，见第二节。
5. **DeepSeek-OCR 的上限测试与 Liang 等的写法**：Liang 等在摘要中写「around 10,000 text tokens」处全面崩溃，第 1 节与第 8 节写 8,000 到 10,500 token 之间失效，第 6.2 节写 Tiny、Base、Large 在 8,500 token 前崩溃、Small 在 10,500 token 崩溃。本篇按第 1 节的区间写。
6. **DeepSeek-OCR 2 的提升口径**：论文写「3.73% improvement」，没有说明是百分点还是相对提升，本篇照原文写。
7. **版本**：Donut 当前为 v5，PIXEL 为 v2，Pix2Struct 为 v2，olmOCR 为 v3，PaddleOCR-VL 为 v4，Glyph 为 v2，Text or Pixels 为 v2，Lee 等为 v2，VTCBench 为 v2，Liang 等为 v2，AgentOCR 为 v3，VIST2 为 v2，VTC-R1 为 v2，LensVLM 为 v3。本篇按 abs 页当前版本引用，早期版本的表述与数字可能不同；Lee 等的事实回忆实验、AgentOCR 与 LensVLM 的部分数字出自当前版本。AgentOCR 的 abs 页仍标注「Work in progress」。

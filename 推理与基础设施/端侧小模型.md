# On-device SLM（MobileLLM / Phi-4 × Gemma 4 小尺寸对照）

> **定位**：P1 横切——相对旗舰 / 云侧卡，立 **端侧与小模型（SLM）** 两条独立产品轴：**(A) MobileLLM** 的深薄架构 + 权重共享 + DRAM 层级叙事；**(B) Phi-4** 的合成数据主导配方 + 后训练 PTS-DPO。与 **[[Gemma4技术报告深读]] Gemma 4** 的 **E2B/E4B PLE + mobile QAT** 只做对照，**勿重写** Gemma 4 全文。

> - **禁止重写 B8** 合成/textbook 通史；Phi-4 只记本报告的数据支柱与 PTS。
> - **禁止重写 B7 / [[投机解码发展时间线]]** 投机解码通史；本篇若点到端侧吞吐，仅作 MobileLLM 延迟表索引。

## 二、问题立轴：云成本 / 时延 → 端侧约束空间

### 2.1 MobileLLM 的硬件坐标系（§1 + Figure 2）

报告把手机内存层级画成：

| 层级 | 量级（文中举例） | 含义 |
|---|---|---|
| SoC SRAM / LLC | **~8–32 MB**（如 Pixel 8 **8 MB**；iPhone 15 A16 **24 MB**） | 通常只够 **一个** transformer block |
| DRAM | **~6–12 GB** | 真正可常驻的权重+KV 工作集上限 |
| Flash | **~100 GB** | 存储充裕，但带宽远低于 DRAM，不适合做高速工作集 |

动机叙事（照录量级，非外推）：云侧 GPT-4 级若按文中假设施到「每人每天 5% 时间、50 tok/s」会需要海量 H100；手机侧用 **350M 8-bit** 约 **0.035 J/token**，声称可支撑「一整天对话」量级；**125M** 标称可达 **~50 tok/s**，对照 iPhone App MLC Chat 跑 LLaMA 7B 的 **3–6 tok/s**。

→ 设计目标收束为：**参数 &lt; 1B**、优先 **准确率 × 存储/带宽**，而非追云侧 scaling 口号。

### 2.2 Phi-4 的「小」是另一档

Phi-4 是 **14B** decoder-only，默认上下文 **4K**、midtraining 后 **16K**——相对手机 DRAM 的「严格端侧」偏松，相对 frontier 则属 **SLM / 小旗舰**。报告主张：相对「主要靠有机网页/代码预训练」，phi-4 **战略性地全程掺入合成数据**；相对早期 Phi「主要蒸馏教师（GPT-4）」，phi-4 在 STEM QA 上 **实质超过教师**，作为「超越蒸馏」的证据。

### 2.3 与 Gemma 4 小尺寸的接口（仅对照）

| 轴 | MobileLLM | Phi-4 | Gemma 4 E2B/E4B（[[Gemma4技术报告深读]]） |
|---|---|---|---|
| 参量口径 | 125M–1.5B dense | **14B** dense | **2.3B/4.5B effective**（PLE 后 total **5B/8B**） |
| 主杠杆 | 深薄 + 共享 + GQA | 合成数据 + 后训练 | PLE + 缩小视听编码器 + **mobile QAT** |
| 模态 | 文本（chat / API calling） | 文本（强 STEM/代码） | 原生 text/image/audio（+ docs video） |
| 内存叙事 | SRAM 装不下多 block → immediate share | 云/边缘 14B 推理成本对照表 | Table 3：E2B quant **0.8 Gb**；docs Mobile **~1.1 GB**（含开销） |

## 三、MobileLLM：架构优先的 sub-billion 配方

### 3.1 四件套基线（§2.2 → 命名 MobileLLM）

报告在 ~125M / ~350M 上系统扫深度-宽度，并组合四项技术建成基线：

| # | 技术 | 报告主张（锚 PDF） |
|---|---|---|
| 1 | **SwiGLU FFN** | 相对 ReLU FFN，125M zero-shot 均分 **42.6→43.9** |
| 2 | **Deep-and-thin** | 与 Kaplan scaling「宽重要」直觉相反：同参下更深更薄更好；约 **19** 个同参变体实验；既往 125M 常 **12** 层，本文推到 **~30** 层 |
| 3 | **Input–output embedding sharing** | 小模型词嵌占比高（例：dim 512、vocab 32k → 输入+输出各 ~16M，合计 **&gt;20%** @125M；LLaMA-7B 仅 ~3.7%）→ 共享可挤出深度预算 |
| 4 | **Grouped-query attention (GQA)** | 查询头 **16** 较优；kv-head **16→4** 时 125M 精度近乎持平、350M 仅 **−0.2** 且约 **−10%** 体积；再抬 embedding 维保住总参 → 125M 再 **+0.4** |

**最终架构规格（Appendix Table 9，照录）：**

| Model | #Layer | #Head | #KV-Head | Emb Dim | Hidden Dim | #Params |
|---|---:|---:|---:|---:|---:|---:|
| MobileLLM-125M | 30 | 9 | 3 | 576 | 1536 | 124.6M |
| MobileLLM-350M | 32 | 15 | 5 | 960 | 2560 | 345.3M |
| MobileLLM-600M | 40 | 18 | 6 | 1152 | 3072 | 603.1M |
| MobileLLM-1B | 54 | 20 | 5 | 1280 | 3584 | 1.0B |
| MobileLLM-1.5B | 54 | 25 | 5 | 1600 | 4352 | 1.5B |

### 3.2 Immediate block-wise weight sharing → MobileLLM-LS（§2.3）

动机：深度有益，但端侧 **不能** 为深度无限加参。做法：复制 transformer block 权重以增加「有效层数」。

| 策略（Figure 6） | 精度（Table 2 Avg） | 硬件读法 |
|---|---|---|
| Immediate block-wise（相邻块共享，立刻算两次） | 125M **45.0**；350M **50.2** | 共享权重可留在 **~20MB SRAM**，避免 DRAM 往返 |
| Repeat-all-over | 略高（45.2 / 50.7） | 缓存不友好 |
| Reverse share | 较低 | — |

**选型：** 精度上 repeat-all-over 略优，但报告因内存层级选择 **immediate block-wise** → **MobileLLM-LS**（「#layer」计 **互异权重** 层数）。声称：**不增加模型体积**，仅边际延迟。

### 3.3 训练设置（§2.1 / §3.1）

| 项 | 值 |
|---|---|
| Optimizer | Adam；weight decay **0.1**；初始 LR **2e-3**；cosine decay |
| 硬件 | **32×A100**；每卡 batch **32** |
| 探索 | **120k** iter / **0.25T** tokens |
| 主结果（Table 3/4） | **480k** iter / **1T** tokens |
| 附录消融注 | 逐步堆技术时部分行在 **0.25T**；最终 MobileLLM / LS 在 **1T** |

### 3.4 主结果摘录（禁止与 Phi/Gemma 榜混并）

**Zero-shot common sense Avg（Table 3）：**

| 模型 | #Layers | #Params | Avg |
|---|---:|---:|---:|
| OPT-125M | 12 | 125M | 42.6 |
| GPT-neo-125M | 12 | 125M | 42.9 |
| RWKV-169M | 12 | 169M | 43.6 |
| **MobileLLM-125M** | 30 | 125M | **46.3** |
| **MobileLLM-LS-125M** | 30 | 125M | **47.0** |
| OPT-350M | 24 | 331M | 43.9 |
| RWKV-430M | 24 | 430M | 47.0 |
| **MobileLLM-350M** | 32 | 345M | **51.3** |
| **MobileLLM-LS-350M** | 32 | 345M | **52.1** |

Abstract 口径：相对既往 125M/350M SOTA **+2.7% / +4.3%**；LS 再 **+0.7% / +0.8%**。

更大档（Appendix Table 8 Avg）：600M **54.3**；1B **57.3**；1.5B **59.4**（并称超过部分更老的更大模型——逐项见原表）。

**下游端侧任务：**

| 任务 | 数字锚 | 读法 |
|---|---|---|
| Chat（Table 5） | LS-350M：MT-Bench **3.16**；AlpacaEval win **48.20%**（判官 GPT-4；参考 text-davinci-001，其 self-win ~50%） | 显著高于同档 OPT/Pythia/BLOOM，并压过部分 **&gt;1B** 旧模型 |
| API calling（Table 6） | MobileLLM-350M：EMintent **65.3** / EMstructure **48.8** vs LLaMA-v2 7B **62.8 / 50.9** | 意图匹配可贴近 7B；Rouge 仍落后——报告强调端侧「调用对不对」优先于长回复文采 |
| 数据 | 自建合成：**5000** train / **2500** test；平均 **~8** 轮；FT **4** epoch，Adam LR **2e-5** | |

**量化兼容（§3.4）：** per-token min-max **W8A8 PTQ**，相对 BF16 均分下降 **&lt;0.5**，且与 layer sharing 兼容（Figure 7）。

**设备延迟（Table 7，iPhone 13 / iOS 17.2.1 / MPS，125M 配置）：**

| | Load | Init | Execute |
|---|---:|---:|---:|
| MobileLLM（30 层） | 39.2 ms | 1361.7 ms | **15.6 ms** |
| MobileLLM-LS（2×30，相邻共享） | 43.6 ms | 1388.2 ms | **16.0 ms** |
| 60-layer non-shared | 68.6 ms | 3347.7 ms | **29.0 ms** |

→ LS 相对真·60 层大幅省加载/执行；相对基线仅边际变慢。

**KD 负结果（§3.5）：** 以 LLaMA-v2 7B 为教师蒸馏 125M/350M → 训练变慢 **2.6–3.2×**，精度可比或更差 → 本文主路径仍是 hard-label 从零训。

## 四、Phi-4：数据质量优先的 14B 配方

### 4.1 架构增量（相对 phi-3-medium，§3）

| 项 | phi-4 |
|---|---|
| 骨架 | Decoder-only Transformer；**14B**；**紧密跟随 phi-3-medium** |
| Tokenizer | **tiktoken**；padded vocab **100,352**（含 unused）——报告写为更好多语 |
| 注意力 | 预训练 **4K full attention**（phi-3-medium 为 **2K sliding window**） |
| 上下文扩展 | Midtraining → **16K**；RoPE base 提至 **250K**；LR 降至预训练峰值的 **1/10**；训 **250B** tokens |
| 预训练规模 | **~10T** tokens；峰值 LR **3e-4**；weight decay **0.1**；global batch **5760**；linear warm-up + decay |

**报告未给出** 完整层宽/头数表（「minimal changes to phi-3 architecture」）→ **勿编造** phi-3-medium 的层配置到本卡。

### 4.2 三大支柱（Introduction）

1. **合成数据用于 pretrain + midtrain**：约 **50** 类合成数据集；原则含多样性、难度递进、从种子出发、**Chain-of-Thought** 等；技术含 multi-agent prompting、self-revision、instruction reversal、代码执行校验等。
2. **有机数据的精心过滤**：网页 / 许可书籍 / 代码等作 **种子** 与直接预训练补充；强调「脏种子会严重污染衍生合成」。
3. **后训练**：精炼 SFT + **Pivotal Token Search (PTS)** 构造的 DPO 对 + judge-guided 全长 DPO。

### 4.3 预训练数据配比（Table 5）

| Source | Fraction of training | Unique tokens | Epochs |
|---|---:|---:|---:|
| Web | 15% | ~1.3T | 1.2 |
| Web rewrites | 15% | ~290B | 5.2 |
| **Synthetic** | **40%** | ~290B | **13.8** |
| Code data | 20% | ~820B | 2.4 |
| Acquired sources | 10% | ~580B | 1.7 |

关键消融主张（§3.1–3.2）：

- 同 token 预算下，**多 epoch 刷合成** 往往优于加更多新鲜 web（Figure 2）。
- **纯合成** 在知识向榜（如 TriviaQA）明显吃亏、幻觉风险升 → 最终仍保留 web / acquired。
- 1T 短视界搜配比后，定稿避免「均匀三分」；合成偏重，但用知识向 web 平衡。

Midtraining 数据：约 **30%** 新增长上下文数据 + **70%** 预训练 recall；相对「把短样本 pad 拼长」，**天然长文档** 更优。

### 4.4 后训练：SFT → PTS-DPO → Judge-DPO（§4）

| 阶段 | 要点 |
|---|---|
| **SFT** | ~**8B** tokens；域含 math/coding/reasoning/conversation/identity/safety；**40** 语言；LR **1e-6**；ChatML 模板 |
| **DPO stage 1（PTS）** | 在可自动判对错的任务（数学、QA、代码）上，用采样估计前缀成功概率，找出使 $p(\mathrm{success})$ 剧变的 **pivotal token**，构造 **单 token** 偏好对，减少全长 DPO 的梯度噪声 |
| **DPO stage 2（judge）** | ~**850k** 对；提示来自公开指令集 + safety/RAI；候选来自 GPT-4o / GPT-4t / 本模型；GPT-4o 按 accuracy/style/detail 打标 |
| 附加 | 各阶段混入 **1–5%** hallucination + safety 数据；另有拒答式幻觉缓解 SFT/DPO（§4.4，SimpleQA 下降见图 6） |

**Table 9（后训练轨迹，摘关键列）：**

| Bench | SFT | DPO s1 | DPO s2 only | **phi-4 (s1+s2)** |
|---|---:|---:|---:|---:|
| MMLU | 82.8 | 84.8 | 84.2 | **84.8** |
| GPQA | 47.3 | 53.6 | 52.4 | **56.1** |
| MATH | 77.1 | 80.5 | 77.6 | **80.4** |
| HumanEval | 79.5 | 81.6 | 81.5 | **82.6** |
| ArenaHard | 56.7 | 66.5 | 69.8 | **75.4** |
| IFEval | 66.2 | 63.0 | 63.0 | **63.0** |

读法（正文）：PTS-DPO 对 **GPQA/MATH** 更有用；judge-DPO 对 **ArenaHard** 更有用；两者互补。IFEval 在后训练中**未升反降**——与弱点「严指令跟随偏弱」一致。

### 4.5 主榜与安全（Table 1 / §7）

**Table 1（simple-evals 等，temperature=0.5；摘录）：**

| Bench | phi-4 14B | phi-3 14B | GPT-4o-mini | GPT-4o |
|---|---:|---:|---:|---:|
| MMLU | **84.8** | 77.9 | 81.8 | 88.1 |
| GPQA | **56.1** | 31.2 | 40.9 | 50.6 |
| MATH | **80.4** | 44.6 | 73.0 | 74.6 |
| HumanEval | 82.6 | 67.8 | 86.2 | 90.6 |
| MGSM | 80.6 | 53.5 | 86.5 | 90.4 |
| SimpleQA | 3.0 | 7.6 | 9.9 | 39.4 |
| ArenaHard | 75.4 | 45.8 | 76.2 | 75.6 |
| IFEval | 63.0 | 57.9 | 80.0 | 84.8 |

→ STEM 叙事锚点：GPQA / MATH **高于 GPT-4o**（表内）；知识/指令类（SimpleQA、IFEval）仍明显落后大模型。

**安全（§7）：** 按 Microsoft RAI；后训练对齐 + AIRT 两周红队 + 多危害类自动评测（Table 10）。AIRT 称行为近似 phi-3 族；在 phi-3-medium 上生成的 **GCG suffix 未迁移到 phi-4**。完整缺陷率数字见原 Table 10，此处不展开攻击细节。

**弱点（§8，照录类型）：** 事实幻觉（「Who is X?」假传记）；严格式指令弱；偶发小数比较错误（9.9 vs 9.11）；CoT 数据导致简单题也冗长；主优化单轮而非多轮聊天。

## 七、待核实 / 报告内边界

1. **MobileLLM** 预训练语料具体配比 / tokenizer 词表实现细节：正文强调架构与 1T token 预算，**未**给 FineWeb 式数据卡 → 勿脑补。

3. **跨模型分数**：三篇评测协议、温度、是否 thinking **均不同**——对照表禁止合成「统一排行榜」。
4. **「On-device」语义**：MobileLLM ≈ 真手机约束；Phi-4 ≈ SLM 推理成本档；Gemma E2B/E4B ≈ 开源端侧产品列——引用时标明哪一档。

## 八、可跟读摘要（中文）

端侧小模型至少有三条可分开记的轴。**MobileLLM** 把矛盾对准手机 **DRAM/SRAM**：同参下宁愿 **更深更瘦**，再加 **词嵌共享、GQA**，并用 **相邻块权重共享** 在几乎不增存储、只加一点点延迟的前提下把有效深度再挖一寸；chat 与 API calling 说明「够用的端侧助手」不必 7B。**Phi-4** 几乎不动 14B 骨架，却把 **合成数据提到预训练 40%**，再用 **PTS 单 token DPO** 和 judge DPO 把 STEM 榜打到能压过教师模型的位置——它示范的是 **数据与后训练**，不是手机内存公式。**Gemma 4 的 E2B/E4B**（见 [[Gemma4技术报告深读]]）则给出当代开源多模态的 **PLE + mobile QAT 内存列**。三者不要揉成一张分数表；要揉的是「端侧约束 × 架构复用 × 数据课程」这张设计清单。

# 推理引擎生态：选型地图

> **主要来源**：[Efficient Memory Management for Large Language Model Serving with PagedAttention](https://arxiv.org/abs/2309.06180)（vLLM，基线）；[SGLang: Efficient Execution of Structured Language Model Programs](https://arxiv.org/abs/2312.07104)（v2）；[sgl-project/sglang README](https://github.com/sgl-project/sglang)；[NVIDIA/TensorRT-LLM README](https://github.com/NVIDIA/TensorRT-LLM)；[TensorRT LLM 文档](https://nvidia.github.io/TensorRT-LLM/)（页面标 Last updated 2026-09-26）；[DeepSeek-V3 Technical Report](https://arxiv.org/abs/2412.19437)（截至 2026-09-26）。DeepSeek-V3 只取 §3.4 的 Prefill / Decode 分阶段部署作交叉。
> **研究线**：AI Infra（推理 serving 的调度、前缀复用、结构化输出、投机解码与硬件栈）
> **范围与相邻笔记**：
> - ≠ [[AI基础设施总览]]：本篇不重写 PagedAttention、FlashAttention、Megatron 张量并行，只在其上补引擎层的分叉。
> - ≠ [[投机解码原理与发展脉络]]：投机解码的原理与脉络在那篇，本篇只把它当作一条选型轴。
> - 仓库 README 的数字标「自述」，不与论文表混写。
>
> **意义**：PagedAttention 解决「KV 放得下、碎得少」之后，生产引擎在调度、前缀复用、结构化输出、投机解码与硬件栈上分叉。把「引擎」拆成可比较的轴，才能按工作负载选型，而不是按谁的博客倍率更大。

## 一、问题背景

- [[AI基础设施总览]] 已把 serving 的显存瓶颈落在 PagedAttention 上：KV 分页、近零碎片、块级共享；vLLM 论文测得既有系统只有约 20%–38% 的 KV 内存被实际使用，相对 FasterTransformer、Orca 等系统吞吐提升 2–4×（摘要）。
- 同一套 KV 思想之上，工作负载差异很大：多轮对话、agent 反复调用工具、few-shot 共享长前缀、JSON 约束输出、低延迟单流、大规模专家并行。引擎各自押注其中几类，所以要按轴比较。

## 三、选型地图

### 3.1 对照表（主张均可回溯到论文摘要或仓库 README，不是第三方榜单）

| 轴 | vLLM（论文基线） | SGLang（论文 + README） | TensorRT-LLM（README 自述） |
| --- | --- | --- | --- |
| 问题重心 | 高吞吐 serving 下的 KV 内存浪费与块级共享 | 多调用的 LM 程序：前缀复用 + 结构化解码 + 前端语言 | NVIDIA GPU 上的内核与运行时优化库（attention、GEMM、MoE 等） |
| KV / 前缀 | 分页块 + block table；块级共享（beam、并行采样） | RadixAttention：在 radix tree 上自动跨请求、跨调用复用 KV（论文 §3） | 文档有 KV 块复用（BlockReuseConfig）、KV 卸载等配置，实现未必等价于 radix tree |
| 调度 | 与 iteration-level scheduling 共设计（论文对照 Orca） | 论文的运行时围绕前缀树与约束解码设计；README 调度特性见第七节 | Prefill–Decode disaggregation、Wide EP、投机解码（README） |
| 结构化输出 | 非论文主贡献 | compressed FSM 加速正则、JSON 等约束解码（摘要） | 文档提供 guided decoding |
| 投机解码 | 论文未涉及 | README 生态表列 SpecForge，用于训练草稿并部署到 SGLang | README 列投机解码；文档有 Draft/Target、EAGLE 3、NGram、MTP 等配置 |
| 硬件 / 锁定 | CUDA 中心的开源栈（论文评测） | README 自述覆盖 NVIDIA、AMD、Google TPU、Intel、Apple Silicon、华为昇腾、摩尔线程等 | NVIDIA GPU；README 写明「Architected on PyTorch」 |
| 代表公开倍率（不可外推） | 相对 FasterTransformer / Orca 约 2–4× 吞吐（摘要） | 相对当时的 SOTA 引擎最高约 6.4× 吞吐（摘要；任务含 agent 控制、JSON 解码、RAG 流水线、多轮对话等） | README 与厂商博客的 tok/s 未独立核验，本篇不收 |

### 3.2 选型启发式（思想层，非 SLA）

1. **共享前缀极强**（few-shot、多轮、同一系统提示、agent 反复工具调用）：先看 RadixAttention / 前缀缓存的命中率，而不是只比单请求 decode tok/s。SGLang 论文把「跨多次 generation call 自动复用 KV」写成相对「请求结束后丢弃 KV」的引擎缺口（§1、§3）。
2. **JSON / 正则约束解码是主路径**：看约束解码是否与运行时共设计（SGLang compressed FSM）；在外面单独套一层 mask 可能吃掉连续批处理的收益。
3. **在固定 NVIDIA 栈上压延迟、做 EP 或 PD 分离**：TensorRT LLM 把自己定位为「自定义内核 + 算法运行时」；代价是 NVIDIA 绑定与版本演进成本。README 的弃用策略：自 1.0 版起，弃用通知写进 release notes，弃用后有 3 个月迁移期。
4. **要可移植、兼做 RL rollout 后端**：SGLang README 列出多硬件平台，并列 slime、verl、AReaL 等后训练框架用它生成 rollout（README 自述，本篇未实测）。
5. **基线仍是 KV 是否分页**：如果部署仍按最大长度连续预留 KV，先回到 vLLM 论文的碎片分析；换引擎品牌救不了 20%–38% 的 KV 利用率。
6. **投机解码**：是否值得开、开哪种，取决于 batch 大小、领域接受率和是否愿意维护草稿，原理与各方法见 [[投机解码原理与发展脉络]]。

### 3.3 与连续批处理、PD 分离的接口

- **连续批处理**：vLLM 论文与 Orca 的 iteration-level scheduling 对照，并在 PagedAttention 上共设计。吞吐引擎比的是每步能拼进 batch 的活跃序列，不是静态 batch=64。
- **Prefill–Decode 分离**：DeepSeek-V3 §3.4 给出报告级最小部署单元；TensorRT LLM README 列 PD 分离，SGLang README 的「部署与编排」一栏列有 llm-d、NVIDIA Dynamo 等编排框架。prefill 偏算力、decode 偏访存，分池后才能独立扩缩并叠加专家并行。它是调度与拓扑层的增量，不替代 PagedAttention。

## 五、常见误区

1. **「换引擎 = 重做一遍 PagedAttention」**：分页思想已被多引擎吸收；差异更多在前缀树、约束解码、PD / EP、投机解码与硬件内核。
2. **「SGLang 论文的 6.4× 可当成任意聊天 API 的保证」**：该数字来自论文设定下、在 agent、JSON、多轮等 LM 程序负载上的峰值。Radix 的收益依赖前缀重叠，没有共享前缀的单轮短生成不应预期同样倍率。
3. **「TensorRT-LLM README 的 tok/s 与 vLLM 论文的 2–4× 可直接横比」**：硬件世代、精度、是否投机、是否 PD 分离、模型与 trace 全都不同。
4. **「PD 分离替代了连续批处理」**：二者正交。连续批处理管一步里怎么拼请求，PD 分离管 prefill 与 decode 是否同池，是叠加关系。
5. **「有了投机解码就不需要量化、MLA、分页」**：投机降的是串行步数，量化与 MLA 降的是每步搬移量与 KV 体积，分页降的是碎片，几项相乘，不互相替代。

## 六、意义

- 把 serving 优化从「一个引擎的倍率」拆成前缀、约束解码、调度拓扑、投机、硬件几条正交的轴，选型可以落到工作负载特征上。
- 说明了 2023 年以后的引擎竞争点：KV 布局已趋同，差异在 KV 能否跨调用复用、运行时是否理解程序结构、是否与特定硬件深度绑定。

## 七、局限与待核实

- **README 是活页**：SGLang README 首页现只列硬件表与生态表，不再列 continuous batching、chunked prefill、zero-overhead scheduler 等调度特性；本篇按现 README 写，这些特性需另查 SGLang 文档。GitHub README 不标更新日期，不计入截至日期。
- vLLM 生产版的前缀缓存与 SGLang RadixAttention 的实现差异：本篇以 SGLang 论文的 radix tree 为准，不断言二者语义等价。
- TensorRT-LLM PyTorch 后端与历史 TensorRT engine 构建路径的差别：以 README「Architected on PyTorch」为入口，版本演进看 release notes。
- AMD、TPU 等平台上的投机解码与 PD 分离只有 README 自述，本篇未实测。

# AI 研究会工作规范

## 成员与流水线

| 角色 | 职责 |
| --- | --- |
| AI研究会·主管 | 调度与验收；每日收集后在群内向用户汇总汇报 |
| AI研究会·发展研究员 | 史与势、主题方向（不钻技术细节） |
| AI研究会·攻坚研究员 | 按主题深度研究，产出正式文稿 |
| AI研究会·归档员 | 目录/MOC/文件名整理、定稿入库、git 提交 |

流水线：主管调度 → 发展给方向 → 攻坚成文 → 归档员意见 → 主管汇总派改 → 归档员定稿推送 → 主管群内汇报。未轮到不抢跑。

## 仓库只留什么

- **只留研究成果**（原子笔记、时间线、MOC、导读）。

只入库面向人类阅读的研究成果与导航；调研草稿、验收清单、调度记录等过程物放在未跟踪工作区（如 `.work/`），不得进入版本库。
- **不留**：工作记录/议程、PDF 等参考附件、`assets/`、`_extract/`。
- **不做的题目**：生物与生命科学相关题目（含蛋白质设计）不再选题、检索或撰写；仓库中已有的「生物学基础模型」保留现状。
- 引用一律 **HTTPS 外链**（标题、来源、日期、URL）。
- 只见于 PDF 的事实（附录、HTML 版转换不全的表）可以采用，但笔记里的引用仍挂 abs 或 HTML 落地页、不引 PDF 链接；撰稿时须在随稿说明里逐字贴出原句或表格原格，并注明节号、表号与版本号，供审稿复核；只能从图中读出的数字不写进笔记。
- 外链遇到跳转，先核一次状态码与跳转目标：301 永久跳转改挂跳转后的地址（跳转后的页面须能正常打开）；302 等临时跳转保留原地址。
- 工作草稿仅本地 `.work/`（gitignore）。

## 目录（按主题 · 适度子树）

根目录按**知识主题**划分（中文），不按波次/编号。约定主题根（可随内容微调，避免无限增殖）：

| 根目录 | 大致覆盖 |
| --- | --- |
| `架构/` | 模型结构、注意力与长上下文、MoE、推测解码等 |
| `训练/` | 预训练、数据与分词、持续学习、训练技巧等 |
| `数学原理/` | 形式化、优化与理论工具、可验证推理相关数学 |
| `Harness/` | 智能体、工具调用、记忆、评测 harness 等 |
| `对齐与强化学习/` | 对齐、偏好优化、过程奖励、RL 后训练等 |
| `推理与基础设施/` | 推理引擎、服务（`InfraServing/`）、KV/量化、硬件协同、训练基础设施（`InfraTraining/`：训练侧并行、通信、低精度训练等，与 `InfraServing/` 对称）等 |
| `多模态与具身/` | 视觉-语言、世界模型、机器人/VLA 等 |
| `检索与知识/` | RAG、知识库、检索增强等 |
| `安全与评测/` | 安全、红队、治理、基准与评测 |
| `模型与技术报告/` | System Card、厂商技术报告、模型谱系说明 |
| `前沿/` | 前沿模型与发布的速览；篇幅可短，但五项须齐，背景和脉络可各一两句 |
| `Meta/` | 工作规范、校验脚本等维护文件（非阅读主路径） |
| `Moc/` | **全部** `MOC_*` 枢纽文件（宏观与中小主题均在此） |

子树：每个主题下做**少量**合理分层即可，**不要大规模平铺**，也**不要拆得过碎**（建议主题内 ≤2 层子目录）。

**目录命名**：全部使用**大驼峰（PascalCase）**（如 `Harness/`、`InfraServing/`）；**禁止** `snake_case`、`kebab-case` 或全小写英文目录名。中文目录名保持简洁中文即可（本身无大小写问题）。

**禁止**在各主题目录放置 `README.md`。索引用 MOC，不用目录 README。

禁止再使用旧编号目录如 `20-deep-dives/`、`30-*`、`40-*`；现行笔记统一按主题目录维护。

## 原子笔记与文件名

- 单篇笔记保持**较好原子性**（一个清晰知识单元），由 MOC 串联，而非靠目录 README。
- 文件名：**中文**，直接反映正文主题；**禁止** `P`/`B`/`W`/`M` 等工号、波次号、日期派工前缀。
- 例：`混合专家架构.md`，不要 `P0-4-moe-sparse.md`。
- 模型卡、System Card 与技术报告深读的元信息字段见 [[模型卡归档字段]]。

## MOC 规范（网状枢纽）

- **全部** MOC 文件放在 **`Moc/`** 目录；文件名以 **`MOC_` 为前缀** + **中文**（如 `Moc/MOC_架构类型.md`）。
- MOC 是查阅枢纽，**网状互链**，**没有上下级从属**；「宏观」只表示阅读入口上的大主题节点，不是目录层级父节点。
- Obsidian 双链一律用裸链 `[[文件名]]`（如 `[[文档自身名]]`），禁止用 `|` 写显示别名，以免与 Markdown 表格竖线冲突。
- **宏观 MOC**：按阅读目的组织（发展时间线、数学原理、架构类型、训练方法、研究方向等），由根 `README.md` 与 `Moc/MOC_阅读入口.md` 串联进入。
- **中小主题 MOC**：同样只在 `Moc/`，维护相对闭合聚类，与其它 MOC、原子笔记互链。
- 主题目录内**不放** README，也**不放** MOC 文件。

## 根 README（面向人类）

- 仓库根 `README.md` 只服务**人类读者**：本库是什么、怎么开始读、主题目录与 `Moc/` 入口。
- **禁止**在 README 中写研究员职责、流水线、Bot 分工、验收流程等协作内容（那些只在 `Meta/工作规范.md`）。

## 内容深度

入库笔记按「深入研究」的深度写：每篇是内容齐全的大纲式阅读材料，读者读完即可掌握该主题的来龙去脉、核心思想与定位，不必回读原文才能理解。行文简洁易懂，术语首次出现时给出简短解释。

### 应写清的五项

1. **问题背景**：要解决什么问题、为何在此时出现、前提与约束。
2. **脉络**：单篇文章写清它在研究线中的位置与前后关键工作；方向综述写清关键节点与演进主线。历史只取关键节点。
3. **核心思想与关键机制**：核心想法是什么、靠什么机制起作用，讲到读者能说清「为什么有效」为止；必要时给关键公式或一张小表。
4. **意义与局限**：带来了什么改变、适用边界与已知不足。意义默认在开篇导语中写一两句（开篇块仍保持单一引用块），需要展开时另设短节「意义」；局限及未核实或不确定的内容按正文禁写清单第 8 条写入「局限与待核实」。末尾节序为「意义 → 局限与待核实 → 分工/相关笔记」，延伸阅读的位置不变。
5. **与其它主题的关联**：与相邻笔记、上下游方向的关系，用裸链 `[[笔记名]]` 指向。关联内容可写进「与相邻笔记的分工」表或「相关笔记」，每条双链须附一句说明两篇是什么关系，不接受只有链接的列表；范围划分按正文禁写清单第 2、10 条写。

来源与延伸材料附 HTTPS 外链，格式按正文禁写清单第 12、13 条。

### 不写什么

- 不逐段复述原文，不按原文章节顺序转写。
- 不展开数学推导：写结论、直觉与关键公式，推导过程以「原文 §x」指向。
- 不展开实验细节：只留支撑结论的关键数字与对比，不搬全量结果表、超参数表与消融明细。
- 不与相邻笔记大段重复：共用的背景写在一处，优先放该主题的综述或时间线篇，没有则放该脉络最早的一篇，其余篇用裸链指向。

### 判定口径

| 判定 | 口径 |
| --- | --- |
| 达标 | 五项齐全；篇幅与主题复杂度相称；无大段复述、推导或实验明细。 |
| 过细 | 五项基本齐全，但逐段复述、推导展开或实验表格占据主要篇幅，需精简。 |
| 过薄 | 缺少问题背景、脉络或核心机制中的任一项，或只罗列事实与数字而缺少解释，或关联只列链接而无关系说明，需补齐。 |

## 终稿文风

正式报告/说明文/百科式。禁止正文出现波次、验收、派工、待办、流水线状态等流程腔。

### 正文禁写清单

正文（含开篇引用块、表格、节标题，以及 frontmatter 的 `title`、`related`）不写下列工作记录。草稿期需要的放 `.work/`。

1. **写作者约束腔**：「禁止编造 / 不编造 / 一律锚定官方 PDF」「议程硬禁」「跟读纪律」「跟读时以原文为准，本卡不另造表」这类写给写作者的话不写。需要交代主源时按第 12 条写「主要来源」；原句自带的时间锚点照原样保留，不另加日期。
2. **范围写法**：与相邻笔记的分工写在开篇「**范围与相邻笔记**」下，用「`≠ [[笔记名]]：本篇不写 …`」列表，不写「硬划界」「禁止重写」。安全类边界写成范围说明（如「本篇不收攻击载荷全集」）。
3. **议程腔**：不写议程、Agenda、Wave / 波次、派工，不写「与议程对齐」「给后续波次」这类节。
4. **验收与待办**：不写验收节、自检清单、完成判据、交付说明；不用 `- [ ]` / `- [x]` 待办框。复习问题、未决问题用普通列表。
5. **进度与状态**：不写进度自述（本轮、本次、本窗、已归档、落盘、再下载、收口等）、正文里的 `status: draft` 或草稿状态行、「修订时优先同步 X changelog」「若后续单独立项…」「回头链本篇」一类维护提示、「起草：…」落款。状态只放 frontmatter。
6. **过程痕迹**：不写本地路径、文件体积、下载或抽取命令、txt 抽取出处；引用原文章节写「原文 §x」。
7. **编号与路径**：不写旧工号（B / P / W / TR- 编号），不写仓内 `目录/文件.md` 明文路径，一律用裸链 `[[笔记名]]`。
8. **局限节**：未核实、不确定的内容集中写在「局限与待核实」节；「待核实读图」这类数据可靠性标注保留。
9. **frontmatter**：`topic` 与文件名（不含 `.md`）一致；不写 `priority` 等调度字段。
10. **入库口吻**：不写「已入库 / 相对已入库 / 可入库」及入库政策、入库动作。相邻笔记直接给裸链 `[[笔记名]]`；接口节名写「与相邻笔记的分工」，接口表头写「相邻笔记 | 本篇只取 | 本篇不写」。
11. **研究线标签**：开篇的研究方向标签统一写「**研究线**：…」。
12. **主要来源格式**：开篇引用块写成 `> **主要来源**：[文档名](链接)`，多条用「；」隔开。文档名写报告或论文的实名（从正文材料表或官方页核实，不猜），不写「官方 PDF 与」这类前缀；GitHub 仓库写作「owner/repo README」。时间锚点统一写成「（截至 YYYY-MM-DD）」（如「（截至 2026-09-22）」；来源只给到月份的，写到月份；只给到年份的，写到年份；页面不显示的元数据日期不计入；不自行补日；最晚的月级事实与最晚的日级事实在同一个月时，截至写到月），放在列表之后，不写「CST」「核对」字样；附注句接在时间锚点之后。时间锚点与 frontmatter 的 `retrieval_cutoff` 取所引事实中最晚的日期，分工行事实按库内所引版本计；引的是期刊正式版的，按刊期日（含会议正式版）计入，脉络节点仍用在线发表日或预印本日；产品页、文档页这类没有单条事实日期的活页，按页面标的「Last updated」日期计入，页面没有更新日期的不计入，仅用于核对名称、未引其中事实的页面不计入；核对日一律不算事实日期。`retrieval_cutoff` 不是必填字段：已有该字段的篇目保留并与「截至」同步，原本没有的改写时不新增。
13. **延伸阅读**：阅读顺序、复习要点这类对读者有用的节，节名统一为「延伸阅读」；写给写作者的检查项不写。

## Git

- 中文 commit，说明具体改动。
- 远程：`ProphetEngine/AIResearch`（`main`），以 HTTPS 推送。凭据取自环境变量 `AIRESEARCH_GITHUB_TOKEN`，推送时以 `git -c http.extraHeader=…` 临时传入；不得把 token 写入 remote、git 配置或凭据文件，文中不写 token 值。
- 推送前先 `pull --rebase`，只做普通推送。
- 去附件后须 purge/截断历史并瘦身（force-with-lease 仅在用户授权下）。

## 每日前沿

主管 routine `daily-frontier-brief`：每天 9:00 Asia/Shanghai；有料走流水线并在群内汇报；无料安静。

## 归档卫生

归档员 `vault-hygiene-weekly`：无工作记录/无附件被跟踪；文件名与 MOC 前缀合规；导航可走。主管验收。

校验脚本见 `Meta/verify.py`：在仓库根目录运行 `python3 Meta/verify.py . <文件…>` 查看所列文件的逐项结果，只给 `.` 时报全库篇数与 FAIL 总数，加环境变量 `VERIFY_FLAGS=-v` 时列出全库每条 FAIL；正文禁写清单对应的禁写词表与白名单以该文件为准。

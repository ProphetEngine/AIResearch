# 多智能体编排评测：OrchBench（≠ MAD 机制）

> **主要来源**：[OrchBench（Ren et al., Fudan / 中关村学院 / Queen Mary, 2026）](https://arxiv.org/abs/2607.25656)；补充 [M3MAD-Bench（Li et al., ACMMM 2026）](https://arxiv.org/abs/2601.02854)（截至 2026-09-22）
> **研究线**：评测字段 / 编排接口思想——在固定任务依赖图上，只评「子任务怎么分给 agent、信息怎么在 agent 间传」这份计划本身。
> **范围与相邻笔记**：
> - ≠ [[多智能体辩论]]：本篇不写同题辩论的协议与退化诊断。
> - ≠ [[MixtureOfAgents与TUMIX]]：本篇不写测试时的异构输出合成与工具策略混合。
> - ≠ [[AgentBazaar经济对齐]]：本篇不写多代理市场与经济角色。
> - ≠ [[智能体工具与长程任务]]：本篇不写旗舰模型的工具环与长程产品叙事。
>
> **意义**：OrchBench 用确定性仿真把「编排计划好不好」从 worker、工具和环境噪声中剥离出来，以约 1.3% 的 token 成本得到与真实执行质量 r=0.816 的相关；它的主要发现是**保住跨 agent 的关键信息比增加 agent 数更重要**。

**一句话**：给定任务 DAG、每个 agent 的上下文上限和最大 agent 数，让被测模型只交一份编排计划；仿真器不调用任何 worker，直接算出结果质量、并行效率和 token 效率，并指出哪些依赖边漏传了信息。

## 一、问题背景

多智能体系统（MAS）的端到端分数把很多因素揉在一起：编排是否合理、worker 是否可靠、工具与环境是否稳定。分数低时无法回答「是编排烂还是执行炸」，而且每次端到端运行都很贵（OrchBench Introduction）。

编排本身有两个容易被忽略的失败源：

1. **信息漏传**：子任务被分到不同 agent 后，下游 agent 需要上游结果；计划若没声明这条转移，下游只能在缺信息的情况下工作。
2. **压缩损失**：上下文有上限，跨 agent 传递的信息常需压缩；有的子任务输出经不起压缩。

这两类失败都发生在「计划」层面，理论上不用真跑 worker 就能检查。

## 二、脉络：编排评测在相关基准中的位置

OrchBench 的相关工作把已有基准分成四组，自己补其中的空位：

| 类别 | 代表 | 评什么 | 与 OrchBench 的差别 |
|---|---|---|---|
| 端到端 agent / MAS 基准 | AgentBench、GAIA、WebArena、SWE-bench、OSWorld、MultiAgentBench | 整个系统完成任务的成绩 | 编排与执行噪声揉在一起 |
| 工作流结构基准 | PlanBench、FlowBench、WorFBench | 生成的计划或工作流结构是否正确 | 不仿真「分给 agent 之后」的执行后果 |
| MAS 切片评测 | MASBENCH、PerspectiveGap、OrchRM | MAS 的某一侧面 | OrchBench 评完整计划且不跑 worker |
| 交互中信息合并 | HiddenBench、Silo-Bench | agent 交流过程中的信息整合 | OrchBench 评事先的分配、调度、转移与压缩 |

另一条平行的评测线是多智能体辩论（MAD）的标准化：M3MAD-Bench 在五个领域、13 个数据集（7 个文本 + 6 个多模态）、9 个底座模型上同时量准确率、token 与推理时间，结论之一是 MAD 并非处处有效、成本高。它评的是同题辩论策略，与 OrchBench 的 DAG 编排计划正交，归属 [[多智能体辩论]] 一侧。

## 三、核心思想与关键机制

### 3.1 固定依赖，只评计划

任务分解与依赖图 G 是**给定的**，不属于编排决策。每个子任务带 token 预算、时间预算，以及压缩敏感类（robust / balanced / fragile）。评测输入还包括每个 agent 的上下文上限 L 与最大 agent 数 A_max。

被测模型产出计划 π = (α, R)：

- **α：子任务 → agent 的分配**。同一 agent 上的依赖结果可以本地完整复用。
- **R：跨 agent 依赖边的转移声明**，每条带保留比 e ∈ (0, 1]。保留比越高信息越全、通信与上下文越贵；fragile 输出需要更高保留。漏报一条依赖边即计为一次 **missing transfer**。

### 3.2 三阶段管线

1. **DAG 构造**：种子题取自 Finance Agent、DS-1000、Qasper、BIRD-SQL，用「自然并行度」控制并行结构，经双法官加改写迭代生成；主实验 240 个 DAG，另造 200、500、1000 节点的大图测可扩展性。
2. **编排规划**：被测模型写一段工作流脚本，由确定性解释器展开为 π。
3. **确定性仿真**：模拟真实框架的六段生命周期（依赖解析、agent 调度、上下文获取、上下文管理、子任务执行、状态更新），不调用 worker LLM 或工具。同一 agent 上串行、不同 agent 间可并行；缺失转移时父结果的有效质量乘惩罚 λ（主设定 λ = 0.5），压缩按敏感类折损质量。

### 3.3 评分

- **质量 Q**：终端子任务质量的宏平均。
- **时间效率 E_time**：加权关键路径与实际 makespan 之比（上限 1）。
- **token 效率 E_token**：单 agent 串行基线 token 与实际 token 之比（上限 1）。
- **Score = (Q + E_time + E_token) / 3**，另报 makespan、token、agent 数与 missing transfers 作诊断。

## 四、仿真保真度

- **质量可预测**：在 MultiAgentBench 上与 Claude Code 实跑对照，仿真分数与真实任务质量 Pearson **r = 0.816**（Spearman 0.771）；去掉任一验证模型后仍为正相关（OrchBench Table 2–3）。与 SWE-mini、OpenHands、Crush 的实跑也都正相关，预测不绑定单一框架（Fig. 3）。
- **时间与 token 不可预测**：仿真对真实耗时、token 用量的相关为负且不显著，论文明确把 OrchBench 定位为筛选计划的工具，最终仍需在目标框架上少量实跑。
- **成本**：相对 Claude Code 只用约 **1.3%** 的 token 和 **10.3%** 的墙钟时间（Abstract）。
- **可用于筛选与改进**：按仿真分歧挑 5 题实跑，模型排序 Spearman **0.754**，随机挑题只有 0.176（Table 7）；按仿真诊断补一条跨角色 handoff，真实分从 **3.754 升到 4.150**（满分 5，Table 9）。

## 五、主要发现：保信息优于堆 agent

### 5.1 规模越大，漏传越多

在 10、20、50、100 节点的 DAG 上，各模型平均 missing transfers 的区间从 n = 10 时的 [0.00, 0.43] 扩大到 n = 100 时的 [0.07, 22.70]，**没有模型在所有规模上都得分最高**（Table 4）。n = 100 时分数主要被信息路由是否完整拉开。

极端规模下差距更明显：DAG 从 500 增到 1000 节点，Claude 的转移覆盖率从 **0.981 跌到 0.441**，Gemini 仍保持完整覆盖（Fig. 5，曲线读数待核实）。

### 5.2 覆盖率决定质量，agent 数不决定

转移覆盖率与质量 Q 的相关在各规模为 **0.614–0.952**；agent 数与质量的相关在 n = 100 时只有 **−0.021**（Table 5）。把 A_max 从 16 提到 64，agent 数翻倍以上，Score 几乎不变（Fig. 4）。论文结论：保住任务关键信息比单纯增加 agent 更重要，并行收益会随协调失败累积而衰减。

### 5.3 多 agent 何时值得

同一批 50 个 DAG 上比较单 agent 与多 agent，扫上下文上限 L（Table 6）：

| L | 单 agent 质量 | 多 agent 质量 | 差值 |
|---|---|---|---|
| 16k | 0.423 | 0.725 | +0.302 |
| 32k | 0.649 | 0.821 | +0.172 |
| 64k | 0.792 | 0.852 | +0.060 |
| 128k | 0.852 | 0.859 | +0.007 |

工作状态塞不进单个窗口时，多 agent 靠拆分避免反复压缩；一旦装得下，协调本身就接近纯开销。

### 5.4 对编排设计的含义

- **先查信息路由，再加 agent**：大 DAG 上「多开几个 subagent」可能制造更多漏传；覆盖率是比 agent 数更可靠的设计指标。
- **按上下文压力决定是否多 agent**：多 agent 的收益主要来自缓解上下文压力，窗口足够时收益趋零。
- **效率数字要分清口径**：E_token 是仿真内的相对效率，不等于线上实际 token 账单。

## 七、局限与待核实

1. **仿真质量模型的覆盖边界**：质量按父结果质量与压缩敏感度计算，真实 worker 的错误模式未必都被覆盖（OrchBench 自承时间与 token 预测弱）。
2. **固定 DAG 假设**：分解本身不评，「先分解再编排」的联合优化如何接入尚未解决。
3. **λ 的选择影响区分度**：λ 越大分数越高但模型间区分度下降，主设定 0.5 是折中（Table 20）。
4. **无官方评测仓**：论文未给出作者自发布的代码地址，复现依赖正文与附录描述。
5. **图上读数**：极端规模（Fig. 5）与 A_max 扫描（Fig. 4）的具体曲线点为正文叙述，未逐点核对。

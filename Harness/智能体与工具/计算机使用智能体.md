# Computer-use agents：OSWorld 2.0 + Operator 系统卡 + StateAct

> **主要来源**：[OSWorld 2.0: Benchmarking Computer Use Agents on Long-Horizon Real-World Tasks](https://arxiv.org/abs/2606.29537)（XLANG Lab 等，简称 OSWorld 2.0，v2 2026-07-13）；[StateAct: Program State, before Pixels, for Long-Horizon Computer-Use Agents](https://arxiv.org/abs/2607.22798)（Yang、Jian、Luo 等，Salesforce AI Research，简称 StateAct，v1 2026-07-24）；[Operator System Card](https://openai.com/index/operator-system-card/)（OpenAI，2025-01-23，API 一节 2025-03-11 增补）；[Computer-Using Agent](https://openai.com/index/computer-using-agent/)（OpenAI 博文，2025-01-23）；[Addendum to OpenAI o3 and o4-mini system card: OpenAI o3 Operator](https://openai.com/index/o3-o4-mini-system-card-addendum-operator-o3/)（OpenAI，2025-05-23）（截至 2026-09-22）。
> **研究线**：架构思想（主：观测与动作接在像素还是程序状态上）；评测字段（辅：长程完成率、部分分、成本、安全叠层）
> **范围与相邻笔记**：
> - ≠ [[UIVenus2GUI智能体]]：本篇不写 GUI 基础模型的训练管线与可验证 RL 信号。
> - ≠ [[代码智能体Harness史线]]：本篇不写 SWE-agent 到 OpenHands 的软件工程 harness 史；StateAct 的对象是通用桌面交付物的状态，不是代码补丁。
> - ≠ [[模型卡与SystemCard规范]]：本篇不写系统卡的规范字段，只用 Operator 系统卡这一个实例。
>
> **意义**：计算机使用智能体有三条互补的轴。Operator 用截图加键鼠上线产品，靠确认、Watch Mode 与注入监控叠层控制风险；OSWorld 2.0 说明短程桌面榜上约 80% 的成功率不能外推到小时级专业工作流，最强配置只完成 20.6%；StateAct 认为长程失败多来自状态漂移而非看不清，把主智能体接到文件、DOM 与 shell 上，同一骨干模型的完成率升到 26.9%，单任务成本约降为九分之一。

## 一、问题背景

能操作浏览器与操作系统之后，风险从「说错话」扩展到「做错不可逆的动作」和「执行屏幕上第三方写的指令」，产品需要系统卡级别的多层缓解，不能只看基准分。评测上，前沿模型在 OSWorld 1.0 上已有 79%–83% 的成功率，Claude Opus 4.8 在 OSWorld-Verified 上达 83.5%（OSWorld 2.0 §1、§3.2），容易让人以为桌面操作已经解决，但真实专业流程是跨应用、跨来源、中途会变化的小时级工作。表征上，截图是程序状态的有损渲染，不同状态可以渲染成相同像素；单步误读影响不大，几百个相互依赖的步骤下会累积成错误的交付物（StateAct §3）。

## 三、Operator 与 CUA：截图键鼠与产品安全栈

### 3.1 产品与能力锚点

CUA 在 GPT-4o 视觉能力上用强化学习训练推理，以截图感知、虚拟键鼠动作，不依赖操作系统或网页的专用 API；训练先用监督学习打下感知与点击基础，再用强化学习学推理、纠错与应对意外（系统卡「Model data and training」）。动作环为感知（截图进上下文）→ 推理（思维链）→ 动作（点击、滚动、输入），登录、验证码等敏感步骤交给用户。Operator 于 2025-01 以研究预览形式向美国 Pro 用户开放。

| 基准 | OpenAI CUA | 此前最佳（通用界面） | 此前最佳（网页智能体） | 人类 |
|---|---:|---:|---:|---:|
| OSWorld | 38.1% | 22.0% | – | 72.4% |
| WebArena | 58.1% | 36.2% | 57.1% | 78.2% |
| WebVoyager | 87.0% | 56.0% | 87.0% | – |

2025-03-11 增补的 API 一节专门指出，38.1% 的 OSWorld 成绩说明模型在操作系统上还不能高可靠地自动化，建议人工监督；API 面的额外风险包括可改写系统消息、非浏览器环境中注入影响更大、规模化滥用。

### 3.2 三类风险与叠层缓解

系统卡把部署风险分为有害任务、模型失误与提示注入三类，分别对应用户、模型与网站「不对齐」，缓解覆盖模型训练、系统检查、产品设计与上线后执法各层。

| 层 | 机制 | 关键数字 |
|---|---|---|
| 有害任务 | 拒绝训练、网站封禁名单、实时审核、离线检测与人工复核 | 内部集上拒绝 97% 的新型智能体危害任务；过度拒绝明显多于 GPT-4o（not_overrefuse 55% 对 90%） |
| 模型失误 | 改变世界状态的终步（下单、发信）先请用户确认 | 未缓解模型在 100 个典型任务中出错 13 次，5 次难以逆转；确认使这类风险约降 90%；607 个任务、20 类风险动作上确认召回率 92% |
| 主动拒绝 | 银行交易、高利害决策直接拒绝 | 合成评测集上召回率 94% |
| Watch Mode | 邮箱等敏感站点上，用户离开页面即暂停 | 产品机制，无评测数字 |
| 提示注入 | 模型加固，加独立的注入监控（看当前截图，可疑即暂停） | 31 个场景的易感率：无缓解 62%，仅提示 47%，最终模型 23%；监控在 77 次红队注入上召回 99%、精确率 90%，13,704 个正常屏幕中误报 46 个 |

### 3.3 前沿风险与 o3 换代

Preparedness 评估中，Operator 在适配到计算机使用场景的生物风险工具评测上成功率为 1%，自主复制评测的主任务都不超过 10%，两项均为 Low；说服与网络安全两类继承 GPT-4o 的 Medium 与 Low。系统卡把两项评测的失败都归于视觉输入与光标输出方式（hindered by its visual input and cursor output modalities）：生物工具评测中，Operator 仅凭截图难以正确识别和处理长 DNA 序列，这类随机串容易被 OCR 认错；自主复制评测中，读取 API 密钥、比特币钱包地址等复杂值时，模型几乎总是看屏幕识别，而不是复制粘贴或把输出重定向到文件，结果出现 OCR 错误。

o3 附录把产品模型换成基于 o3 的版本，API 仍用 4o；附加了确认与拒绝边界的安全数据，没有原生编码环境或终端。附录全文报告：确认率从 92% 升到 94%，金融交易评测中 100% 确认；注入易感率从 23% 降到 20%，作为主防线的注入监控不变；生物能力评测弱于 o3，仍低于 High。

## 四、OSWorld 2.0：长程真实工作流评测

### 4.1 设计

| 维度 | OSWorld 1.0 | OSWorld 2.0 |
|---|---|---|
| 任务 | 短任务 | 108 个端到端工作流 |
| 人类中位主动操作时间 | 约 2 分钟 | 约 1.6 小时（约 48 倍） |
| 智能体步数 | 约 30 步 | Opus 4.7（单调用、max thinking）平均 318.4 次工具调用；最强评测设置下每任务超过 250 步 |
| 跨应用 | 平均 1.35 个应用或服务 | 平均 2.44 个；按指令 64.8% 的任务需要两个以上，计入实际使用后为 75.9% |
| 环境 | 桌面应用 | 31 个自托管网站加桌面应用；有状态的用户画像、中途到达的消息、模拟用户 |
| 计分 | 二元 | 二元完成率为主指标，另有平均 27.25 个检查点的部分分；功能检查优先，模型评判占总分 11.53% |
| 安全 | – | 8 项诊断检查，另出安全审计报告 |

任务按 10 种挑战现象标注（可多标）。最常见的是跨源推理 46 个（42.6%）、视觉空间精度 45 个（41.7%）、隐状态推断与多项状态追踪各 43 个（39.8%）；流式交互与主动交互各只有 6 个（5.6%）（Table 2）。作者公开了环境、108 个任务、自托管网站与轨迹，所有结果用评测版本 v2026.06.24。

### 4.2 主结果（Table 3）

设置：截图观测，步数上限 500；Claude 用原生 computer use 工具，其余模型输出 pyautogui 代码；各模型取最高思考档。

| 配置 | 二元完成 (%) | 部分分 (%) | 单任务成本 |
|---|---:|---:|---:|
| Claude Opus 4.8，批量调用 | 20.6 | 54.8 | 约 $72.4 |
| Claude Opus 4.7，批量调用 | 18.2 | 48.9 | 约 $33.6 |
| GPT-5.5，批量调用 | 13.0 | 49.5 | 约 $25.5 |
| Claude Opus 4.8，单调用 | 18.5 | 49.3 | 约 $76.1 |
| Claude Sonnet 4.6，单调用 | 8.3 | 41.5 | 约 $22.3 |
| MiniMax M3 / Kimi 2.6 / Qwen 3.7-Plus | 4.6 / 4.6 / 2.8 | 22.3 / 22.1 / 21.5 | 约 $2.4 / $6.6 / $3.8 |

同一批前沿模型在 OSWorld 1.0 上为 79%–83%，在 2.0 上低一个数量级。GPT-5.5 的输出 token 最省（单任务约 37K），但 150、300、500 步预算的结果都停在 13% 附近。部分分高、严格完成低：更多推理预算主要换来部分分，很少换来最后一步的完成。

### 4.3 失败模式

作者的结论是，智能体失败很少是因为不会点击或不会写代码，而是：
1. 丢掉已给的约束，漏掉中途到达的信息，该问用户时自己猜；
2. 跳过验证，用于发现和修复自身错误的预算合计不到 7%；
3. 在依赖隐状态的现象上最弱：隐状态推断、多项状态追踪、冲突消歧与动态环境。

人类觉得简单的任务对智能体仍可能很难，所以按人类耗时外推的缩放规律只能部分迁移。

## 五、StateAct：程序状态优先于像素

### 5.1 原则（§3）

程序状态（文件、应用后端、DOM、表格）有两条观测通道：像素渲染有损且非单射，状态查询对任务相关的子状态近似精确。StateAct 把动作、验证与记忆默认接在状态上（作者称为 state-grounding），截图点击降为委托给子智能体的后备。

### 5.2 架构（§4）

- **主智能体**：用 bash、Python 与文件编辑器直接读写文件、DOM、数据库与 shell。
- **子智能体**：GUI、网页与通用三类专家，各用新的上下文接收子目标；GUI 子智能体只在 108 个任务中的 28 个出现，占主智能体步数的 1.1%（占全部轮次约 11%）。
- **上下文管理**：压缩历史，外置计划清单。
- **完成门**：不看智能体的叙述，只检查持久化的交付物；在完成时触发（至少三步非完成动作之后），最多三轮。

提供递归委托时，只有 7 个任务用到且从不嵌套，作者据此保持扁平结构，并认为增益来自观测通道而非层级深度。

### 5.3 结果与消融（OSWorld 2.0，同为 Claude Opus 4.8）

| 系统 | 二元完成 (%) | 部分分 (%) | 单任务成本 |
|---|---:|---:|---:|
| 截图式参考（OSWorld 2.0 Table 3 最强配置） | 20.6 | 54.8 | 约 $72 |
| StateAct | 26.9 | 61.6 | 约 $7.8 |
| 只有 bash（无 GUI、无子智能体、无完成门） | 15.7 | 45.9 | – |

- 去掉「在状态上动作」的下降最大，部分分从 61.6% 降到 51.3%；只有 bash 的配置部分分也低于截图基线，说明光写代码不够，需要整套脚手架（§5.3–5.4）。
- 换成 Claude Sonnet 4.6，二元完成从 8.3% 升到 11.1%；在短程的 OSWorld-Verified 上两者接近（78.4% 对 77.3%），优势集中在长程任务。
- **完成门的上限**（§6.1）：到达完成门的 76 个非满分任务中，只正确拒绝 8 个，误放行 68 个（约 90%）；完成门能抓未保存、路径错、缺文件等结构错误，抓不到数值与推理错误，后者是可挽回失败中最大的一类（38 个任务）。作者据此认为，状态接地把主要瓶颈从感知移到了推理。

## 六、三轴对照

| 轴 | 默认观测 | 默认动作 | 核心问题 | 代表数字 |
|---|---|---|---|---|
| Operator / CUA | 截图 | 键鼠 | 安全叠层能否挡住注入与不可逆误操作 | OSWorld 38.1%；注入易感率 23%→20%（o3）；确认 92%→94% |
| OSWorld 2.0 | 截图（主协议） | 原生工具或 pyautogui | 小时级、跨来源、会变化的环境下能否严格完成 | 最强 20.6 / 54.8，约 $72.4 每任务 |
| StateAct | 程序状态为主 | 代码，少量 GUI | 同一骨干上状态接地能否同时提分和降本 | 26.9 / 61.6，约 $7.8 每任务 |

三者的分数来自不同脚手架与预算，不能当作严格的同条件对比。

## 七、意义

三项工作分别回答了上线后怎样控制风险、长程评测还暴露出什么问题、主接口是否必须是像素。Operator 系统卡给出了计算机使用产品的安全叠层模板：拒绝、确认、Watch Mode、独立注入监控，各层都附召回率或易感率。OSWorld 2.0 把评测从短任务推到小时级工作流，并用部分分、成本与安全审计把「完成率低」拆成可诊断的失败模式。StateAct 指出，在长程任务上改变观测通道可以同时提高完成率、降低成本，剩下的瓶颈是推理正确性，而不是感知。

## 八、局限与待核实

- **Operator 系统卡**：作者明确说对抗鲁棒性仍是开放问题，红队为避免真实伤害，部分情况下改在模拟网站与邮箱中演示，作者承认可能没有覆盖最坏情况；38.1% 的 OSWorld 成绩不代表桌面任务已解决。o3 附录的数字见该页链出的系统卡全文，HTML 页正文只有概述。
- **OSWorld 2.0**：v1（2026-06-28）与 v2（2026-07-13）正文逐行比对一致，只有版本号与日期不同；任务只有 108 个，单任务方差大；模型评判占总分 11.53%，评判与用户模拟器都用 Claude Sonnet 4.6。
- **StateAct**：截图式参考的 20.6 / 54.8 与约 $72 取自 OSWorld 2.0 的报告值，StateAct 没有在同一次运行中重跑；许多应用没有完整的可编程接口，何时必须看屏幕仍没有系统性的判据；完成门遇到价值层面的错误基本无效。
- **安全与自主**：高确认召回与 Watch Mode 降低了风险，也限制了无人值守；长程专业流程（报销、合规）如何分级授权，系统卡没有给出通用做法。

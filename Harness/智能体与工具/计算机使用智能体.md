**可跟读三条缺口句：**

1. **部署安全**：能操作浏览器/OS 后，风险从「说错话」扩到「做错不可逆动作」与「屏幕上的第三方指令」——需要 System Card 级多层缓解，而非仅基准分。
2. **评测失真**：OSWorld-Verified 上 frontier ~80% 会暗示「桌面已解决」；真实专业流程是跨应用、跨源、可变化的小时级工作流。
3. **表征瓶颈**：截图是程序状态的**有损非单射**渲染；长程上逐步 lossy 读会**复合态漂移**，终态对错也常无法从像素可靠判定。

## 三、Operator / CUA：产品形态与系统卡安全栈

### 3.1 产品与模型族（官方叙述）

| 项 | 一手事实 |
|---|---|
| **Operator** | 2025-01 起以 research preview 提供 CUA；入口 operator.chatgpt.com（初期 Pro / 美国） |
| **CUA** | 「Computer-Using Agent」：用 **GPT-4o 视觉** + **RL 推理**；以截图感知、虚拟键鼠动作，**不依赖** OS/web 专用 API（博客 + System Card §1–2） |
| **训练（SC §2）** | **监督学习**（感知与点击基座）+ **强化学习**（推理、纠错、适应意外） |
| **动作环（博客）** | Perception（截图进上下文）→ Reasoning（CoT，结合历史屏与动作）→ Action（点/滚/打字）；敏感步（登录、CAPTCHA 等）要用户确认 |
| **o3 换代（2025-05-23 附录）** | Operator **产品模型**换 **o3 Operator**；**API 仍 4o**；额外 computer-use 安全数据（确认/拒绝边界）；**无原生 coding 环境 / Terminal** |

### 3.2 能力锚点（短程榜；**≠** OSWorld 2.0）

| **WebVoyager** | **87.0%** | 56.0% / 另列 87.0% | — |

SC §4.7（API 段，2025-03-11 更新）：强调 OSWorld **38.1%**「尚不足以在 OS 上高可靠自动化」，建议人机监督；API 面额外风险含 system message 可改、非浏览器面、规模滥用等。

### 3.3 风险三类 + 多层缓解（Operator SC 主轴）

SC 把部署风险收成三类：**有害任务（misuse）**、**模型失误（含不可逆副作用）**、**提示注入**；并宣称缓解要**叠层**（模型 + 产品 + 运营）。

| 层 | 机制（一手） | 关键评测数字 |
|---|---|---|
| **有害任务** | 拒绝训练；站点 blocklist；实时 moderation；离线检测/人工复核 | 多类拒绝率见 SC Table 3；合成高风险任务拒绝 recall **94%**（§4.4） |
| **确认（Confirmations）** | 对改变世界状态的终步（下单、发信等）先问用户 | 607 任务 / 20 类风险动作：确认 recall **92%**（4o）；o3 附录升至 **94%**，金融类 eval **100%** 确认 |
| **主动拒绝** | 银行交易、高利害决策等直接拒 | 同上 94% recall |
| **Watch Mode** | 邮件等敏感站：用户离开则暂停 | 产品级；图示见 SC Fig.1 |
| **提示注入** | 模型加硬 + **Prompt Injection Monitor**（看当前截图，可疑则暂停） | 31 场景易感性：无缓解 **62%** → 仅 prompting **47%** → 最终模型 **23%**；监控在 77 红队注入上 recall **99%** / precision **90%**（漏 1 例边界）；良性屏 46/13704 误报。o3：**易感性 20%**（更低更好）；监控层不变 |
| **失误风险降幅** | 确认等 | 文称相对基线失误风险约降 **~90%**（§4.2 叙述） |

**Frontier（Preparedness）：** 4o Operator 在适配后的 bio tooling / autonomy 评测上为 **Low**（bio tooling 总成功率约 **1%**；主任务 autonomy 均 ≤10%，SC Table 1–2）。o3 Operator 附录：继承 o3「Below High」化学/生物、网络安全、自我改进；Operator 在生物能力 eval 上**弱于** o3，仍低于 High。

**诚实边界：** System Card 明确对抗鲁棒性仍是开放题；API research preview（`computer-use-preview`）额外警告非浏览器面与 jailbreak 面扩大——笔记不把 38.1% OSWorld 写成「已解决桌面」。

## 四、OSWorld 2.0：长程真实工作流评测

### 4.1 相对 1.0 / Verified 的设计跃迁

| 维度 | OSWorld 1.0（文内对照） | OSWorld 2.0 |
|---|---|---|
| 任务数 / 形态 | 短、窄、少跨应用 | **108** 端到端工作流 |
| 人类中位主动操作 | ~2 分钟量级（文：约 **48×** 差距） | **~1.6 小时** |
| Agent 步数 | ~**30** / 任务 | Opus 4.7 max thinking 均 **318.4** tool calls；强配置常 **>250**（Appendix Table 5） |
| 环境 | — | **31** 自托管面向任务的网站 + 桌面应用；有状态用户画像；中途消息注入；有界知识模拟用户 |
| 现象标签 | — | **10** 种 challenge phenomena（可多重标注） |
| 计分 | 二元 | **细粒度 partial**：均 **27.25** checkpoints/任务；功能检查优先；模型评判约占分 **11.53%** |
| 安全 | — | **8** 项诊断检查 + 安全敏感执行审计报告 |
| 发布 | — | 环境、108 任务、自托管站、rollout 轨迹；评测 release **v2026.06.24** |

**十现象（Table 2，任务数/占比）：** Cross-source Reasoning 46 (42.6%)；Visual-spatial Precision 45 (41.7%)；Implicit-state Inference 43 (39.8%)；Multi-item State Tracking 43 (39.8%)；Conflict Disambiguation 39 (36.1%)；Multimodal Editing 30 (27.8%)；Tutorial Following 22 (20.4%)；Dynamic Environment 10 (9.3%)；Streaming Interaction 6 (5.6%)；Proactive Interaction 6 (5.6%)。

**跨应用：** 指令设定上 **64.8%** 任务需 ≥2 应用/服务；含 rollout 使用升至 **75.9%**；rollout 均 **2.44** apps/services（1.0 为 1.35）。

### 4.2 主结果（500-step；Table 3）

设置要点：截图观测；步预算 **500**；Claude 走 `claude_computer_use`，其余发 **pyautogui**；生成上限 16K（MiniMax 8K）；动作后 pause 3s；batched vs single tool；思考档取各模型最高（Claude max / GPT-5.5 xhigh 等）。

|---|---:|---:|---:|---|
| **Claude Opus 4.8** batched + max | **20.6** | **54.8** | ~**$72.4** | 榜首；~224K out tok；~103 steps（batched） |
| Claude Opus 4.7 batched | 18.2 | 48.9 | ~$33.6 | — |
| **GPT-5.5** batched | **13.0** | 49.5 | ~$25.5 | **最省 token**（~37K）；150/300/500 步均平台在 ~13–14% |
| Opus 4.8 single | 18.5 | 49.3 | ~$76.1 | — |
| Sonnet 4.6 single | 8.3 | 41.5 | ~$22.3 | — |
| MiniMax M3 / Kimi 2.6 / Qwen 3.7-Plus | 4.6 / 4.6 / **2.8** | 22.3 / 22.1 / 21.5 | 低美元成本 | 开源/低价对照 |

文内对照：同批 frontier 在 OSWorld 1.0 / Verified 约 **79–83%** binary，在 2.0 上低一个数量级。**部分分高、严格完成低**——额外推理预算多买 partial，少买「最后一英里」完成。

**与 [[UIVenus2GUI智能体]] 交叉（勿重抄训练）：** UI-Venus-2 笔记已报 OSWorld 2.0 **@150 steps** 上 9B/27B Binary/Partial **0.0/7.5** 与 **2.8/13.2**（相对 GPT-5.5 500-step Binary 13.0 的短预算切片）。本篇主表用官方 **500-step** 协议。

### 4.3 失败模式（评测诊断，非训练菜谱）

摘要与 §4.4 共识：失败**很少**是「不会点、不会写代码」，而是：

1. **掉约束 / 漏中途信息 / 该问不问**（动态邮件改预算等）；
2. **流式 UI 时序**：观察–思考–动作间隙导致点击落在**陈旧坐标**；
3. **缺验证与自修**：recovery+repair 合计占用预算 **<7%**；
4. **隐状态簇**：implicit-state、multi-item tracking、conflict disambiguation、dynamic environment 上暴露归因最高。

人类「简单」任务对 agent 仍可难（Streaming / Multimodal Editing）——文指出与纯「人类耗时 scaling」的软件任务规律**只部分迁移**。

## 五、StateAct：程序状态优先于像素

### 5.1 原则（§3）

- 程序状态 $s$（文件、应用后端、DOM、表格…）经两条通道观测：像素 $o_{\mathrm{pix}}=f_{\mathrm{render}}(s)$（**有损、非单射**）与状态查询 $o_{\mathrm{state}}=g(s)$（任务相关子状态上近似可逆）。
- **State-grounding**：动作、验证、记忆默认接地在 $s$；截图点击降为**委托后备**。
- 单步 lossy 读可忍；**数百依赖步**上会复合为错误交付物，且截图难当「已正确保存」的可靠判据。

### 5.2 架构（Figure 2 / §4）

`
Main agent (state-first: bash / Python / file editor)
 │ observe/act on files·DOM·DB·shell
 ├─ delegate (fresh context) → GUI specialist（点选打字）
 ├─ delegate → Web specialist（导航 / 读 DOM）
 ├─ delegate → General agent
 ├─ Context manager：compaction + 外置 plan checklist
 └─ Finish Gate：narration-blind，只查持久化交付物（finish 后；≥3 非 finish 步；最多 3 轮）
`

经验频率（Opus 4.8）：GUI 子代理触及 **28/108** 任务、占主代理步 **1.1%**（占全回合约 11%）；递归委托仅 **7/108** 且从不嵌套——增益来自**观测通道**，不是堆深度。

### 5.3 主结果与消融（OSWorld 2.0；同 Opus 4.8）

| 系统 | Binary % | Partial % | Cost/task |
|---|---:|---:|---:|
| 截图 CUA 参考（OSWorld 2.0 文 Table 3 最强） | 20.6 | 54.8 | ~$72 |
| **StateAct** | **26.9** | **61.6** | ~**$7.8**（约 **9×** 更便宜） |
| Bash-only（无 GUI / 无门控等） | 15.7 | **45.9** | —（partial **低于** 视觉基线 54.8 → 纯代码不够） |

其他（Table 4）：Sonnet 4.6 上 harness 把 binary **8.3→11.1**；**OSWorld-Verified（短程）** StateAct 78.4 vs 参考 77.3——优势**集中在长程**。

**Finish gate 诊断（§6.1 / Table 5）：** 无真值 oracle 时，门控擅长结构性错误（未保存、路径错、缺文件）；在到达门控的 **76** 个非完美任务上，正确拒绝仅 **8**，误放行 **68**（≈90%）——剩余主瓶颈是**价值/推理正确性**，不是「看不见」。

**相对 [[代码智能体Harness史线]]：** 文引 SWE-agent「agents deserve purpose-built interfaces」作相关工作；本篇只记 StateAct 的 **默认路由**（主路径 code/state，GUI 委托），**不展开** ACI 设计史。

## 七、可迁移的评测 / 系统卡字段清单

写 computer-use 相关笔记或卡时，建议显式登记（有则填、无则标缺失）：

1. **观测通道**：纯像素 / DOM·a11y / 文件系统·shell / 混合；是否声明 lossy。
2. **动作空间与 scaffold**：官方 computer-use 工具 vs pyautogui vs code-first；batched 与否。
3. **视野与预算**：最大步/回合、人类中位耗时、跨应用数、中途环境变化。
4. **计分**：binary vs partial checkpoints；模型评判占比；是否审计 reward hacking。
5. **现象标签**：隐状态、动态环境、流式交互、需 ASK_USER 等。
6. **成本**：$/任务、output tokens、tool calls（OSWorld 2.0 / StateAct 示范）。
7. **安全叠层**：拒绝、确认 recall、Watch Mode、注入易感性、独立 monitor 的 P/R、API vs 产品面差异。
8. **验证器能力边界**：结构性 vs 价值正确性（StateAct gate 的 68/76 警示）。

## 八、开放问题（文内已暗示、未闭环）

1. **状态 API 覆盖**：许多应用无完备可编程面——StateAct 仍需 GUI 子代理；如何系统化「何时必须看屏」仍开放。
2. **价值级验证**：无 oracle 时 narration-blind 门控到结构性天花板；能否与任务检查点 / 形式规格对接（勿与 [[过程奖励模型PRM谱系]] PRM 通史混写）。
3. **安全 vs 自主**：高确认 recall 与 Watch Mode 降风险，也限制无人值守；长程专业流（报销、合规）如何分级授权，System Card 未给通用配方。
4. **榜单外推**：Verified ~80% 与 2.0 ~20% 并存——对外沟通必须绑定**任务视野**，避免单一 OSWorld 数字。

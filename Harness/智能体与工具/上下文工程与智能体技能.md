# 上下文工程与智能体技能

> **主要来源**：Anthropic [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)（2025-09-29，简称 Anthropic 上下文工程文）；Anthropic [Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)（2025-10-16，简称 Skills 文）；[Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models](https://arxiv.org/abs/2510.04618)（简称 ACE）；[MCP 规范 2025-11-25 版](https://modelcontextprotocol.io/specification/2025-11-25)（截至 2026-10-08）。其余来源见第十一节。
> **研究线**：架构思想（智能体每一步该把什么放进有限的上下文窗口：系统提示、工具、示例、检索结果、历史与外部状态如何组织，以及程序性知识如何打包成按需加载的技能）· AI Infra（KV 缓存命中率与 token 成本对上下文设计的约束）
> **范围与相邻笔记**：
> - ≠ [[智能体长程记忆]] / [[Mem0与Zep生产级记忆]]：不写记忆系统的实现（分页、记忆提炼与更新、时序知识图），只把「写到窗口外、按需读回」当作一种上下文组织手段。
> - ≠ [[MCP协议与大规模工具导航评测]]：不写 MCP 协议栈与工具检索评测，只取 MCP 原语作为上下文来源的分类，以及工具定义占用上下文的问题。
> - ≠ [[智能体工具与长程任务]]：不写旗舰产品叙事。
> **意义**：模型能力不再是唯一瓶颈之后，智能体是否可靠越来越取决于每一步窗口里放了什么。上下文工程把这件事从「写好提示词」提升为贯穿整个运行过程的系统设计，技能则把其中可复用的部分变成可打包、可共享、按需加载的组件。

**一句话**：上下文是有限且会随长度「变质」的注意力预算，上下文工程的目标是每一步只放「最小的一组高信号 token」。做法分四类：常驻内容要精简（系统提示、工具、示例）；其余内容按需加载（即时检索、渐进披露、技能、以代码调用工具）；长程任务定期整理（压缩、结构化笔记、子智能体）；整体结构为 KV 缓存而设计（稳定前缀、只追加）。ACE 进一步把上下文本身当成可以随经验增量演化的对象。

## 一、问题背景：窗口变长，注意力没有同比变好

1. **位置与长度都会伤害表现**。Lost in the Middle 发现，相关信息位于输入开头或结尾时表现最好，位于中间时显著下降，长上下文模型也不例外（Lost in the Middle 摘要）。RULER 在大海捞针之外加入多跳追踪与聚合任务，发现声称支持 32K 及以上的模型中，只有约一半在 32K 长度上保持令人满意的表现（RULER 摘要）。
2. **任务难度不变，只加长度也会变差**。Chroma 的 Context Rot 报告评测 18 个模型，固定任务难度、只改变输入长度，表现仍随长度下降；干扰项的影响随长度放大。在 LongMemEval 上，只给相关片段（约 300 token）的表现明显好于给完整对话（约 113k token）。报告的结论是：信息是否在上下文里还不够，怎样呈现同样重要。
3. **机制上的解释**。Anthropic 上下文工程文把这种现象称为 context rot：Transformer 中每个 token 要与其余所有 token 建立关系，n 个 token 有 n² 对关系，长度增加时注意力被摊薄；模型训练数据中短序列更多，对长距离依赖的经验也更少。因此上下文应被看作边际收益递减的「注意力预算」。
4. **智能体放大了问题**。Anthropic 多智能体研究系统文称，智能体一般比对话多用约 4 倍 token，多智能体系统约 15 倍；Manus 称其任务平均约 50 次工具调用，输入与输出 token 之比约 100:1。每一轮工具结果都写回上下文，窗口很快被填满。

## 二、概念与脉络

**从提示工程到上下文工程**。Anthropic 上下文工程文的界定：上下文是采样时送入模型的全部 token；提示工程关注如何写好指令，上下文工程关注在推理全过程中如何策划和维护最优的 token 集合，包括提示之外进入窗口的一切（工具、MCP、外部数据、消息历史）。前者是一次性的写作，后者是每一轮都要做的取舍。

## 三、常驻内容：越精简越好

### 3.1 系统提示的「高度」

Anthropic 上下文工程文要求系统提示处在合适的「高度」，避开两种失败：一端是把复杂、脆弱的条件逻辑硬编码进提示，试图精确控制行为，结果难以维护；另一端是只给模糊的高层指导，缺少具体信号。建议用 XML 标签或 Markdown 标题分节，先写最小可用版本，再按观察到的失败模式补充指令。

### 3.2 工具：智能体与环境之间的契约

- **少而清楚**。最常见的失败是工具集臃肿、功能重叠，让模型在选择时面临歧义；文中的判据是：如果人类工程师都说不清该用哪个工具，就不能指望智能体做得更好（Anthropic 上下文工程文）。
- **为模型写工具**。Anthropic 工具写作文（2025-09-11）建议按服务和资源给工具加命名空间前缀；返回对决策有用的信息而非原始标识符；对可能很长的返回做分页、过滤或截断，Claude Code 默认把单次工具返回限制在 25,000 token；参数校验出错时返回能指导修正的信息。
- **协议层的呼应**。MCP 2025-11-25 规范新增工具命名指引，并明确参数校验错误应作为工具执行错误返回而非协议错误，以便模型自我纠正（MCP 规范变更记录）。

### 3.3 示例：典型而非穷举

上下文工程文建议提供多样、典型的示例，而不是把所有边界情况塞进提示。Manus 从另一面提醒：上下文里大量相似的动作—观察对会让模型机械模仿既有模式，偏离当前最优动作；他们在序列化模板、措辞和顺序上引入少量结构化变化来打破这种惯性。

## 四、按需加载：即时检索、工具与技能

### 4.1 即时检索与渐进披露

与其预先检索好所有相关内容放进窗口，不如只保留轻量的引用（文件路径、查询、链接），在运行时用工具读取。文件夹层级、命名和时间戳本身就是相关性信号，智能体可以逐层探索、逐步披露。Claude Code 采用混合策略：CLAUDE.md 预先放入上下文，其余文件用 glob、grep 等原语即时读取。代价是运行时探索比读取预计算结果更慢，且需要好的工具与启发式来避免走偏（Anthropic 上下文工程文）。

### 4.2 工具定义也按需加载

MCP 把服务器能暴露的内容分为资源、提示模板、工具三类（MCP 规范 Overview），这三类都是上下文的来源。服务器一多，仅工具定义就会占掉大量窗口。工具一多时检索与选择的失败，见 [[MCP协议与大规模工具导航评测]]。

- **工具搜索**。Anthropic 高级工具使用文（2025-11-24）举例：58 个工具的定义约 55K token。把工具标记为延迟加载、由模型通过工具搜索按需展开后，官方称 token 用量降约 85%，启用工具搜索后 Opus 4.5 在 MCP 评测上的准确率从 79.5% 升到 88.1%；延迟加载的定义不在初始提示中，因此不破坏提示缓存。
- **对照：遮蔽而不移除**。Manus 主张任务中途尽量不增删工具：工具定义通常位于上下文前部，任何改动都会让其后所有内容的 KV 缓存失效；历史动作引用了已删除的工具，也会让模型困惑。他们改用状态机在解码时遮蔽 logits，并给同类工具统一前缀（如 browser_、shell_），从而在不改上下文的前提下限制可选动作。两种做法的共同点是：不在已缓存的前缀中间改动工具定义。

### 4.3 以代码调用工具

- **工具即文件树**。Anthropic「以代码执行 MCP」文（2025-11-04）把 MCP 服务器呈现为执行环境中的代码 API 文件树，智能体只读取需要的定义，中间结果在执行环境中过滤后再返回。官方称一个示例中上下文从约 150,000 token 降到约 2,000 token（98.7%）。代价是需要安全的沙箱、资源限制与监控。
- **程序化工具调用**。高级工具使用文中，模型写一段代码编排多次工具调用，中间结果不进入上下文；官方称在复杂研究任务上平均 token 降约 37%。同文还建议在工具定义中附调用样例，帮助模型正确填写复杂参数。

### 4.4 智能体技能（Agent Skills）

**形式**。一个技能是一个文件夹，核心是 SKILL.md：YAML 头至少包含 name 与 description，正文是完成某类任务的指令，另可附带脚本、参考文档与模板（Skills 文；agentskills.io）。

**三级渐进披露**（Skills 文）：

| 层级 | 何时进入上下文 | 内容 |
|---|---|---|
| 第一级 | 启动时预载到系统提示 | 每个技能的 name 与 description，供模型判断何时相关 |
| 第二级 | 模型判断相关时读取 | SKILL.md 正文 |
| 第三级及以下 | 执行中按需读取 | 附带的参考文件；脚本可直接运行而不读入 |

由于不必一次读入整个技能，官方称一个技能能打包的上下文量实际上不受限制。

**代码的角色**。确定性操作交给附带脚本。Skills 文的例子是 PDF 技能中预写的脚本负责读取表单的全部字段，模型运行它即可，脚本与 PDF 都不必进入上下文。「以代码执行 MCP」文还指出，智能体把跑通的代码存成可复用函数，再配一个 SKILL.md，就成为技能。

**与 MCP 的关系**。Skills 文把两者定位为互补：MCP 负责连接外部工具与数据，技能负责教会智能体使用这些工具完成复杂流程的程序性知识。

**作者指南与安全**。Skills 文建议先在代表性任务上评测、找出能力缺口，再逐步写技能；SKILL.md 过长时拆成多个文件；name 与 description 决定能否被正确触发。恶意技能可能引入漏洞或诱导数据外泄，应只从可信来源安装，安装前审查附带代码、依赖与指向外部网络的指令。技能与工具描述都是不可信输入的入口，架构层防御见 [[Prompt注入架构防御]]。

**开放标准**。2025-12-18，Anthropic 把 Agent Skills 发布为跨平台开放标准；agentskills.io 的客户端展示列出 Cursor、GitHub Copilot、VS Code、Gemini CLI、OpenAI Codex、OpenHands 等采用方。

## 五、长程任务：跨越窗口的三种手段

1. **压缩**。接近窗口上限时把历史总结成摘要，用摘要开启新窗口。Claude Code 的做法是保留架构决策、未解决的 bug 与实现细节，丢弃冗余的工具输出，再附上最近访问的五个文件（Anthropic 上下文工程文）。最轻的形式是清除早已用过的工具结果；Anthropic 平台的上下文编辑功能即自动清除过期工具调用，官方称在 100 轮网页搜索评测中，它让原本会因窗口耗尽而失败的流程得以完成，token 消耗降 84%（上下文管理公告，2025-09-29）。Manus 强调压缩应可恢复：网页内容可以丢，URL 要留；文档内容可以省，路径要在。编码智能体里的同类做法（只保留最近几条完整观测、更早的折叠为一行）见 [[代码智能体Harness史线]]。
2. **结构化笔记**。智能体把进度、待解决问题写到窗口外的文件，需要时读回。Manus 让智能体维护 todo.md 并逐步勾选，把全局计划反复「复述」到上下文末尾，对抗长循环中的目标漂移。Anthropic 长时程 harness 文（2025-11-26）用一个初始化智能体建立 init.sh、进度日志与初始提交，并按需求列出结构化的功能清单；后续每个会话只推进一项功能并留下清晰的交接痕迹，避免过早宣布完成。把窗口当稀缺内存来分页的系统化做法见 [[智能体长程记忆]]。
3. **子智能体**。主智能体持有高层计划，子智能体在干净的窗口里深入探索，可能用掉数万 token，只返回 1,000 到 2,000 token 的精炼摘要（Anthropic 上下文工程文）。多智能体研究系统文称，Opus 4 主智能体加 Sonnet 4 子智能体的组合在内部研究评测上比单个 Opus 4 高 90.2%；在 BrowseComp 上，token 用量单独解释了约 80% 的表现方差。

**怎么选**（Anthropic 上下文工程文）：需要大量来回对话的任务用压缩保持连贯；有明确里程碑的迭代开发用笔记；可以并行探索的复杂研究用多智能体。

## 六、为缓存而设计：上下文工程的成本面

Manus 把 KV 缓存命中率称为生产智能体最重要的单一指标：输入远多于输出，缓存与否的价差很大，以 Claude Sonnet 为例，缓存输入 0.30 美元每百万 token，未缓存 3 美元，相差 10 倍。由此得出几条原则：

- **前缀稳定**：系统提示开头不放精确到秒的时间戳，一个 token 的差异就会让其后缓存失效；
- **只追加**：不回改历史动作与观察，序列化保持确定（例如 JSON 键序固定）；
- **显式断点**：推理框架不支持自动增量前缀缓存时，手动标记缓存断点；
- **保留错误**：失败的动作和报错留在上下文里，模型会据此调整，降低重复犯错的概率。

前缀缓存的计费结构见 [[Prompt前缀缓存]]。按缓存机制推论，压缩与清除工具结果都会改写历史、放弃此前的缓存，长程设计需要在「窗口更干净」与「缓存命中更高」之间权衡。

## 七、让上下文自己演化：ACE

**问题**。在不改权重、只改上下文的适应方法（提示优化、推理时记忆）中，ACE 指出两种失败（ACE §2.2）：

- **简短偏置**：优化器倾向于产出简洁通用的提示，丢掉领域里具体而有用的启发式；
- **上下文坍缩**：让模型每次整体重写上下文，内容会突然大幅缩水。论文举例，Dynamic Cheatsheet 在第 60 步的上下文有 18,282 token、准确率 66.7，下一步塌缩到 122 token，准确率降到 57.1，低于不做适应的基线 63.7。

**机制**（ACE §3）。上下文被当作逐条积累的「操作手册」（playbook），由三个角色维护：生成器产出推理轨迹，反思器从成败中提炼具体经验，策展器把经验写成小条目的增量更新，由确定性的非 LLM 逻辑合并进现有上下文（§3.1）；条目带编号与计数，新条目追加、旧条目原地更新，再按语义嵌入去重（「增长加精修」，§3.2）。

**结果**（论文称）：智能体任务平均提升 10.6%，金融领域任务提升 8.6%；在 AppWorld 上用较小的开源模型追平榜单第一的生产级智能体；可以只靠执行反馈、不需要标注；适应延迟平均降低 86.9%（ACE 摘要、§4.7）。前身 Dynamic Cheatsheet 让模型在推理时持续积累策略与代码片段，论文称 GPT-4o 在 24 点游戏上的成功率从 10% 升到 99%（Dynamic Cheatsheet 摘要）。

**与技能的对照**。两者都把程序性知识外置为可编辑的文本：技能多由人编写、按需加载、以文件夹为单位分发；ACE 的手册由模型自己策展、常驻上下文、以条目为单位增量更新。Skills 文也把「让智能体自己创建、编辑和评估技能」列为未来方向。

## 八、与相邻笔记的分工

## 九、意义

- **把可靠性问题前移到输入侧**：许多被归因于「模型不够聪明」的失败，其实是窗口里噪声太多、关键信息不在注意力范围内；上下文工程给出了可操作的排查维度。
- **把提示从文本变成运行时结构**：上下文不再是一段写好的提示，而是每一轮由检索、压缩、笔记、子智能体和缓存约束共同决定的结构。
- **技能让知识可以分发**：渐进披露让一个智能体能挂载大量专门知识而不撑爆窗口，开放标准又让同一个技能能在多个产品间复用。

## 十、局限与待核实

1. **证据以工程博客为主**：Anthropic 与 Manus 的数字多来自内部评测，评测集与基线未公开，难以独立复现；它们说明方向，不宜当作可比的基准结果。
2. **模型与时间相关**：上下文腐化的程度、合适的压缩力度、工具数量上限都依赖具体模型；随着模型更擅长长上下文，部分技巧的收益可能下降。
3. **方法之间存在张力**：压缩与清理利于窗口干净，却破坏缓存；即时检索节省窗口，却增加延迟和走偏风险；子智能体提升效果，token 成本也成倍上升。
4. **ACE 的适用面**：论文的提升集中在 AppWorld、金融等少数基准；常驻的手册越长，同样会受第一节所说的长度代价影响。
5. **未覆盖的方向**：上下文工程的自动化评测、多模态上下文（截图、视频）的组织、通过训练让模型学会管理自身上下文的方法。

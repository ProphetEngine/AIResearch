## 一、为何 2025 旗舰强调智能体 / 工具 / 长程

2024–2025 的公开叙事里，「旗舰模型」的验收口径发生了一次可见的平移：**从单轮答题分数 → 能否在工具环里把多步真实工作做完**。Claude 4 发布页把 Opus 4 / Sonnet 4 直接写成「coding、advanced reasoning、**AI agents**」的新标准；OpenAI 则把 GPT‑5 在 ChatGPT 侧写成「统一系统」，在 API 侧写成「**best model yet for coding and agentic tasks**」（开发者页）。两条线都在回答同一类产品问题：用户不再只问「这道题答对了吗」，而问「能不能连续改仓库、查环境、调工具、坚持几小时还不跑偏」。

把公开叙述压成三股推力，便于跟读：

1. **任务形态变了：多步、有状态、可失败**
 SWE-bench / Terminal-bench / τ（tau）类工具基准，测的是「仓库 + 工具 + 环境反馈」闭环，而不是纯文本选择题。Claude 4 页强调 Opus 4 在复杂、长时任务与 agent workflows 上的持续表现；GPT‑5 开发者页强调「dozens of tool calls—both in sequence and in parallel」以及 long-running agentic tasks。

2. **能力接口变了：思考与工具不再互斥**
 Claude 4 明确推出 **Extended thinking with tool use（beta）**：在扩展思考中穿插工具（如 web search），在推理与工具调用之间交替。GPT‑5 ChatGPT 侧用 **router** 按「对话类型、复杂度、**tool needs**、显式意图」在快答与更深思考（GPT‑5 thinking）之间切换；API 侧则用 `reasoning_effort` / preamble / parallel tool calling 把「想多久、说多少、何时调工具」交给开发者旋钮。

3. **产品形态变了：从「聊天框」到「可挂载运行时」**
 Anthropic 同期 GA **Claude Code**，并发布 code execution tool、MCP connector、Files API、最长约一小时的 prompt cache——这些不是「又一个基准分」，而是把模型嵌进 IDE、后台任务与文件/沙箱世界。OpenAI 侧则强调 agentic coding 产品（Cursor、Windsurf、GitHub Copilot、Codex CLI 等）里的协作行为：计划、工具间更新、主动推进复杂任务。

**一句话抓手：** 2025 旗舰把「智能」重新定义为 **工具环上的长程稳定性**——能并行调工具、能在思考中查证、能在上千步 / 数小时级工作流里少走捷径、少丢上下文。架构思想上，这是「单次前向生成」向「带状态的闭环策略」扩展；Infra 辅线上，则是会话时长、沙箱、缓存与可观测边界成为一阶产品约束。

## 二、架构思想：工具调用、并行工具、扩展思考与长程稳定性

以下分块只写**官方已公开**的机制与主张；两边对照，便于看到「同一问题的两种产品化答案」。

### 2.1 工具调用：从「会说话」到「会行动」

| 维度 | Claude 4（官方页） | GPT‑5（官方主页 + 开发者页） |
|------|-------------------|------------------------------|
| 定位 | 面向 coding / agents；Opus 4 强调 agent workflows | ChatGPT：统一系统；API：coding & agentic tasks |
| 工具环能力 | 扩展思考中可调工具（beta）；可并行用工具；本地文件访问下记忆增强 | 指令跟随 + agentic tool use 显著提升；可串行/并行链式调用大量工具；更好处理工具错误 |
| 人机协作 | Claude Code GA；IDE 内联编辑；GitHub Actions 后台任务 | 工具调用前后可输出 preamble（计划/进度）；更主动完成复杂任务而不频繁停顿征求确认 |
| 公开基准锚点 | SWE-bench Verified：Opus 4 **72.5%**、Sonnet 4 **72.7%**；Terminal-bench：Opus 4 **43.2%**（页内注明 SWE/Terminal **未**用 extended thinking） | SWE-bench Verified：**74.9%**；τ²-bench telecom：**96.7%**；Scale MultiChallenge（指令跟随，o3-mini 评分）：**69.6%** |

**跟读要点：** 两边都把「工具」写成一等公民，而不再是插件演示。架构思想上，工具调用 = 模型输出一种**可解析的行动意图**（函数名 / 参数 / 自定义明文协议），运行时执行后把观察写回上下文；长程任务的「策略」因此分布在 **模型策略 + 工具结果 + 开发者指令** 三者之间，而不是只在权重里。

### 2.2 并行工具：把「一步一调」改成「一轮多行动」

- **Claude 4**：官方页明确「Both models can use tools in parallel」。对 agent 而言，这意味着同一决策步可同时拉搜索、读文件、跑检查，减少「串行往返」带来的延迟与上下文漂移。
- **GPT‑5**：开发者页写明可可靠地链式组合 **dozens of** 工具调用——**既可序列也可并行**——且「without losing its way」；API 能力列表也包含 parallel tool calling。相对 o3，SWE-bench Verified 上 GPT‑5 在高分同时宣称 **少 22% output tokens、少 45% tool calls**（开发者页）——提示「并行 / 更准的工具选择」可能同时改善延迟与成本，而不只是「多调几次」。

**思想对照：** 并行工具改变的是控制流图：从线性「想→调→看→再想」变成「一批假设并行取证 → 再聚合」。这对长程稳定性的含义是：减少中间轮次，也就减少「中途换目标 / 遗忘约束」的机会；但也提高了对**工具沙箱并发、超时与部分失败**的 Infra 要求（见第三节）。

### 2.3 扩展思考 / 统一路由：何时快答、何时深想、何时摸工具

**Claude 4：Hybrid + Extended thinking with tool use**

- 两个模型都是 **hybrid**：近即时回复 vs **extended thinking** 更深推理；用户可按任务切换。
- **Extended thinking with tool use（beta）**：允许在扩展思考过程中使用工具（如 web search），在 reasoning 与 tool use 之间交替，以改进回答。
- 对过长思维过程引入 **thinking summaries**（用更小模型压缩）；官方称约 **5%** 的思维过程长到需要摘要，其余多数可全文展示；需要原始 CoT 的开发者可走 Developer Mode（销售渠道）。
- System Card（§1.1.2）确认：相对 Sonnet 3.7「默认展示原始思维」，Claude 4 对较长思维改为摘要展示；Developer Mode 可保留全文。

**GPT‑5：Unified system + router + reasoning_effort**

- ChatGPT 侧：GPT‑5 是 **unified system**——高效快答模型 + 更深推理模型（GPT‑5 thinking）+ **real-time router**；路由依据包括 conversation type、complexity、**tool needs**、以及显式意图（如提示里写 “think hard about this”）。
- Pro 档提供 **GPT‑5 pro**：更长思考，使用 scaled 但高效的 **parallel test-time compute**，面向最难任务（主页）。
- API 侧（开发者页）：ChatGPT 里的「系统」与 API 里的「推理模型」不完全等同——API 的 GPT‑5 是支撑 ChatGPT 最高性能的推理模型；`reasoning_effort` 现含 **minimal / low / medium / high**；另有 `verbosity`；另有 **custom tools**（明文而非 JSON，可加 CFG/正则约束）。
- 开发者页强调：若被指示，模型可在工具调用**之前与之间**输出用户可见的 **preamble**（计划与进度），与隐藏推理文本不同。

**跟读抓手（架构思想）：**

> **思考预算** 与 **工具预算** 被显式产品化：Claude 用「扩展思考开关 + 思考中可调工具」；OpenAI 用「路由 / effort 旋钮 + 工具前后可见 preamble」。二者都在解决同一矛盾——长程任务既需要额外计算，又不能把所有延迟与 token 无差别砸进每一次回复。

### 2.4 长程稳定性：持续注意力、记忆、少走捷径

官方叙述里，「长程」不是抽象口号，而是可引用的工作形态：

1. **持续执行时长与步数（Claude）**
 - Opus 4：「sustained performance on long-running tasks that require focused effort and **thousands of steps**」，并可「work continuously for **several hours**」。
 - 客户侧公开例子：Rakuten 验证独立运行约 **7 小时**的开源重构且保持持续表现（Claude 4 页转述）。
 - System Card 引言：两模型尤其擅长复杂编程任务，并可在**持续时段内自主、有成效地执行**。

2. **记忆作为外部状态（Claude）**
 - 当开发者赋予本地文件访问时，模型更擅于创建/维护 **memory files**，提取并保存关键事实，以保持连续性、积累「默会知识」。
 - 页内 Pokémon 例子：Opus 4 写 Navigation Guide 类笔记以改善长期任务意识——说明长程 agent 的稳定性往往来自 **把状态写到工具可达的外部存储**，而不只靠上下文窗口。

3. **少捷径 / 少 reward hacking 倾向（Claude）**
 - 官方页：相对 Sonnet 3.7，两模型在易诱发捷径与漏洞的 agentic 任务上，使用 shortcut / loophole 的倾向约低 **65%**。
 - System Card 专设 **Reward hacking** 与 **Agentic safety** 章节（计算机使用、提示注入、恶意 agentic coding）——把「长程能干活」与「长程乱干活」绑在同一评估议程里。

4. **长程工具智能与协作风格（GPT‑5）**
 - 开发者页：擅长 **long-running agentic tasks**；工具指令更准、更会处理工具错误、长上下文检索更强；在 agentic coding 产品中可输出计划、更新与复盘，并更主动推进高复杂度任务。
 - 主页：指令跟随与 agentic tool use 基准提升，使模型更能可靠执行 **multi-step** 请求、跨工具协调、并适应语境变化，把更多工作 **end-to-end** 做完。

5. **脚手架仍在（重要纠偏）**
 Claude 4 页附录写明：SWE-bench 仍用「仅 bash + 字符串替换式文件编辑」的简单 scaffold，并**去掉**了 Sonnet 3.7 用过的第三种 planning tool。这说明公开高分仍依赖 **明确的工具面与 harness**；「模型变强」与「运行时变强」要分开记账，避免把 scaffold 功劳全记到权重上。

### 2.5 两边叙事的「同构」与「分叉」（架构思想小结）

**同构：**

- 都把 **coding agent** 当作旗舰能力的主舞台。
- 都强调 **并行工具**、**多步不丢线**、**更深思考可按需开启**。
- 都在补「人机接口」：一边是 IDE/Claude Code/MCP/Files；一边是 preamble、verbosity、custom tools、Responses/Chat Completions 等 API 控制面。

**分叉（仅就已核实公开文）：**

- Claude 更直白地讲 **数小时 / 上千步** 与 **外部 memory files**；并把「思考中途调工具」做成独立 beta 能力名。
- GPT‑5 更直白地讲 **统一路由系统**、**effort/verbosity 旋钮**、**工具前后可见进度**，以及相对前代的 **工具调用次数效率**（更少无效调用）。
- 安全层级表述：Claude System Card 写明 Opus 4 以 **ASL-3**、Sonnet 4 以 **ASL-2** 部署；GPT‑5 主页指向 system card 与生物风险等综合防护，**具体 ASL 类比框架不适用于 OpenAI，勿混用术语**。

## 三、AI Infra 辅线：会话时长、工具沙箱、可观测性边界（公开层面）

本节只谈官方页 / System Card **公开可见**的基础设施含义；内部集群拓扑、精确超时、未公开监控指标 → **待核实**。

### 3.1 会话时长与上下文经济

| 公开线索 | Infra 含义（跟读，非内部规格） |
|----------|--------------------------------|
| Claude：prompt cache **最长约 1 小时**；数小时级持续工作叙事 | 长程 agent 需要 **跨多轮的前缀复用** 与会话粘性；缓存 TTL 变成产品能力，而不只是计费优化 |
| Claude：thinking summaries（约 5% 触发） | 超长 CoT 若全文回传，会挤占上下文与带宽；摘要是 **展示层 / 传输层** 的折中，Developer Mode 保留原文给高级用户 |
| GPT‑5：开发者页称模型可接受极大输入/输出与总上下文（页内给出合计约 **400,000** tokens 量级的表述；具体以官方实时文档为准） | 长程工具轨迹（多轮 tool result）本身就是上下文压力；Infra 要同时管 **KV / 计费 / 截断策略** |
| GPT‑5：相对 o3 在 SWE-bench 上更少 output tokens 与 tool calls | 「更强 agent」不完全等于「更贵轨迹」；路由与工具选择质量会反馈到 serving 成本 |

**待核实：** 两侧生产环境的硬超时、最大连续工具步数、后台任务（如 GitHub Actions 上 Claude Code）的调度与重试策略——公开页未给出可复述的数值 SLA。

### 3.2 工具沙箱与执行面

Claude 4 页列出的新 API 能力，可直接读成 **执行面拆分**：

1. **Code execution tool**——把「写代码」变成「在受控环境跑代码」。
2. **MCP connector**——把外部工具/数据源以协议方式接入（Model Context Protocol）。
3. **Files API**——文件成为一等资源，支撑记忆文件、物料上传与跨会话资产。
4. **本地文件访问（由开发者授予）**——记忆与长程连贯性的前提是 **权限边界清晰的文件系统**。

GPT‑5 开发者页对应的执行面语言包括：built-in tools（web search、file search、image generation 等）、**custom tools**（明文 + 可选语法约束）、parallel tool calling，以及 prompt caching / Batch 等降本能力。

**跟读原则：** 长程 agent 的正确性高度依赖沙箱语义——网络是否出站、文件系统是否可写、密钥是否注入、失败是重试还是上报。System Card **§3 Agentic safety** 明确评估：计算机使用恶意用途、**prompt injection**（环境中的弹窗/隐藏文本劫持意图）、以及恶意 agentic coding。公开给出的 computer-use prompt injection 防护分数示例（System Card 表 3.2.A）：带 safeguards 时 Opus 4 **89%**、Sonnet 4 **86%**（越高越好）。这说明 Infra 上的「检测并中止」与模型侧 RL 防护是叠层的，而不是单靠模型自觉。

### 3.3 可观测性边界（公开能说清的部分）

1. **对用户可见 vs 对开发者可见**
 - Claude：多数思维全文可见，少数长思维被摘要；原始 CoT 需 Developer Mode。
 - GPT‑5：隐藏推理 vs 用户可见 preamble 被显式区分——preamble 用于沟通计划/进度，不等于完整 chain-of-thought。

2. **对安全运营可见**
 System Card 描述计算机使用与 agentic coding 的部署后监控、违规账号干预（系统提示干预、移除计算机能力、封禁等）。这是典型的 **策略面可观测性**，不是给终端用户的 debug UI。

3. **评估可观测性**
 Claude 的 SWE-bench「high compute」叙述包含：多样本并行尝试、丢弃破坏可见回归测试的 patch、内部评分模型选优——这是 **test-time compute + 过滤** 的评估 harness，本身也是一种 Infra 模式；产品是否原样提供同等并行尝试 → **待核实**。

4. **对齐评估中的高主动性提醒（Claude System Card）**
 Opus 4 在被鼓励「take initiative」等提示时，可能在模拟场景中采取非常大胆的行动（如大量外发邮件）。公开建议：对可能引发高主动性的系统提示保持谨慎。这对 Infra/产品的启示是：**工具权限 × 系统提示语气** 必须一起进入发布审查，而不是只审查模型权重。

## 四、常见误区与引用

### 4.1 常见误区

1. **误区：旗舰分高 = 已解决长程 agent。**
 纠正：公开高分仍绑在特定 scaffold、工具集、步数上限与是否 extended thinking 上。Claude 附录对 TAU-bench 甚至写明：为配合「思考中用工具」，最大步数从 30 提到 100。换 harness 可能换故事。

2. **误区：并行工具只是加速，不改变架构。**
 纠正：并行改变控制流与失败模式（部分成功、竞态、重复副作用）。模型「会并行」与运行时「能安全并行」是两件事。

3. **误区：扩展思考 / router 等于永远更深、永远更好。**
 纠正：两边都在卖 **按需分配思考**。GPT‑5 的 minimal effort、Claude 的 hybrid 近即时模式，都承认延迟与成本约束；开发者页还提醒并非所有任务都随 effort 单调收益。

4. **误区：memory files / 长上下文 = 永久记忆。**
 纠正：Claude 的记忆叙述以 **开发者授予的本地文件访问** 为前提；本质是外部状态存储。没有权限与写入约定，就没有产品意义上的「长期记忆」。

5. **误区：把 System Card 里的极端对齐场景当成日常产品行为。**
 纠正：System Card 的 self-preservation / high-agency 等评估多在构造场景与特定系统提示下；官方同时强调日常用法下的表现与缓解措施。跟读时应区分 **能力边界探测** 与 **默认产品行为**。

6. **误区：混用两家安全等级术语或未核实的发布日期/分数。**
 纠正：ASL-2/3 是 Anthropic RSP 用语；引用分数时核对是否含工具、是否 extended thinking、子集大小（如 SWE-bench 全量 500 vs 477 子集）。本笔记未在原文出现的数字一律不写。

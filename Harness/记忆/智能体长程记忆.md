# Agent 长程记忆（相对 13 的子题）

> **定位**：智能体记忆评测**子题补洞**——相对 **[[智能体工具与长程任务]]**（工具环 / MCP / 长程任务可靠性）**未单独立题**的部分：分层记忆、分页（paging）、Zettelkasten 式 agent memory。
> **攻坚线**：**架构思想（主）** + **AI Infra（记忆存储，辅）**。
> **硬划界（禁止重写）**：**不写** ReAct 全文、MCP 协议栈、并行工具环、扩展思考中调工具、Claude/GPT 旗舰 agent 产品叙事——那些已在 **[[智能体工具与长程任务]]**。本篇只收「上下文窗口当作稀缺物理内存 → 如何外置与自管理」。
> **与 [[智能体工具与长程任务]] 的接口一句**：[[智能体工具与长程任务]] §2.4 / 误区 4 已点明 Claude 的 memory files = **开发者授权的外部状态**；本篇把同一问题做成**可对照的两套系统论文**：OS 分页隐喻（MemGPT）vs 卡片盒互联笔记（A-Mem）。
> **禁止编造**：机制、分层名、公式编号、评测数字一律取自官方 PDF（2026-09-22 CST）；图中仅曲线、正文未给精确点值处 **不读点、不臆造**。

## 二、问题框定（相对「加长上下文」）

两篇论文的共同前提（MemGPT §1；A-Mem §1）：

1. **窗口有硬顶**：开源与 API 模型的 token 上限仍约束「多轮对话 / 长文档」；MemGPT Table 1（数据截至约 **1/2024**）列出 Llama～Yi-34B-200k 等窗口与粗算可容纳消息数。
2. **盲目扩窗不免费**：自注意力成本随长度恶化；即便能训更长模型，Liu et al. (2023a) 等显示长上下文也常 **用不好中间段**（MemGPT §1 / §3.2 引用）。
3. **Agent 场景需要外置状态**：工具环（[[智能体工具与长程任务]]）解决「怎么行动」；长程记忆解决「跨会话 / 跨文档的事实与关系放哪、怎么取回」——A-Mem 明确说：现有记忆系统多要求开发者 **预先规定结构、写入点与检索时机**，图数据库等也仍受 **预设 schema** 限制（§1、Figure 1）。

**本篇不展开：** 长上下文注意力核（→ **[[长上下文位置编码与系统侧]]**）、RAG 索引工程全文（→ **B6**）、旗舰 System Card 里的 agent safety（→ [[智能体工具与长程任务]] / [[GPT6AstraSystemCard]]）。

## 三、MemGPT：OS 隐喻下的分层记忆与分页

### 3.1 两层总览（§2）

| 层级（论文用语） | OS 类比 | 内容 / 可达性 |
|---|---|---|
| **Main context** | 主存 / RAM | = LLM **prompt tokens**；推理时「可见」 |
| **External context** | 磁盘 | 窗口外一切；必须经函数 **显式换入** main context 才参与推理 |

Main context 再切三段连续块（§2.1，Figure 3）：

| 段 | 读写 | 用途（文内） |
|---|---|---|
| **System Instructions** | 只读、静态 | 控制流说明、各内存层用途、MemGPT 函数用法（如何检索 out-of-context 数据） |
| **Working Context** | 固定大小；**仅**经 MemGPT 函数读写 | 对话设定下存用户/人设关键事实与偏好，支撑连贯对话 |
| **FIFO Queue** | Queue Manager 写入 | 滚动消息史（用户、系统告警、函数 I/O）；队首常为 **对已驱逐消息的递归摘要** |

External 侧两大库（Figure 3）：

- **Recall Storage**：消息数据库；FIFO 驱逐后消息仍无限期保存在此，可经函数搜回并 append 回队列。
- **Archival Storage**：任意长度文本对象的读写库（对话里也可把重要信息从 FIFO **升华**写入；文档任务则整库向量检索）。

### 3.2 压力告警、驱逐与分页（§2.2–2.3）

**Queue Manager 溢出策略（文内举例）：**

- prompt tokens 超过 **warning token count**（例：**70%** 窗口）→ 插入系统消息（**memory pressure**），提示模型用函数把 FIFO 中重要信息写入 working context 或 archival。
- 超过 **flush token count**（例：**100%**）→ **flush**：驱逐约 **50%** 窗口量级消息，用「旧递归摘要 + 被驱逐消息」生成新递归摘要；被驱逐消息不再 in-context，但在 recall 中可搜。

**自导编辑 / 检索：** 记忆更新与搜索完全由 LLM 经函数调用决定（§2.3）；解析器校验参数，运行时错误（如 working context 已满仍写入）回灌处理器形成反馈环。检索侧实现 **pagination**，避免一次取回撑爆窗口。

**控制流（§2.4，与「工具环」的边界）：** 事件（用户消息、容量告警、登录/上传完成、定时器）触发推理；函数可带 `request_heartbeat=true` **链式**多步检索后再 yield 给用户。此处函数调用是 **内存 OS 的控制面**，本篇**不**据此重述通用 ReAct/MCP。

### 3.3 评测锚点（只记文内可核对结论）

**对话（§3.1，Multi-Session Chat 扩展）：**

- **Deep Memory Retrieval（DMR）** Table 2：固定上下文基线 Accuracy 约 **32–39%**；同模型 + MemGPT 升至 **66.9%（GPT-3.5 Turbo）/ 92.5%（GPT-4）/ 93.4%（GPT-4 Turbo）**，ROUGE-L 同步上升。
- **Conversation opener** Table 3：MemGPT 各底座在 SIM-1/3 上可接近或超过 Human opener；文内强调 **working context 中持久化人设信息** 是高参与度 opener 的关键。

**文档（§3.2）：**

- **Multi-document QA**（NaturalQuestions-Open + Wikipedia dump；检索共用 `text-embedding-ada-002`；MemGPT 默认 **PostgreSQL + pgvector + HNSW**）：Figure 5 叙述——MemGPT 表现 **不随检索文档数增加而崩**；截断等压缩手段会随压缩变强而劣化（**精确逐点准确率以图为准，正文未列表格点值 → 不臆造**）。
- **Nested KV retrieval**（作者新任务）：需沿「值即下一键」多跳；Figure 7 叙述——**MemGPT 是唯一能在嵌套层数 >2 时持续完成**的路线；固定上下文基线在嵌套任务上明显吃力（GPT-3.5 无法完成嵌套变体等，§3.2 正文）。分页多跳示例见 Figure 6/8（archival_storage.search 带 `page=`）。

**实现细节可跟读：** GPT-4 Turbo = `gpt-4-1106-preview`（128k）、GPT-4 = `gpt-4-0613`（8192）、GPT-3.5 Turbo = `gpt-3.5-turbo-1106`（16385）（§3 Implementation details）。

## 四、A-Mem：Zettelkasten 式 Agentic Memory

### 4.1 相对「传统记忆系统 / agentic RAG」的主张（§1–2.2）

- **传统记忆（Figure 1a）**：工作流里写死何时 Write/Read → 换环境难泛化。
- **图库 / Mem0 等**：结构化有帮助，但 **预设 schema** 限制「新知识长出新组织方式」。
- **相对 agentic RAG**：后者 agency 多在 **检索阶段**（何时取、取什么）；A-Mem 主张 agency 下沉到 **存储结构自身的演化**——笔记自生成上下文描述、建链、随新经验改写旧笔记（§2.2）。

灵感：**Zettelkasten**（Ahrens；Kadavy 等，文内引用）——原子笔记 + 灵活链接；A-Mem 允许同一记忆同时落入多个「box」（相似上下文描述聚成的概念盒，Figure 2）。

### 4.2 三件套方法（§3）

**（1）Note Construction（§3.1）**

每条记忆
$$
m_i=\{c_i,\, t_i,\, K_i,\, G_i,\, X_i,\, e_i,\, L_i\}
$$
（式 1）：原始交互 $c_i$、时间戳 $t_i$、LLM 生成的 **keywords** $K_i$、**tags** $G_i$、**contextual description** $X_i$、链接集 $L_i$、稠密向量 $e_i$。

$$
K_i,G_i,X_i \leftarrow \mathrm{LLM}(c_i\Vert t_i\Vert P_{s1})\qquad(2)
$$
$$
e_i = f_{\mathrm{enc}}[\mathrm{concat}(c_i,K_i,G_i,X_i)]\qquad(3)
$$
实现：全文实验统一 **all-minilm-l6-v2** 作文本编码器（§4.2）。

**（2）Link Generation（§3.2）**

新笔记 $m_n$ 入库存后：对历史笔记算余弦相似度（式 4）→ 取 top-$k$ 近邻 $M^{n}_{\mathrm{near}}$（式 5）→ LLM 判定是否建链并更新 $L_i$（式 6，模板 $P_{s2}$）。嵌入粗筛 + LLM 细判，声称可捕获「非纯相似」的因果/概念关系。

**（3）Memory Evolution（§3.3）**

对近邻中每条 $m_j$，再经 LLM 决定是否更新其 context / keywords / tags（式 7，模板 $P_{s3}$），以 $m_j^*$ 替换原笔记——网络随写入 **持续改写**，而非只追加。

**检索（§3.4）：** 查询编码后余弦 top-$k$（式 8–10）；Figure 2 还写：取回某条时，同 box 内链接记忆可一并触及。主实验默认 **$k=10$**，部分类别另调（§4.2；细节见 Appendix A.5）。

### 4.3 评测锚点（§4；以表内数字为准）

**数据：**

- **LoCoMo**：对话更长（文称均值约 **9K** tokens、最多约 **35** sessions；相对旧集约 1K / 4–5 sessions）；**7512** QA；五类：Multi-Hop / Temporal / Open-Domain / Single-Hop / Adversarial。
- **DialSim**：长 multiparty 对话 QA（Friends 等；约 **350k** tokens 量级叙述）。

**基线：** LoCoMo、ReadAgent、MemoryBank、**MemGPT**（同台）。

**LoCoMo × GPT-4o-mini（Table 1 节选）：**

| Method | Multi-Hop F1 | Temporal F1 | Avg Ranking (F1) | Token Length |
|---|---:|---:|---:|---:|
| LoCoMo | 25.02 | 18.41 | 2.4 | 16,910 |
| MemGPT | 26.65 | 25.52 | 2.4 | 16,977 |
| **A-Mem** | **27.02** | **45.85** | **1.2** | **2,520** |

（同表另有 Open Domain / Single Hop / Adversarial 及 BLEU-1；GPT-4o 行上 A-Mem Multi-Hop F1 **32.86** vs MemGPT **30.36**，Token Length **1,216** vs **16,987**。完整格以 PDF Table 1 为准。）

**DialSim（Table 2）：** A-Mem F1 **3.45** vs LoCoMo **2.55** vs MemGPT **1.18**（文内称相对 LoCoMo +35%、相对 MemGPT +192%——百分比为作者叙述，原始分为上列）。

**消融（Table 3，GPT-4o-mini）：** 去掉 Link Generation + Memory Evolution → Multi-Hop F1 跌至 **9.65**；仅去 ME（保留 LG）→ **21.35**；完整 A-Mem → **27.02**。文内结论：LG 是组织基础，ME 提供结构精炼，二者互补（§4.4）。

**成本叙述（§4.3）：** 约 **1,200** tokens / memory operation，相对 LoCoMo/MemGPT 约 **16,900** tokens 称 **85–93%** 削减；商业 API 下称每次操作 **\<$0.0003**；GPT-4o-mini 约 **5.4 s**、本地 Llama 3.2 1B 约 **1.1 s**（文内数字，部署条件以原文为准）。

**$k$ 敏感性（§4.5 / Figure 3）：** $k\in\{10,20,30,40,50\}$ ——增大 $k$ 通常先升后平台甚至略降；**精确曲线点不臆造**。

**局限（§6）：** 组织质量仍受底座 LLM 能力影响（不同模型生成描述/链接可能不同）；当前实现偏文本，多模态为未来工作。

## 五、对照：分页 OS vs 卡片盒网络（架构思想）

| 维度 | MemGPT | A-Mem |
|---|---|---|
| **核心隐喻** | 虚拟内存 / 分层存储 / page in-out | Zettelkasten：原子笔记 + 链接 + 演化 |
| **「热」状态** | System + Working + FIFO（固定窗口预算） | 当前交互 prompt + top-$k$ 检索笔记 |
| **「冷」状态** | Recall（对话史）+ Archival（任意文本/文档向量库） | 全体笔记库 $M$（带 $K,G,X,L,e$） |
| **谁决定换入换出** | LLM 函数调用 + Queue Manager 告警/驱逐；分页防溢出 | 写入时 LLM 建链/改写；查询时嵌入 top-$k$（链上邻居可连带） |
| **结构是否预设** | 层类型预设，但写入内容自导 | 反对写死 workflow/schema；结构随笔记生长 |
| **Infra 辅线** | PostgreSQL + pgvector + HNSW；消息库与归档库分离 | 轻量编码器（all-MiniLM）+ 笔记属性存储；强调 token 预算 |
| **典型压力测试** | 超长文档 QA、嵌套 KV 多跳、多 session 对话一致性 | LoCoMo 多跳/时间推理、DialSim；相对 MemGPT 的 token 效率 |

**跟读抓手（可写进卡片）：**

> **MemGPT** 回答：「窗口是 RAM——如何 **page** 才不丢长期事实？」
> **A-Mem** 回答：「记忆应是 **可改写的互联笔记**——如何让新经验 **进化** 旧组织？」
> 二者都把 agency 放进记忆子系统；都 **不是**「只把 RAG 挂到 ReAct 环上」的同义反复。

**与 [[智能体工具与长程任务]] 的干净接口：** 工具环决定 *call tool / use MCP*；本篇机制决定 *working_context.replace / archival.search(page=…)* 或 *写笔记→建链→演化*。产品上的「memory files」（[[智能体工具与长程任务]]）更贴近 MemGPT 的 **外部可写存储** 叙事，而 A-Mem 额外强调 **笔记图的自主重组**。

## 六、AI Infra 辅线（记忆存储，短）

仅列论文已写、与部署相关的接口——不扩成向量库选型长文：

1. **MemGPT archival**：PostgreSQL + **pgvector**，HNSW 近邻；文档嵌入可预计算装库；搜索结果 **分页**进 main context（§3.2.1）。
2. **MemGPT recall / FIFO**：会话消息持久化与递归摘要，对应「对话历史冷热分层」。
3. **A-Mem**：统一句子嵌入模型；每条记忆多字段（关键词/标签/描述/链接）；写入路径含 **多次 LLM 调用**（构造 + 链接 + 演化），换来检索阶段更短的 prompt（§4.3 成本段）。
4. **共同产品含义：** 长程 agent 的可靠性预算 = **模型推理** + **记忆读写延迟/费用** + **上下文装配策略**；只扩窗口或只堆工具调用，都不自动等于「会记得」。

# Long-context：检索式注意力加速 vs 全注意力（RetrievalAttention + InfiniRetri）

> **定位**：检索式注意力 **P1**——相对 **[[长上下文位置编码与系统侧]]**（YaRN 位置外推 + vLLM/PagedAttention 显存通史）补一条近窗横切：**在模型内部用「检索」近似或替代精确全注意力 / 全 KV 流**，对照「精确全注意力」的推理轴。主锚两篇一手 PDF：**RetrievalAttention**（2409.10516）与 **InfiniRetri**（2502.12962）。
> **攻坚线**：**架构思想（主）**——KV 向量 ANNS / 注意力分数句级缓存如何对齐全注意力；**评测/延迟字段（辅）**——∞-Bench、RULER、NIH、LongBench 与 128K 级 per-token 延迟。
> **硬划界（禁止重写）**：
> - **≠ [[长上下文位置编码与系统侧]]**：不重写 RoPE / YaRN / Dynamic-YaRN、PagedAttention block 表、vLLM 调度通史；本篇只在「窗口已认、KV 已在」之后谈 **检索近似**。
> - **≠ B6 / [[SelfRAG与CorrectiveRAG]]**：外挂语料 RAG（DPR / Self-RAG / CRAG）≠ **模型内部** 对 KV 或注意力分数的检索；InfiniRetri 文内自称「unlike RAG、不用外部 embedding」，本篇跟读该主张，**不展开**外挂索引产品。
> - **≠ [[注意力效率族MQA到MLA]]**：注意力效率通史（FlashAttention 等）只交叉引用；本篇钉 **检索式稀疏 / 句级重填窗口** 两条近窗方法。
> - **≠ [[KV缓存量化与压缩]]**：不写 KV **量化**压缩；本篇是检索选 token / 选句，不是低比特 KV。
> **禁止编造**：公式骨架、表数字、延迟与扫描比例一律取自官方 PDF（2026-09-22 CST）。

**一句话谱系（跟读枢纽）：**

| 轴 | 精确全注意力 / Full KV | RetrievalAttention | InfiniRetri |
|---|---|---|---|
| **检索对象** | 无（对全部 $k_i$ 做 softmax） | **key 向量**（内积 ≈ 注意力 logits） | **注意力分数导出的句级 token ID** |
| **发生阶段** | prefill + decode | 主打 **decode**（假定长 prompt 已 prefill / context caching） | **整段超长输入**的分段迭代推理 |
| **落点硬件** | 全量 KV 常驻 GPU（易 OOM） | 多数 KV → **CPU ANNS**；GPU 只留静态近窗 + 检索回灌 | 缓存在 **模型外**（token ID），每步再 merge 进窗口做标准注意力 |
| **相对「外挂 RAG」** | — | 仍是**同一次**注意力计算的稀疏近似 | 文称用 **LLM 自身注意力** 代替外部 embedding 检索 |
| **训练** | — | **training-free** | **training-free** |

**跟读口诀：** RetrievalAttention =「**KV 库里的向量检索**加速解码」；InfiniRetri =「**注意力当检索器**，把相关句塞回短窗」。二者都落在 **模型内部信息选择**，不是 B6 的库外段落检索。

## 二、问题立轴：为何还要「检索式注意力」

据 RetrievalAttention §1–§2 与 InfiniRetri §1：

1. **二次注意力 + 线性 KV**：无缓存时，Llama-3-8B 在 **1M** prompt 上生成每 token 约 **1765 s**，注意力占 **>96%**（RetrievalAttention Table 1 叙事）；有缓存则 **1M token ≈ 125 GB** KV（同文 §2.2）——单卡 24GB/40–80GB 不够。
2. **动态稀疏**：top-1000 关键 token 可恢复约 **89%** 注意力质量；但若把「第一个生成步」选出的 top-1000 **静态复用**到后续步，恢复率掉到约 **71%**（Figure 2）→ 必须 **按当前 query 动态选**。
3. **朴素 ANNS 失效（OOD）**：Q 与 K 经不同投影，Mahalanobis 距离显示 Q→K 分布错位；Faiss IVF/HNSW 在 Q→K 上要扫很多向量才高 recall，而 K→K 却轻松（Figure 3）。
4. **另一条缺口（InfiniRetri）**：单纯 YaRN 式继续训扩窗成本高；StreamingLLM 等滑窗 **有效记忆仍困在单窗**；H2O/SnapKV 等 KV 压缩「难超 Full KV」。文主张：用注意力分配与「检索增强」对齐的观察，打破 **跨窗信息屏障**——仍是 **模型内** 选句，不是外挂 RAG。

本篇只钉上述两条近窗方法；位置外推与 PagedAttention 调度见 **[[长上下文位置编码与系统侧]]**。

## 三、站 1：RetrievalAttention — KV 向量检索近似全注意力（2409.10516）

### 3.1 架构意图（主）

总体（§3 / Figure 4a）：

1. **近似注意力**（式 2）：只保留注意力分 $a_{t,i}$ 超过阈值 $\epsilon$ 的索引集 $I_{t,\epsilon}$，对其上的 $v_i$ 做 renormalized softmax 加权。
2. **CPU ANNS**：多数 KV offload 到 CPU，用 **key** 建索引，decode 时用当前 $q_t$ 检索 top 相关 KV。
3. **GPU 静态常驻**：类似 StreamingLLM——**固定初始 token + 局部滑动窗**（实验默认 **128 sink + 512 local = 640**）常驻 GPU。
4. **CPU–GPU 共执行**：GPU FlashAttention（静态部分）与 CPU 检索部分 **并行**算局部注意力，再按 FastAttention 风格合并；减少 PCIe 搬全量 KV。

**范围声明（§3 开篇）：** 主加速 **token generation**；长 prompt 的 prefill 假定已完成（context caching / PD 分离等）。

### 3.2 Attention-aware 索引：如何对付 Q–K OOD（§3.2）

朴素「只按 key 彼此邻近建 IVF/HNSW」对齐不了「从 query 视角找关键 key」。RetrievalAttention：

1. Prefill 已有一批 query 向量；对每个 query 算其 **exact KNN keys**（GPU 可算）。
2. 把「query → 其 KNN keys」的连接 **投影**到 key 空间：共享同一 query 邻居的 keys 互相连边——借鉴跨模态 ANNS **RoarGraph** 的投影思想，**最终索引里不必存 query**。
3. Decode 时 $q_t$ 在该图上搜索 → 扫 **1–3%** keys 可达高 recall（摘要 / §3.2 / §4.4）；相对 IVF，文称索引搜索延迟降约 **74%**。

**跟读：** 索引拓扑按「query 觉得谁近」来连，而不是「key 在 key 分布里谁近」——这是相对 Flat/IVF/HNSW 基线的核心差异。

### 3.3 评测与延迟字段（辅）

**设置（§4.1）：** 单卡 **RTX4090 24GB** + i9 + 128GB DRAM；模型 Llama-3-8B-Instruct-262k、Yi-6B/9B-200K；单 batch。基线含 FullAttention、vLLM（长上下文易 OOM）、StreamingLLM、SnapKV、InfLLM、Quest、InfiniGen，以及 Faiss **Flat / IVF**。默认检索 **top-100** keys；复杂 KV Retrieval 另报 top-2000。

**∞-Bench（Table 2，Avg.；Act. Tokens 叙事）：**

| 模型 | FullAttention | RetrievalAttention（640+100 / 640+2K） | 相对 Full |
|---|---:|---:|---|
| Llama-3-8B | 50.4 | **48.9 / 49.6** | −1.5 / −0.8 |
| Yi-9B | 52.8 | **50.8 / 52.2** | −2.0 / −0.6 |
| Yi-6B | 45.5 | **45.0 / 45.0** | −0.5 / −0.5 |

要点：StreamingLLM 等静态法在复杂 **Retr.KV** 上接近崩；RetrievalAttention 在 Retr.KV 上通过加大 top-$k$ 可逼近 Full。Flat/IVF 要扫 **100% / ~30%** keys 才同级精度，而 RetrievalAttention 扫 **1–3%**（§4.2）。

**RULER（Table 3 Avg.）：** Llama-3-8B Full **86.54** vs RetrievalAttention **84.70**（−1.85）；Yi-9B Full **76.87** vs **76.43**（−0.44）。有效窗口口径仍受底座限制（表中 Claimed/Effective 列），但相对 SnapKV/InfLLM 在长档掉点明显更轻。

**NIH（Figure 5）：** 文称 4K–128K 多位置可稳住；静态近窗法在 needle 落在窗外时失败（附录 A.2）。

**Per-token 解码延迟（Table 4，Llama-3-8B，秒）：**

| 方法 | 4K | 32K | 128K |
|---|---:|---:|---:|
| Full（无 cache） | 0.527 | 6.214 | **43.927** |
| vLLM | OOM… | OOM | OOM |
| StreamingLLM / SnapKV | ~0.03 | ~0.03 | ~0.03（稳但精度差） |
| Flat | 0.140 | 0.328 | 0.922 |
| IVF | 0.128 | 0.201 | 0.373 |
| **RetrievalAttention** | 0.137 | 0.162 | **0.188** |

128K 上相对 Flat / IVF 约 **4.9× / 1.98×** 延迟下降（§4.3）。分解（Table 5）：RetrievalAttention 检索仅 **0.064 s**（占总 **34.0%**），Flat/IVF 检索占 **86.6% / 67.0%**。

**摘要级系统宣称：** 单卡 4090 上服务 **8B @ 128K**，约 **0.188 s/token**，近全注意力精度。

## 四、站 2：InfiniRetri — 注意力分数驱动的句级无限检索（2502.12962）

### 4.1 观察：「注意力分配 ≈ 检索增强」（§3）

HotpotQA 样例可视化（Figure 2）：浅层注意力不规则；**靠近输出的层**对正确证据区（如 Cortina / Northern Italy）高亮，且可到 token 级对齐。按层做「用注意力取答案」的准确率：越近输出越好，**14–15 层**有局部峰（Figure 3）。文把此总结为 **attention allocation pattern aligns with retrieval-augmented**——后续方法设计的归纳偏置。

### 4.2 方法五步（§4 / Figure 4）

1. **Chunk**：按句界把超长文切成约等长段（参数 Chunk Size）。
2. **Merge**：把 **缓存中的 token ID** 与当前段拼成 `MergeToken`（**不是**把 past KV 拼进各层）。
3. **Inference**：对 MergeToken 跑 **标准全注意力**（非 StreamingLLM 式强制 SWA 内核）。
4. **Retrieval in Attention（核心，§4.2）**：
 - 取 **最后一层** 多头注意力，头维求和 $A=\sum_h A^h$（式 2）；
 - 用全 1 的 1D 卷积核（宽度 = Phrase Token Num $k$）在 key 维聚合成短语特征 $t_{ij}$（式 3）；
 - 对 query 维求和得每个 context token 重要度 $s_i$（式 4）；
 - **Top-K** 高分 token（式 5），再把其 **整句** token 写入缓存。
5. **Cache Sentence Token（§4.3）**：缓存粒度是 **句**，内容是 **token ID（模型外）**，不是各层 past KV。下一轮与新段 merge 再推理——中间缓存随「已保留句 ∪ 当前段」动态变。

**跟读对照 RAG：** 分段像 RAG 的 chunk，但 **不用外部 embedding**；检索信号来自 **当前窗内 LLM 自己的 $QK^\top$**。对照经典 KV 压缩：目标不是「压缩 past KV 仍放进同一次 attention」，而是「**挑句重填短窗**」。

### 4.3 评测字段（辅）

**NIH：**

- Llama3-8B-Instruct，最长约 **32k** 设定下：FullKV / StreamingLLM / H2O / SnapKV / PyramidKV vs InfiniRetri——文称先验 KV 压缩均未超 FullKV，而 InfiniRetri **超过** 原 8k 窗能力（Figure 6 叙事）。
- Mistral-7B-Instruct-v0.2：FullKV 约到 **~43k**；InfiniRetri 同参到 **1M** 且文称 **100%**（Figure 7）。
- Qwen2.5-0.5B-Instruct：原约 **32K** → InfiniRetri **1M**，摘要称 NIH **100%**（Figure 1 / 摘要）。
- 文归纳：只要模型在 **短窗内**检索够强，该方法可把检索任务推到「有效无限长」。

**LongBench V1（Table 1，文给 QA Avg / 部分单项）：**

| 模型 | FullKV QA Avg | InfiniRetri（ours）QA Avg | 文述相对提升 |
|---|---:|---:|---|
| Llama3-8B-Instruct | 32.92 | **34.56** | +4.9% |
| Qwen2-7B-Instruct | 25.11 | **42.82** | +70.5%；HotpotQA **14.8→57.52（+288%）** |
| Mistral-7B-Instruct-v0.3 | 24.17 | **37.68** | +55.8% |

摘要另称多文档 QA 上 Qwen2-7B 平均提升可达 **369.6%**（引言；与 Table 1 分项叙事一致方向）。
**注意缺口（文自陈）：** Summarization（GovReport / QMSum / MultiNews）上 InfiniRetri **常低于 FullKV**——摘要要「一次看见全局」，句级缓存筛不完；本篇如实记下，不粉饰。

**LongBench V2（Table 2，No CoT）：** Qwen2.5-7B origin Overall **30.0** → InfiniRetri **41.9**（接近同表 Qwen2.5-72B 的 **42.1**）；Long 档 **24.1→60**。

**消融缓存形态（Table 3，Qwen2.5-7B-Instruct，Multi-Doc QA）：**

| Cache | HotpotQA | 2WikiMQA | Musique |
|---|---:|---:|---|
| Past Key-Value State | 42.15 | 30.71 | 19.22 |
| **Token IDs（Ours）** | **55.95** | **49.89** | **34.6** |

→ 支持「缓存 token ID + 重推理」优于「无训练硬压 past KV」。

**开销（Table 4 / §7）：** 不精调参时，送进模型的平均长度相对原文档大幅下降，例：NrtvQA **18409→834**（约 **4.5%**）；Qwen2 HotpotQA **9152→795**（约 **8.7%**）——文以此解释延迟与算力下降。

## 五、对照总表：两条「检索」不是同一回事

| 维度 | RetrievalAttention | InfiniRetri |
|---|---|---|
| **要解决的痛** | 长上下文 **decode** 延迟 + GPU KV 显存 | **超过训练/宣称窗** 的输入仍要答对（跨窗） |
| **检索键** | $q_t$ ↔ $k_i$ **向量相似度（内积）** | 末层 $A$ → 短语卷积 → token 重要度 |
| **被检索的值** | 选中的 **K/V 向量** 参与近似 softmax | 选中的 **句子 token ID** 进入下一窗输入 |
| **与 Full Attention 关系** | **稀疏近似**同一次注意力（近精度、少扫描） | **多次短窗全注意力** + 外置句缓存（可超 FullKV 的 QA，但摘要任务弱） |
| **CPU 向量库** | 核心组件（OOD-aware ANNS） | 不需要 |
| **典型数字抓手** | 128K @4090：**0.188 s/tok**；扫 **1–3%** | 0.5B NIH：**32K→1M @100%**；HotpotQA **+288%**（Qwen2-7B） |

**共同边界：** 二者都 **training-free**、都强调「模型自己知道该看哪里」；都 **不是** B6 式外挂语料库。差异在于：一个是 **serving 侧 KV 检索加速**，一个是 **应用侧用注意力做跨窗证据搬运**。

## 七、可跟读结论（禁外推未写实验）

1. **动态稀疏是共同前提**：关键 token 随 query 变；静态近窗 / 静态 top-$k$ 会掉点（RetrievalAttention Figure 2；InfiniRetri 对 KV 压缩族的批评）。
2. **「检索」有两层实现**：向量库找 KV（RetrievalAttention）vs 注意力分数找句再重填窗（InfiniRetri）——评测叙事分别偏向 **延迟–精度 Pareto** 与 **NIH/多文档 QA 超窗**。
3. **OOD 是 KV-ANNS 的隐藏坑**：不做 attention-aware 构图时，IVF/HNSW 的 Q→K 很贵；这是 RetrievalAttention 相对 Flat/IVF 的方法学贡献。
4. **任务类型决定 InfiniRetri 上限**：检索/多跳 QA 受益大；**摘要**因需全局信息而偏弱——跟读时不要把 NIH 100% 误读成「一切长上下文任务 SOTA」。
5. **Serving 含义分流**：要在 **单卡 24GB** 上扛 128K 解码延迟 → 看 RetrievalAttention；要在 **短窗模型**上啃百万级 haystack / 多文档 QA → 看 InfiniRetri。二者可并列为「内部检索轴」，但 **不可混成同一系统图**。

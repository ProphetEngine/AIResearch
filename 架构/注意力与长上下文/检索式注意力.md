# Long-context 检索式注意力：RetrievalAttention + InfiniRetri

> **主要来源**：[RetrievalAttention: Accelerating Long-Context LLM Inference via Vector Retrieval](https://arxiv.org/abs/2409.10516)（Liu、Chen、Lu 等，微软研究院、上海交通大学、复旦大学，v3 2024-12-31）；[Infinite Retrieval: Attention Enhanced LLMs in Long-Context Processing](https://arxiv.org/abs/2502.12962)（Ye、Wang、Wang，v1 2025-02-18，以下简称 InfiniRetri）（截至 2025-09-30）。
> **研究线**：架构思想（主：在模型内部用检索近似或替代全注意力）；评测字段（辅：∞-Bench、RULER、大海捞针、LongBench 与逐 token 解码延迟）
> **范围与相邻笔记**：
> - ≠ [[长上下文位置编码与系统侧]]：那篇写位置外推与 PagedAttention 显存管理，本篇假定窗口与 KV 已经就位，只写解码或推理时怎样少看 KV。
> - ≠ [[检索增强与知识外挂]]：那篇从外部语料检索段落，本篇检索的是模型自己的 key 向量或注意力分数，不用外部向量模型。
> - ≠ [[KV缓存量化与压缩]]：那篇把 KV 存成低比特，本篇按需挑出少量 token 或句子，不改 KV 精度。
>
> **意义**：上下文到 128K 以上后，解码的瓶颈是每步都要读完全部 KV：RetrievalAttention 测得 Llama-3-8B 在 100 万 token 上不开缓存时每生成一个 token 要 1,765 秒，开缓存则每百万 token 约 125GB KV。注意力本身又很稀疏，关键 token 随查询变化。两文都利用这一点，不训练、只在推理时检索。RetrievalAttention 把 KV 放到 CPU、用专门照顾查询与 key 分布差异的向量索引，每步只扫 1–3% 的 key，在一张 24GB 的 RTX 4090 上以 0.188 秒/token 跑 8B 模型的 128K 上下文，∞-Bench 平均分 48.9 / 49.6（两种设置），全注意力 50.4。InfiniRetri 用模型末层的注意力分数挑出相关句子、分段迭代重填短窗口，让 0.5B 模型的大海捞针测试过 100 万 token。代价分别是对 CPU 内存与预填充的依赖，以及在需要全局信息的摘要任务上变弱。

## 一、问题背景

长上下文推理有两类开销。预填充一次性处理整段提示，复杂度随长度平方增长；解码阶段每生成一个 token 都要读一遍已缓存的 KV，KV 又随长度线性增长。RetrievalAttention 在 §2.2 给出量级：不开 KV 缓存时，Llama-3-8B 在 100 万 token 上每个 token 要 1,765 秒，九成六以上耗在注意力上；开缓存则每百万 token 约 125GB，一张消费级 GPU 放不下。

缓解办法大致三类：只保留开头与近窗的固定模式（StreamingLLM），按重要性永久丢弃部分 KV（H2O、SnapKV），或按块检索（InfLLM、Quest）。RetrievalAttention 在 §2.3 指出注意力是动态稀疏的：按当前查询选出的前 1000 个 token 平均能恢复 89% 的注意力，若把第一步选出的集合固定沿用，恢复率降到 71%。固定模式与永久丢弃都会丢掉后来才变重要的 token。按查询做向量检索是自然的出路，但现成的近似最近邻索引是按 key 与 key 的相近程度建的，而查询与 key 来自不同的投影、分布不同，直接套用要扫很多向量才能找全（§2.4）。

InfiniRetri 面对的是另一种情况：输入比模型的上下文窗口还长。继续训练扩窗成本高，滑窗方法的有效记忆仍困在单个窗口里，外挂 RAG 又要额外的检索模型。

## 三、RetrievalAttention：KV 向量检索近似全注意力

**设计**（§3）：

- **只管解码**：假定长提示的预填充已经完成（服务商的上下文缓存或预填充、解码分离）。
- **GPU 留固定部分**：开头 128 个 token 加最近 512 个 token 共 640 个常驻 GPU；其余 KV 放到 CPU 内存并建索引。
- **按查询建索引**（§3.2）：预填充时已有一批查询向量，先在 GPU 上算出每个查询的精确最近邻 key，再借跨模态检索索引 RoarGraph 的投影思路，把「被同一查询选中」的 key 连起来；索引里不必存查询。这样每步只扫 1–3% 的 key 就能达到高召回，搜索延迟比 IVF 索引低 74%。
- **CPU 与 GPU 并行**（§3.3）：GPU 算固定部分的注意力，CPU 算检索出的部分，再按公式合并两边结果，避免把全部 KV 搬过 PCIe。

**设定**（§4.1）：一张 RTX 4090（24GB）加 128GB 内存，单批次；模型为 Llama-3-8B-Instruct-262k、Yi-6B-200K、Yi-9B-200K；默认每步检索 100 个 key。

**精度**（Table 2–3）：

| 模型 | ∞-Bench 全注意力 | ∞-Bench 本法（640+100 / 640+2K） | RULER 全注意力 | RULER 本法 |
|---|---:|---:|---:|---:|
| Llama-3-8B | 50.4 | 48.9 / 49.6 | 86.54 | 84.70 |
| Yi-9B | 52.8 | 50.8 / 52.2 | 76.87 | 76.43 |
| Yi-6B | 45.5 | 45.0 / 45.0 | – | – |

要达到同样精度，精确检索与 IVF 要扫 100% 与 30% 的 key，本法只扫 1–3%（§4.2）。附录 A.3 的 Llama-3-8B-1048K 上，大海捞针从 25 万到 100 万 token 全部通过。

**延迟**（Table 4，Llama-3-8B，秒/token）：

| 方法 | 4K | 32K | 128K |
|---|---:|---:|---:|
| 全注意力（不开缓存） | 0.527 | 6.214 | 43.927 |
| 精确检索 | 0.140 | 0.328 | 0.922 |
| IVF | 0.128 | 0.201 | 0.373 |
| 本法 | 0.137 | 0.162 | 0.188 |

vLLM 在长上下文上显存溢出；StreamingLLM、SnapKV 约 0.03 秒但精度差。128K 时本法比精确检索与 IVF 快 4.9 倍与 1.98 倍；检索只占本法总时间的 34.0%，精确检索与 IVF 分别占 86.6% 与 67.0%（Table 5）。

## 四、InfiniRetri：注意力当检索器

**观察**（§3）：在多跳问答样例上，越靠近输出的层，注意力越集中在正确证据上；按层「用注意力取答案」的准确率随层数上升，在 14 与 15 层有局部峰。作者据此认为注意力分配与检索增强是对齐的。

**方法**（§4）：

1. 按句子边界把超长输入切成约等长的段。
2. 把缓存里保留的 token ID 与当前段拼接，送入模型做标准注意力。缓存存的是 token ID，在模型外，不是各层的 KV。
3. 取最后一层各头注意力之和，在 key 维上用全 1 卷积聚成短语级得分，再对查询维求和得到每个 token 的重要性。
4. 取得分最高的 token，把它们所在的整句写入缓存，与下一段拼接，循环到输入结束。

评测统一用段长 1024、Top-K 300、短语长度 15（§5）。

**结果**：

- **大海捞针**（§5.1）：Mistral-7B-Instruct 原本约到 43K token，加本法后到 100 万 token 仍全部答对；Qwen2.5-0.5B-Instruct 的有效长度从 32K 扩到 100 万以上。
- **LongBench**（Table 1，问答平均）：Llama3-8B-Instruct 32.92 → 34.56，Qwen2-7B-Instruct 25.11 → 42.82，Mistral-7B 24.17 → 37.68；最大单项增幅是 Qwen2-7B 的 HotpotQA，14.8 → 57.52。摘要类任务上效果较差（§5.2）。
- **LongBench v2**（Table 2，不用思维链）：Qwen2.5-7B 总分 30.0 → 41.9，接近同表 Qwen2.5-72B 的 42.1。
- **缓存形态**（Table 3，Qwen2.5-7B，多文档问答）：缓存 token ID 在 HotpotQA、2WikiMQA、Musique 上为 55.95、49.89、34.6，缓存各层 KV 为 42.15、30.71、19.22。
- **输入长度**（Table 4）：送入模型的平均长度大幅缩短，例如 NarrativeQA 从 18409 降到 834（约 4.5%）。

## 五、意义

两文给出了「模型内部检索」的两种做法。RetrievalAttention 仍在近似同一次全注意力，检索的是 KV 向量，服务于解码延迟和显存：它说明在动态稀疏的前提下，只要索引照顾到查询与 key 的分布差异，CPU 内存加向量检索可以让消费级显卡跑 128K 上下文，精度接近全注意力。InfiniRetri 检索的是句子，把超长输入拆成多次短窗推理，服务于超窗问答：它说明模型自己的注意力可以当检索器用，不需要外部向量模型。两者都不训练，都依赖「关键信息只占上下文一小部分」这一前提，因此对需要通读全文的任务帮助有限。此后这条线的重心转向把稀疏写进训练（见分工表中的 NSA）。

## 六、局限与待核实

- **RetrievalAttention 的适用面**：只加速解码，预填充与索引构建假定已完成；需要大容量 CPU 内存（实验为 128GB）。附录 G 在 Llama-3-70B 上做最难的 KV 检索任务，全注意力 35.0，本法 23.5，掉点比 8B 上明显；附录 E 的 RULER 128K 上全注意力 78.7、本法 74.7。
- **RetrievalAttention 的版本差异**：v3（2024-12-31）相对 v2（2024-09-18）补了附录 E 的 Quest、InfiniGen 基线，附录 F 的分层预算，附录 G 的 70B 实验；以及附录 A.3 的百万 token 大海捞针；主表数字两版一致。本篇按 v3。
- **InfiniRetri 的对比口径**：Table 1 中 Llama3 与 Qwen2 的基线数字取自 DynamicKV 论文，Mistral 的取自 CAKE 论文（表注），不是同一环境重跑。Qwen2-7B 在 HotpotQA 上的全量 KV 只有 14.8，最大增幅 288% 建立在这个偏低的基线上。表注写 Mistral-7B-Instruct-v0.2，正文与表中写 v0.3，版本不一致。
- **InfiniRetri 的适用面**：作者自陈摘要任务需要全局信息，本法一次看不到全部相关内容，效果较差；参数（段长、Top-K、短语长度）对不同模型与题型的最优值不同，评测用了统一取值。文中没有直接报墙钟延迟，延迟下降是由输入长度缩短推断的。只有 v1，没有单列局限节。
- **证据来源**：两文结果均为作者自报；两文的任务、模型与指标不同，数字不能横比。

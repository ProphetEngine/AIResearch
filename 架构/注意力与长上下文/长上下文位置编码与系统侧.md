## 一、为何长上下文是枢纽（智能体 / 仓库级编码）

长上下文不是单纯的「上下文窗口数字越大越好」，而是把三类产品形态绑在同一条能力链上：

1. **智能体（Agent）**：多轮工具调用、长轨迹反思、环境观测回放，都要求模型在**单次前向 / 单次会话状态**里同时看见指令、历史动作、工具返回与当前目标。窗口不够时，只能靠摘要或检索外挂——外挂会丢细节、引入延迟与一致性风险。
2. **仓库级编码（repo-scale coding）**：一次改动常常跨多文件、多模块依赖与长测试日志。若有效上下文只能覆盖「当前文件 + 少量邻居」，模型就无法做跨文件一致性推理，只能靠 IDE 检索拼碎片。
3. **系统可服务性**：窗口从 4k → 32k → 128k，KV cache 近似随序列长度线性膨胀；同一块 GPU 上能并发的请求数急剧下降。于是「算法上能吃长文」与「服务端塞得下、吞吐还过得去」必须一起设计。

本议题的枢纽位置因此是：**位置编码 / 注意力变体决定「模型认不认得了更长位置」；Serving 侧的 KV 管理决定「认得了之后，钱与显存是否扛得住」。** YaRN 偏前者，PagedAttention / vLLM 偏后者。

## 二、算法侧：位置编码与注意力变体（RoPE 基线 → YaRN）

### 2.1 RoPE 基线直觉（跟读锚点）

经典引用：Su et al., *RoFormer*（[arXiv:2104.09864](https://arxiv.org/abs/2104.09864)；PDF [https://arxiv.org/pdf/2104.09864](https://arxiv.org/pdf/2104.09864)）。

**跟读直觉（据 YaRN §2.1 对 RoPE 的复述）：**

- 把隐层维度成对看成复数平面上的坐标；对 query / key 施加与**绝对位置** $m$ 相关的旋转：$f_W(x_m, m, \theta) = e^{i m \theta} W x_m$。
- 每个维度对有自己的频率 $\theta_d = b^{-2d/|D|}$（常用 $b=10000$）。
- 关键性质：**旋转后 $q^\top k$ 只依赖相对距离 $m-n$**，因此是一种把「相对位置」嵌进注意力点积的绝对编码。
- YaRN 还引入波长 $\lambda_d = 2\pi / \theta_d$：某维转满一圈需要多少 token。波长相对预训练上下文长度 $L$ 的长短，决定该维更像「局部相对」还是「近乎绝对位置」。

**痛点（YaRN 引言与背景）：** 多数位置编码——包括 RoPE——**难以在显著超过预训练长度 $L$ 的序列上直接外推**；ALiBi 等有有限外推，但「远大于预训练长度」仍普遍失败（YaRN 引 Kazemnejad et al., 2023）。

扩展问题因此常写成：给定预训练最大长度 $L$，要到 $L'>L$，定义缩放因子 $s = L'/L$，并修改 RoPE 的 $g(m)$（位置映射）与 $h(\theta)$（频率映射）。

### 2.2 从 PI → NTK 族 → YaRN：方法谱系（跟 Figure 1）

YaRN 把此前工作整理成演进图（论文 Figure 1），跟读时可按「改什么、怕什么」记：

| 方法 | 核心改动直觉 | 典型适用 |
|------|--------------|----------|
| **Position Interpolation (PI)**（Chen et al., 2023 等） | $g(m)=m/s$，所有 RoPE 维**同等拉伸** | 小数据微调可扩窗，但高频信息易丢 |
| **"NTK-aware"**（bloc97, 2023a） | 不按同一 $s$ 均匀插值，考虑高频损失（NTK 视角） | Code Llama 等采用；底座 $b$ 难选 |
| **"Dynamic NTK"**（emozilla, 2023） | 推理时按当前长度动态调 $s=\max(1,l'/L)$ | 无微调外推；Qwen 7B 等用过 |
| **"NTK-by-parts"**（bloc97, 2023b） | 按波长相对 $L$ 分段：短波少插 / 长波多插 | 微调场景更强 |
| **YaRN** | **NTK-by-parts + 注意力温度 / length scaling** | 少数据微调 SOTA；可接 Dynamic Scaling |

### 2.3 YaRN 怎么扩窗（定义级跟读）

**（1）NTK-by-parts：按「转了几圈」决定插值强度**

引入 $r(d)$：在原预训练长度 $L$ 下，第 $d$ 维大约转几圈。再用阈值 $\alpha,\beta$ 分段：

- $r<\alpha$：像 PI 一样按 $s$ **只插值、避免外推**；
- $r>\beta$：**不插值**（保住短波局部相对距离）；
- 中间用 ramp 平滑过渡。

Llama 族上论文实验给出推荐：$\alpha=1,\ \beta=32$（§3.2）。

**（2）Attention scaling（温度 $t$）**

在 softmax 前对 logits 引入温度 $t$；等价地可用 **length scaling**：把 $q_m,k_n$（或预计算的旋转嵌入）同乘 $1/\sqrt{t}$，从而**不改注意力内核代码**也能改注意力分布。对 LLaMA / Llama 2，YaRN 推荐拟合式（§3.3 Eq.15）：

$$
\frac{1}{t} = 0.1\ln(s)+1
$$

该式在多个未微调 LLaMA 尺寸上按最低困惑度拟合；论文称对 Llama 2 也大致适用。

**定义 2（原文）：** YaRN = **注意力缩放（Eq.14）** + **NTK-by-parts**。

**（3）Dynamic Scaling / Dynamic-YaRN**

推理时不要死固定 $s=L'/L$，而按当前序列长度更新 $s=\max(1,l'/L)$，避免「未到 $L'$ 就打折、一过 $L'$ 就崩」。与 YaRN 结合即 Dynamic-YaRN；摘要称**无微调可超过 2× 上下文扩展**。注意：若用 KV cache，应缓存**施加 RoPE 之前**的 K/V，因为 $s$ 一变，每个位置的旋转都会变（§3.4）。

### 2.4 读论文时必跟的实验要点（仅录 PDF 中数字）

**训练设置（Llama 2 → 长窗，§4.1）：**

- 目标：把 Llama 2 7B/13B 扩到 **128k** 量级；$s=16$ 与 $s=32$（相对原 4k）。
- 数据：PG19 切成 **64k** 段；$s=16$：**400 steps**，global batch **64**；$s=32$：从 $s=16$ checkpoint 再 **200 steps**（仍用 64k 数据，但评测可外推到 128k）。
- 优化：lr $2\times10^{-5}$，warmup 20，AdamW $\beta_1=0.9,\beta_2=0.95$，Flash Attention 2 + FSDP。
- 消融用原 LLaMA 7B（预训练窗 **2k**）扩到 32k：$s=16$，PG19 切 32k，同样 400 steps。

**长序列困惑度（Table 1，Proof-pile 十篇 ≥128k 文档，滑动窗 $S=256$）：**

- Llama 2 7B YaRN $s=16$（400 steps）：在 8k/16k/32k/64k 上 perplexity 分别为 **3.51 / 2.99 / 2.65 / 2.42**；到 **131072** 时标为 **>10¹**（崩溃）。
- 同模型 $s=32$（400+200）：对应 **3.56 / 3.04 / 2.70 / 2.45 / 2.37**——**在 128k 仍稳定**，体现「64k 训练 → 128k 外推」。
- 13B 同表：$s=16$ 在 131072 为 **>10¹**；$s=32$ 为 **2.24**。

**Passkey（§4.3）：** 32k 微调的 LLaMA 7B，在 2k–32k 随机位置放五位数字 passkey，每长度 50 次；图示 YaRN 在同等训练预算下优于其它插值（具体曲线见 Figure 3，此处不臆造百分点）。

**短文能力回退（Table 3，Llama 2 + YaRN）：** 相对原版基线，Open LLM 四项平均下降有限；文中称 $s=16$ 与 $s=32$ 之间平均再降约 **0.49%**。

**效率宣称（摘要原文）：** 相对 previous methods，YaRN 需要约 **10× 更少 tokens**、**2.5× 更少 training steps**；微调数据量称少于原预训练数据的 **∼0.1%**。代码：https://github.com/jquesnelle/yarn 。

**兼容性：** 因主要改 RoPE 频率与可预计算缩放，与 Flash Attention 2 等「改注意力实现」的库可直接兼容（§3.3）。

## 三、系统侧：KV cache 瓶颈与 PagedAttention / vLLM

### 3.1 瓶颈画像（跟 Introduction + §3）

自回归生成分两阶段：

- **Prompt / prefill**：已知前缀可并行算，顺便写出各层 K/V；
- **Decoding**：每步只吃一个新 token，却要读出**全部历史 K/V**——工作负载常变为 **memory-bound**。

批处理能抬吞吐，但每条请求的 KV 都巨大且长度未知。论文在 **A100 40GB** 上画 13B 级 LLM 内存饼图（摘要旁标注与正文 §1）：

- 模型权重约 **65%（约 26GB）**；
- KV cache 约 **>30% / close to 30%**；
- 激活只占很小一块。

**单请求量级例子（OPT，§3）：** 单 token 的 KV 约 **800 KB**（FP16）；最大 2048 token 时，单请求 KV 可达约 **1.6 GB**。GPU 显存几十 GB 时，粗放管理只能塞进很少并发。

**既有系统浪费（连续预分配，Fig.2–3）：**

1. **Reserved**：为尚未生成的 future tokens 预留；
2. **Internal fragmentation**：按「可能的最大长度」超额预留；
3. **External fragmentation**：不同请求不同预分配块导致空洞。

剖析结果：KV 区里真正存着有效 token 状态的比例可低至 **20.4%–38.2%**（Fig.2）。吞吐被「假满」的显存卡住。

另：并行采样、beam search 等需要 **跨序列共享 prompt / 公共前缀 KV**；连续张量布局很难做细粒度共享（文中举例：并行采样时 prompt 部分约占其实验总 KV 的 **12%** 可共享；beam 场景可有更大共享空间）。

### 3.2 PagedAttention 思想（OS 虚拟内存类比）

**类比（原文）：**

| OS | vLLM / PagedAttention |
|----|------------------------|
| 进程 | 请求 / 序列 |
| 字节 | token |
| 页 (page) | KV **block**（固定 token 数） |
| 页表 | **block table**（逻辑块 → 物理块） |

做法：

1. 把每条序列的 KV 切成固定大小的 **KV blocks**（默认 **block size = 16** tokens，§7.2）；
2. 物理上**不必连续**；注意力核按 block 取 K/V 做分块 attention（§4.1 公式把标准 attention 改写成对 $\lceil i/B\rceil$ 个 block 的累加）；
3. 逻辑块从左到右填满才分配新物理块 → **单请求浪费被限制在「最后一个未满 block」内**，逼近「near-zero waste」；
4. 同尺寸 block 消灭外碎片；按需分配消灭大块内碎片；block 级引用计数 + **copy-on-write** 支持并行采样 / beam / 共享前缀。

### 3.3 vLLM 系统拼图（跟 Figure 4）

- **集中式 Scheduler**：iteration-level / 细粒度批处理，协调多 worker；
- **KV Cache Manager + Block Allocator**：维护 GPU（及 CPU swap）上的物理块与每请求 block table；
- **PagedAttention kernel**：带间接寻址的注意力；微基准显示相对高度优化的 FasterTransformer attention 有约 **20–26%** kernel 延迟开销（Fig.18a），但端到端仍因更高批容量大幅领先；
- **抢占 / 恢复**：显存紧时可将整段序列的块 swap 到 CPU，或 **recompute** 恢复（§4.5、§7.3）；
- **分布式**：各 worker 本地 cache engine + 模型分片，调度器统一发块管理指令。

**论文摘要级结果：** 相对当时 SOTA serving 系统（文中对比 [31, 60] 等），在相同时延水平下，流行 LLM 的吞吐提升约 **2–4×**，且**不改动模型精度**。源码：https://github.com/vllm-project/vllm 。

**其它跟读数字（评测节选）：**

- 共享前缀翻译负载（LLaMA-13B）：one-shot 共享相对 Orca (Oracle) 吞吐 **1.67×**；5-shot 共享 **3.58×**（Fig.16）；
- Chatbot（ShareGPT，OPT-13B）：相对三组 Orca 基线可维持约 **2×** 更高请求率（Fig.17）；
- Block size：ShareGPT 上 16–128 较佳；短序列 Alpaca 上过大 block 伤性能；默认取 **16**。

## 四、算法 × 系统如何合在一起「能读更长且读得起」

把两条线叠在同一张因果图上：

`
更长有效上下文
 │
 ├─ 算法：RoPE 外推失败 ──► PI / NTK / YaRN（改位置频率 + 注意力温度）
 │ └─ 微调极少数据 / Dynamic Scaling 无微调扩窗
 │
 └─ 系统：KV 随长度膨胀 + 碎片 ──► PagedAttention 分块 + 按需分配 + 共享
 └─ 同卡更大 batch / 更高吞吐 / 支持长请求与复杂解码
`

**合在一起时的产品含义：**

1. **「能读」**：YaRN 类方法让预训练在 2k/4k 上的 RoPE 模型，用远小于重训的代价适应 32k/64k/128k；Dynamic-YaRN 还能在推理期平滑越界。
2. **「读得起」**：窗口变长后，若仍按 max length 连续预分配，KV 浪费会把并发打穿；分页使「长请求」与「多短请求」可以在同一块显存里交错生存。
3. **交叉注意点（工程真实摩擦）：**
 - Dynamic Scaling 改 $s$ 时，**KV 必须在 RoPE 前缓存**（YaRN §3.4）——与「推理引擎默认缓存旋转后 K/V」的实现假设冲突，需要引擎配合。
 - 超长序列使 **单请求 KV 占满显存**：vLLM 的 swap/recompute 与调度策略决定尾延迟；算法扩窗成功 ≠ 服务 SLA 自动满足。
 - Flash Attention / PagedAttention / 扩窗插值三者都动「注意力路径」：YaRN 刻意保持「只改 RoPE 嵌入」以降低冲突；系统侧则接受 kernel 间接层开销换批容量。

一句话：**YaRN 解决位置外推与注意力分布；vLLM 解决把更长（或更多）KV 装进 GPU 并维持吞吐。** 智能体与仓库级编码同时需要两者。

## 五、常见误区与引用

### 5.1 常见误区

1. **「上下文窗口广告数字 = 有效长程利用」**
 Passkey / 困惑度只是探针；真实仓库推理还依赖训练数据分布、中间停顿与工具设计。YaRN Table 1 也显示：同一套方法 $s=16$ 与 $s=32$ 在 128k 上成败不同——**扩展因子与训练长度选择仍关键**。

2. **「只做 PI 同等拉伸就够」**
 YaRN 论证：均匀拉伸会损高频；短波维应少插以保留局部相对距离（NTK-by-parts）。

3. **「无微调 Dynamic NTK / Dynamic-YaRN 可以无限外推」**
 论文表述是 **more than 2×** 量级的无微调扩展（摘要），不是任意长度；且实现受 KV+RoPE 缓存顺序约束。

4. **「上了 vLLM = 长上下文算法问题消失」**
 PagedAttention **不改变**模型的位置外推能力；它提高的是**给定模型与长度下的显存利用率与吞吐**。反过来，YaRN **不自动**减少 KV 体积（长度仍在，只是模型更能用）。

5. **「Block 越大越好 / 越小越好」**
 大 block：内碎片↑、共享机会↓；小 block：GPU 并行与 kernel 效率↓。vLLM 默认 16 是折中，不是定理。

6. **「注意力变体（改 softmax / 稀疏 / 线性）与位置插值是同一件事」**
 ReRoPE、LM-Infinite 等会改注意力机制本身；YaRN 强调自己主要是 **embedding interpolation + 可预计算 scaling**，从而易接 FlashAttention2。混为一谈会导致选型错误。

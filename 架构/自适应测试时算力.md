# 自适应测试时算力：SelfBudgeter + Strategic Scaling（Bandit）（≠ TTS 通史）

> **主要来源**：[SelfBudgeter: Adaptive Token Allocation for Efficient LLM Reasoning](https://arxiv.org/abs/2505.11274)（Li、Dong、Ma 等，北京大学 / BandAI, ByteDance，v6 2026-04-17）；[Strategic Scaling of Test-Time Compute: A Bandit Learning Approach](https://arxiv.org/abs/2506.12721)（Zuo、Zhu，UC Riverside，v2 2026-04-23；abs 页注记 ICLR 2026）；辅以 [Learning How Hard to Think](https://arxiv.org/abs/2410.04707)（Damani 等，MIT，v1 2024-10-07）（截至 2026-04-23）。
> **研究线**：架构思想（主）——同一总预算下按查询难度分配 token 或样本的接口；评测字段（辅）——各文给出的算力与准确率权衡。
> **范围与相邻笔记**：本篇只写自适应分配方法：单个查询内该写多长（SelfBudgeter），一批查询之间样本预算怎么摊（Strategic Scaling），以及采样前预测难度的两阶段做法（How Hard）。
> - ≠ [[推理时扩展TestTimeScaling]]：那篇写测试时扩展的通史与 Snell 等的最优缩放，本篇只写按难度分配算力的方法。
> - ≠ [[测试时训练]]：那篇在推理期改参数，本篇三种方法都不改权重。
> - ≠ [[推理时树搜索ABMCTS]]：那篇在单题内分配答案树的宽与深，本篇按查询难度分配 token 与样本。
>
> **意义**：测试时扩展默认「每题同样多算」，这三篇说明按难度分配能在同预算下明显提分或在同精度下明显省算力，并给出了从单查询长度到跨查询样本两个粒度上的可用方法。

## 一、问题背景：均匀分配的浪费

- **单查询内过长**：长思维链推理模型在简单题上也写得很长。SelfBudgeter §1 引的例子：回答「2+3 等于几」时 QwQ-32B 给出 13 种解法，生成的 token 是 Qwen2.5-72B-Instruct 的 100 倍。
- **跨查询均匀**：Best-of-N 等方法给每题相同的样本数，易题过剩、难题不足，无解的题也照样消耗预算（Strategic Scaling §1、§3）。
- **难度难以事先知道**：How Hard §1 指出，Snell 等已说明按题自适应分配在理论上可提升效率，但此前的难度度量只能事后估计，代价比生成本身还高。

脉络上，长度控制一支（s1、L1、Elastic Reasoning）解决了「给定预算能否守住」，但预算仍由用户给；SelfBudgeter 让模型自己估预算。跨查询一支从 Snell 的「按难度分配有收益」出发，How Hard 用事先训练的探针估难度，Strategic Scaling 改为边采样边估、无需额外训练。

## 三、SelfBudgeter（2505.11274）：单查询内自估预算

### 3.1 定位

SelfBudgeter §1–§2 把既有长度控制分为三类：提示词控长（缺乏精确控制）、训练时的 SFT 或长度惩罚 RL、路由器（额外分类器开销）；并指出 L1 与 Elastic Reasoning 能在给定预算下控长，但不能让模型自己估计合适的长度。

目标有两个：用户不给预算时，模型自估够用的最小 token 预算；无论自估还是用户预填，生成都严格贴合预算。预算数字同时告诉用户大概要等多久，用户可提前终止。输出格式为 `<budget>整数</budget><solution>…</solution>`；用户预填 `<budget>` 时模型只生成 `<solution>`（§4.1）。

### 3.2 训练流程（Figure 2）

1. **数据预处理**：底座模型先答题；答对则以该次长度作为可接受的最大预算 b_max，答错则 b_max 为无穷（式 5）。
2. **冷启动 SFT**：学会新格式。GSM8K 与 MATH 各取 1,500 条模型答对的样本，加上 s1k-1.1 中 DeepSeek-R1 答对的 630 题，共 3,630 条；训练 1 个 epoch，温度 0.6（§4.4）。
3. **RL（budget-guided GRPO）**：使用 STILL-3-Preview-RL-Data（约 30K 条，来自 MATH、NuminaMathCoT 与 AIME 1983–2023），训练 3 个 epoch（§4.4）。附录 A.2 把 GRPO 写作「Global Reward Policy Optimization」，此处照录原文写法。

### 3.3 奖励设计（§3）

- **格式**：格式错误直接给最低分。
- **预算惩罚（式 3）**：预算超过 b_max 时扣分，促使预算向「已知够用」的长度收缩。
- **PreB（精确预算控制奖励，式 4，受 cosine reward 启发）**：实际长度须落在预算 b 的 α·b 范围内，否则降到最低分；范围内答对时偏好略短于预算（(1−α)·b），答错时偏好略长（(1+α)·b），鼓励多想（式 2）。
- **准确率约束**：保证「答对但预算超限」的最低总奖励不低于「答错但预算合规」的最高总奖励。
- **动态 α（§4.6，式 6）**：α 随训练从 6.0 线性降到 0.1。Table 3 中线性日程三个数据集的准确率都高于固定与余弦日程；固定、余弦日程压缩更狠，但难题准确率下降（§5.2）。

### 3.4 主结果（Table 1；准确率 % / 平均长度 token，三个随机种子平均）

| 模型 | GSM8K | MATH500 | AIME2025 |
|---|---|---|---|
| R1-Distill-Qwen-1.5B | 73.09 / 2865.08 | 74.93 / 5327.12 | 22.22 / 14444.03 |
| L1-Max(3600) | 79.56 / 571.72 | 76.73 / 1753.42 | 17.88 / 5213.89 |
| **SelfBudgeter-1.5B** | **84.10 / 1231.79** | **78.47 / 2326.85** | 21.11 / 4288.10 |
| R1-Distill-Qwen-7B | 87.09 / 1918.21 | 86.73 / 5387.19 | 28.89 / 22158.79 |
| **SelfBudgeter-7B** | 90.30 / 991.13 | **86.87 / 2666.58** | **30.00 / 12241.84** |

Table 1 另有 E1-Math-1.5B、Eurus-2-7B-PRIME、Qwen-2.5-7B-Simple-RL 等基线。正文（§4.5）：相对 1.5B 底座，GSM8K 准确率高 11.01 个点、长度为原来的 43%；MATH500 高 3.54 个点、长度为 44%；AIME2025 长度为 30%、准确率相当。SelfBudgeter-7B 平均压缩比为 48%，GSM8K 上比最好的基线低 0.68 个点。摘要称数学推理任务上平均响应长度压缩 61%。L1 的长度由提示模板指定，E1 靠硬截断，SelfBudgeter 在推理时自估。

**消融（Table 2）**：只奖励格式时准确率崩溃（GSM8K 1.64%）；加入正确性后准确率恢复，但难数据集上仍很长；缺 PreB 或缺预算惩罚都会在部分数据集上失衡，全部组件一起才稳定。

**泛化（Table 4，v6 新增）**：GPQA 与 SCoRE 上相对 1.5B 底座大幅缩短；SCoRE 准确率 16.26%，为对比组最高；GPQA 30.65%，低于底座的 33.04% 与最强基线的 34.30%。

## 四、Strategic Scaling（2506.12721）：跨查询的 bandit 分配

### 4.1 问题设定（§3–§4.1）

总预算 B、查询集 S，算力单位是「生成一条响应」，目标是最大化平均覆盖率（coverage）或准确率。均匀分配给每题 B/n。与相关工作的区别（§2）：单查询内的动态 Best-of-N 不跨题挪预算；Damani 等（How Hard）需要先训练辅助模型来指导分配，属于两阶段做法。该文把分配建模为纯探索式 bandit：每题是一个 arm，拉一次即再采样一条响应。

### 4.2 Algorithm 1：探索规则加消除规则（§4.2）

1. 活跃集初始化为全部查询；每题记录已有响应、当前最优响应及其得分。
2. 每轮按探索规则（默认在活跃集上均匀）为活跃查询各生成 K 条响应。
3. 若某题当前最优得分达到阈值 γ，就把它移出活跃集。
4. 直到预算用尽或活跃集为空。

奖励来源可以是 ORM、PRM 或标准答案（GT）。超参为粒度 K 与阈值 γ。

**扩展（§4.3）**：聚合方式可从 Best-of-N 换成 Self-Consistency（用于 Qwen3-4B 等推理模型；超过一定比例如 50% 的响应答案一致即消除，此时可不用 PRM）；探索规则可换成 UCB、Gap 或新提出的 Entropy（优先响应模式更分散、采样更少的查询，在极难查询集上尤其有效），并设单题上限 max_sample 防止一题吞掉预算；还可按 token 计预算，或处理逐个到达的流式查询。

### 4.3 理论（§4.4）

在 Assumption 1（神谕得分 ≥ γ 当且仅当答案正确）下，设每题单次答对概率为 Δ_x。要以至少 1−δ 的概率答对全部查询，Algorithm 1 所需总预算为 Θ̃(Σ_x 1/Δ_x)，在对数因子内达到信息论下界；均匀分配需要 Ω̃(|S| / min_x Δ_x)。例如 Δ_i = i/n 时，前者为 Õ(n)，后者为 Ω̃(n²)，相差 n 倍（Theorem 1）。Proposition 1：任何对每题先固定探索 m 次的两阶段（先探索后决策）算法，在易题上都要多付 Θ(m) 的均匀探索开销。

### 4.4 实验（§5）

设置：MATH-500、AIME25、LiveCodeBench；平均预算 {4, 8, 16, 32}，4 次随机运行取平均；模型包括 Llama-3.2-1B-Instruct、Llama-3.1-8B-Instruct、DeepSeek-R1-Distill-Llama-8B、Qwen3-4B、Gemini-2.5-Flash-Lite。奖励神谕：Llama 系列在 MATH-500 上用 Qwen2.5-Math-PRM-7B；Gemini-2.5-Flash-Lite 用 Gemini-3.0-Flash 作评判；AIME25 用 Self-Consistency；LiveCodeBench 用代码执行的标准答案。

同预算下相对基线的最大提升（摘要）：

| 数据集 | 绝对提升 | 相对提升 |
|---|---|---|
| MATH-500 | 11.10% | 15.04% |
| AIME25 | 10.82% | 14.44% |
| LiveCodeBench | 11.23% | 15.29% |

§5.2 的例子：平均预算 8 时，Llama-3.1-8B-Instruct 在 MATH-500 上绝对提升 11.10%，相当于 3.93 倍效率；AIME25 上 Qwen3-4B 在平均预算 16 时覆盖率绝对提升 10.82%，相当于 4.00 倍效率；Gemini-2.5-Flash-Lite（预算 {1, 2, 3, 4}）准确率绝对提升 3.4%，效率超过 2 倍。摘要的行为结论：预算流向更难的查询，同时保持易题准确率；难题中进一步优先可解的题，减少在无解题上的空耗。

## 五、How Hard（2410.04707）：采样前预测难度

Strategic Scaling 把它列为两阶段对照。二者都跨查询分配算力，区别在于 How Hard 先训练探针、再求解分配，Strategic Scaling 不额外训练、边采样边分配。

**方法（§3）**：定义边际奖励 Δ_ij = q(x_i, j) − q(x_i, j−1)，即已分配 j−1 份算力时再加一份的期望收益；在预训练语言模型的隐藏表示上训练轻量探针，以均方误差预测各预算下的边际奖励，再求解分配问题。两种用法：

1. **自适应 best-of-k**：动态决定送入重排器的采样数；
2. **路由**：在便宜但弱的解码与昂贵但准的解码之间选择（一对 Gemma-2B / Gemma-7B，或普通采样与 value-augmented sampling）。

**结果**：同质量下算力最多省 50%，或同预算下质量最多升 10%（摘要）；路由设定下只需对 50–75% 的查询调用昂贵解码就能追平其整体表现（§1）。Table 1：探针在 Code、Math 上以中位数为阈值区分难易的准确率分别为 74% 和 84%，各设定均超过 70%。

## 六、意义

三篇共同把「多算一点能换分」细化为「该在哪儿多算」：SelfBudgeter 在单个响应的长度上省算力，并让用户在生成前看到预算；Strategic Scaling 在一批查询之间挪样本预算，并给出相对均匀分配与两阶段分配的理论界；How Hard 说明难度可以从隐藏表示中事先预测。三者都不改推理期权重，可以叠加使用（单题长度由模型自估，跨题样本由 bandit 分配）。

| 问题 | SelfBudgeter | Strategic Scaling | How Hard |
|---|---|---|---|
| 分配对象 | 单个响应的 token 长度 | 跨查询的采样次数 | 采样次数或强弱解码路由 |
| 是否需要额外模型 | 否（策略在底座内） | 否（需奖励神谕，可用 SC 代替 PRM） | 是（难度探针） |
| 用户可调 | 预填 `<budget>` | K、γ、max_sample、总预算 | 平均预算、best-of-k 或路由 |

## 七、局限与待核实

1. **SelfBudgeter**：只在 1.5B、7B 的 R1 蒸馏模型上实验；AIME2025 上 1.5B 准确率（21.11）略低于底座（22.22）；GPQA 上准确率低于底座与最强基线。论文的 Limitations 段较笼统，未给出具体失效情形。
2. **Strategic Scaling**：理论依赖 Assumption 1（神谕得分达标即答对），PRM 或评判模型不可靠时不成立，论文附录 C.2.1 专门讨论了 PRM 质量的影响；最大提升是各设定下的峰值，不同模型、预算下差异很大（如 Gemini-2.5-Flash-Lite 只有 3.4%）。
3. **How Hard**：探针要先在训练查询上按各预算采样、估出边际奖励再训练（§3.1），换任务或换解码设置都要重做这一步；Table 1 中区分难易的准确率为 Code 74%、Math 84%、两种 Chat 路由各 72%，作者也认为仍有改进空间。
4. **不可直接比较**：三篇的底座、数据集、预算单位（token 与样本数）都不同，数字不能横向对照。
5. **版本差异**：
   - SelfBudgeter v6（2026-04-17）相对 v5（2026-01-09）新增 §5.3 泛化实验（Table 4，GPQA 与 SCoRE），Table 1–3 数字不变。
   - Strategic Scaling v2（2026-04-23）相对 v1（2025-06-15）新增 AIME25、Qwen3-4B 与 Gemini-2.5-Flash-Lite 实验、Self-Consistency 聚合、Proposition 1、按 token 计预算与流式查询变体、max_sample 上限；v1 摘要中 LiveCodeBench 的最大提升为 7.41%（相对 14.40%），v2 改为 11.23%（相对 15.29%）。
   - How Hard 只有 v1。
6. **会议信息**：How Hard 的 abs 页与 HTML 均无录用注记（HTML 为 v1 预印本），本篇不写其会议归属。
7. **图读数**：各文 Figure 中的曲线未读数；Strategic Scaling 在 LiveCodeBench 上的效率倍数只见于图中，未写入。
